# 検証: Pi Durable と Souther で、設計からアプリケーションが出来るか

untie の設計を材料に、[Pi Durable](https://github.com/earendil-works/pi/tree/main/packages/durable) (エージェントの実行基盤) がアプリケーションを作り、
業務ルールは [Souther](https://github.com/souther-lang/souther) のモデルを呼ぶ、という流れが実際に動くかを確かめたもの。
本体のワークスペース (`packages/*`・`apps/*`) には入れていない。検証のためのスクリプトと、その材料だけを置く。

確かめた日: 2026-11-11。Node 22.23、JDK 25 (Temurin)、Souther 0.4.1、souther-wasm-compiler 0.4.1、`@souther-lang/wasm` 0.4.1、Pi Durable 1.5.2。

## 確かめたこと

| # | 確かめたこと | 結果 |
| --- | --- | --- |
| 1 | untie が書き出した業務ルール (`workspace/design/sys_pms.sou`。宿泊サンプルの宿泊管理システム) を、Souther が受け付ける | 通った (`adequacy: satisfied`。7 つの操作) |
| 2 | そのモデルを WebAssembly にコンパイルできる (`souther compile --target wasm`) | 通った (`pms.wasm`) |

| 4 | Pi Durable が、ツール (read・write・bash) で作業フォルダにアプリケーションを書き、依存を入れ、テストを実行する | 通った (台本のモデル) |
| 5 | 途中でプロセスが落ちても、同じストレージを開き直すと続きから終わる | 通った (台本のモデルと、本物の LLM の両方) |

確かめているのは実行基盤が動くこと。6〜9 が、本物の LLM に書かせたもの。

## 本物の LLM での結果 (Claude Sonnet 5.5)

`node run.ts llm` で、依頼 (予約まわりの 7 つの操作の HTTP API を作る。業務ルールは書き直さずにモデルを呼ぶ) を渡した。
モデルは `claude-sonnet-5-5` (thinking は adaptive、Pi の thinkingLevel は medium)。4 回動かした (A〜C と、下の D)。どれも、シェルを隔離し、完了の検査を付けている。

| | A: ふつうに作る | B: 途中で落として再開 | C: 検査で差し戻す |
| --- | --- | --- | --- |
| 依頼文 | `harness/task.md` (受け入れテストと検査のことを書いてある) | 受け入れテストに触れない依頼文 | B と同じ。受け入れテストのファイルも、最初は置かない |
| 経過 | 97 秒で完了 | 18 秒 (6 回めのツールの実行中) で強制終了 → 開き直して 90 秒で完了 | 81 秒で「できた」→ 検査が落ちる → 39 秒で直す |
| ツールの呼び出し | 10 回 | 6 回 + 5 回 | 15 回 |
| 費用 | 約 0.28 ドル | 約 0.30 ドル | 約 0.31 ドル |
| 完了の検査 | 1 回めで通る | 1 回めで通る | **1 回めは落ちる、2 回めで通る** |
| 受け入れテスト | 39 件 (37 ケース + 2) 通る | 39 件通る | 39 件通る |
| アプリのテスト | 31 件通る | 36 件通る | 46 件通る |
| 記録 | `results/sonnet-5-5-acceptance/` | `results/sonnet-5-5-resume/` | `results/sonnet-5-5-sent-back/` |

3 回とも、終わったあとに `node run.ts gate` で検査を流し直して、同じ件数が通ることを確かめた。A は、起動して HTTP で一通り
(予約の確定 → 早めのチェックインができない → 部屋の割り当て → チェックイン → 追加料金 → チェックアウト、状態違いの 409、無い予約の 404、入力の誤りの 400) も確かめた。

業務ルールの扱いは、依頼のとおりだった。操作の前提の状態・次の状態・条件のときの別の結果は、どれも WebAssembly のモデルに訊いていて、
アプリのコードは「状態が違う」と返ってきたら 409 にする、といった入出力と保存だけを持つ。

### C で起きたこと (「できた」は、やはり当てにならない)

C では、Sonnet は自分でテストを書いて実行し、「46 件すべて通った」と答えた。それ自体は本当だったが、外の検査では 2 つとも落ちた。

- 受け入れテスト: `acceptance/driver.ts` が無い (受け入れテストのことを知らされていない)
- アプリのテスト: `npm test` が 0 件 (テストを、土台の `package.json` が見る場所 (`app/test/`) と違うところに置いていた。**終了コードは 0**)

実行基盤が検査の結果を返すと、Sonnet は受け入れテストの説明を読んでドライバーを書き、テストとサーバーを決まった場所へ移して、2 回めの検査を通った。
B では、依頼文に書いていなくても、Sonnet が自分で `acceptance/` を見つけてドライバーを書いた。見つけてくれることもあるが、当てにはできない。

### D: untie が書き出した設計書で作る

A〜C の設計書 (`design/design.md`) は、この検証のためにその場で作ったもので、このシステムの操作しか載せていなかった。
そのため Sonnet は、分析には入っていること (条件を何で判断するか・予約を作るほかのシステムの操作・予約と部屋の結びつき) まで、毎回「設計の抜け」として挙げ、仮に決めて作っていた。
設計書の書き出しを本体の機能にして (`exportDesignBrief`。開発モードの「設計書を書き出す…」)、このシステムの外で作られる前提も載せるようにしてから、A と同じ依頼でもう一度動かした。

| | D |
| --- | --- |
| 経過 | 100 秒で完了。ツール 9 回、約 0.29 ドル |
| 完了の検査 | 1 回めで通る (受け入れテスト 39 件、アプリのテスト 33 件。外で流し直しても同じ) |
| 記録 | `results/sonnet-5-5-brief/` |

挙げられた「設計の抜け」は、次のように変わった。

| A〜C で挙げられたこと | D では |
| --- | --- |
| 条件を何で判断するかが無い | 判断のもと (説明と、見る状態・区分) は読めている。無いのは **式** だけ、という指摘になった |
| 予約を登録する操作・部屋を「準備完了」にする操作が無い | 挙がらなくなった (ほかのシステム・帳票の操作だと分かっている) |
| 予約と部屋の結びつきが無い | 結びつきは読めている。残ったのは「割り当てた部屋が無くても、チェックアウトできるのか」という、操作の細部 |
| (挙がっていなかった) | 金額の扱い (単位・上限・取消料の額の出どころ)、日付の前後の検査、部屋を割り当てるときに予約の状態を見るか |

つまり、設計書に載せるだけで消える抜けと、分析にまだ無いもの (条件の式・情報の項目・操作の細かい前提) が分かれた。後のほうが、次に untie の側で持たせるもの。

### 1 回め (2026-11-11 の午前。直す前の形) で見つかった設計の抜けと、その後

`results/sonnet-5-5/` は、書き出しを直す前のモデルで動かしたもの。そこで Sonnet が見つけた抜けを、untie の側で直してから、上の A〜C を動かした。

| 見つかったこと | 直したこと | A〜C での結果 |
| --- | --- | --- |
| 前提の状態を、モデルが断れない (どの状態を渡しても通る) | 操作は、今の状態を受け取り、前提でなければ「状態が違う」を返す | アプリは、モデルの答えを 409 にするだけになった |
| 条件のときの別の結果に、状態が無い (取消料のとき、取消になるのかが分からない) | 代替パターンに「そのあとの状態」を持たせた (形式 0.6.3) | 取消料が発生するとき、モデルが「取消」を返す |
| 状態を 1 つだけ返す操作は、結果が `{}` になる | 状態を、グループごとの和 (`予約の状態`) にした | `"確定"` と返る |
| 呼び出しコードを、アプリの中へ写す必要がある | 作業フォルダの土台に、依存を前もって入れる | `model/pms.ts` を、そのまま import できる |
| 「出来ました」は当てにならない | 完了の検査 (下) | C で実際に差し戻した |
| エージェントが作業フォルダの外に出る | シェルの隔離 (下) | `/tmp` への試し書きは今回もあったが、外に残らない |

## 完了の検査

エージェントが最後の答えを出すたびに (`hook(GenerationTask, { onYield })`)、実行基盤が次を行う (`harness/run.ts` の `runGate`)。

1. 書き換えさせないもの (`design/`・`model/`・`acceptance/` の、untie が書き出したファイル) を、元から置き直す。
2. 受け入れテスト (`node --test acceptance/run.test.ts`) と、アプリのテスト (`npm test`) を、隔離の中で流す。
3. どちらも「終了コードが 0・失敗が 0・**通ったテストが 1 件以上**」なら完了。そうでなければ、落ちたテストのまわりを添えて返し、続けさせる (3 回まで)。

判定は、エージェントの答えではなく、最後の検査の結果で決める (`*.gate.json` に残る)。

## シェルの隔離

`harness/sandbox-shell.sh` を、エージェントの bash の代わりに使う (`NodeExecutionEnv` の `shellPath`)。Linux の名前空間 (`unshare`) で、

- `/tmp`・`/home`・`/root`・`/mnt`・`/run` を空にして、作業フォルダだけを同じパスに戻す (この機械の設定・記録・資格情報は見えない)
- ほかのプロセスは見えない。環境変数は `PATH` など決まったものだけ
- ネットワークは無い (自分自身 (127.0.0.1) だけ。テストがサーバーを起こして呼べる)。依存は、作業フォルダに前もって入れておく
- 隠したものを、中から外せない (名前空間をもう 1 段重ねる)

read・write・edit のツールは、このシェルを通らない (実行基盤のプロセスで動く)。`run.ts` で、作業フォルダの外のパスと、リンクをたどると外に出るパスを断っている。
検証のためのもので、本番の隔離 (会話ごとのコンテナ) の代わりではない。Linux でしか動かない。

## 確かめていないこと

- Cloudflare の上で動かすこと (Durable Object に実行基盤、Containers に実行環境)。ここでは 1 つの Node のプロセスで動かした。
- 画面 (UI)・データベース。作ったのは、メモリに予約を持つ HTTP の API だけ。
- 条件の式・情報の項目・不変条件。Souther のモデルは、状態と、条件の真偽による分岐だけ (untie の今の書き出しの範囲)。
- ファイルを書いている途中で落ちたときの再開 (B で落としたのは、読むだけのコマンドの実行中)。
- 検査が上限 (3 回) まで落ち続けたときの扱い (起きなかった)。

## 分かったこと (直すとよいところ)

1. **結果の形が、操作によって違う。** 単位だけの和は文字列 (`"確定"`)、状態を持つ結果 (product) が 1 つでも混ざる和は、すべて `{ type: "取消" }` の形になる。
   A と B のアプリは、操作ごとに結果の形で分け、状態の名前を 1 か所だけ直に書いた (`"取消"`)。
   書き出しを、どの操作も同じ形 (結果の種類と、そのあとの状態) を返すようにそろえるとよい。
2. **日本語の識別子は、TypeScript の型の名前では `_` の並びになる。** `souther-wasm-bindings` は、ASCII でない文字を `_` に置き換えるので、
   `export type _____ = "仮予約" | "確定" | …` のような、読めない名前になる。A のアプリは、型を合わせられずに `as never` を 7 か所に書いた。
   実装から呼ぶモデルは、英語の名前で書き出すほうがよい (名前は AI が付け、日本語はコメントに残す)。
3. **ドライバーを実装する側が書くかぎり、受け入れテストは、アプリケーションを通らずに通せる。** 3 回とも、ドライバーは HTTP を通してアプリを動かしていた (読んで確かめた) が、
   仕組みでは保証できない。API の形 (経路と本文) を設計から決めて、受け入れテストが HTTP を直に叩く形にすると、ドライバーが要らなくなる。
4. **前の状態の用意のしかたが、実行ごとに違う。** 受け入れテストは「この状態のものに」から始まる。A は、状態を指定して予約・部屋を作る、確かめるための API (`/dev/…`) を足した
   (本番と同じサーバーに入る)。B と C は、予約を、ふだんの操作を順に行って目的の状態まで進めた (このほうが、アプリを確かめたことになる)。
   部屋は、「準備完了」にする操作が設計に無いので、3 回とも、登録するときに状態を指定する形になった。
   確かめるための入口を作ってよいか・本番でどう外すかを、決めておく必要がある。
5. **設計書に無いことは、作る側が「抜け」と見て、仮に決める。** A〜C で 3 回とも挙げられた抜け (条件を何で判断するか・予約と部屋の結びつき・最初の状態を作る操作) は、
   分析には入っていて、設計書に載せていなかっただけだった。設計書の書き出しを本体の機能にして、このシステムの外で作られる前提も載せた (D)。
   あわせて、「実装を始める準備」に、状態がどの情報のものか・2 つの情報の状態に関わる操作でその情報どうしが結ばれているか、の検査を足した。
   D で残った抜けは、分析にまだ無いもの: 条件の式、情報の項目 (金額・日付) とその検査、操作の細かい前提 (部屋を割り当てるときの予約の状態)。
6. **検査は、終了コードだけでは足りない。** C では、`npm test` が 0 件のまま終了コード 0 で終わった。「通ったテストが 1 件以上」まで見る必要がある。
7. **落ちたときの bash は、やり直されない。** 実行中だった bash は「中断された」という結果になり、モデルがもう一度呼ぶ。B でも、開き直したあとに、同じ内容を読み直すところから続いた。
8. **検査の回数は、いまはプロセスのメモリに持っている。** 落ちると数え直しになる。本番では、実行基盤のストレージに持つ (`api.memo`)。
9. **Pi Durable は AGENTS.md を読まない。** 実装するエージェントへの指示は、拡張の `section()` で渡す (`run.ts` の `untie-project`)。
10. **シェルに、親プロセスの環境変数がそのまま渡る。** `NodeExecutionEnv` の `shellEnv` は、親の環境変数に重ねるだけで、置き換えない。
    隔離のスクリプトの側で、決まったものだけにしている (中から、API キーが見えないことを確かめた)。
11. **エージェントは、作業フォルダの外に書こうとする。** 隔離していても、3 回のうち 3 回、`/tmp` に試し書きをしようとした (隔離の中の `/tmp` なので、外には残らない)。
    Pi Durable には権限の仕組みが無いので、隔離は必須。

## 動かし方

```sh
cd spikes/pi-durable-souther

# 1. 業務ルールを WebAssembly にする (JDK 25 と souther 0.4.1 が要る。済んだものを workspace/model に置いてあるので、飛ばしてもよい)
SOUTHER_BIN=/path/to/souther ./build-model.sh

# 2. Pi Durable で、アプリケーションを作る (台本のモデル。API キーは要らない)
cd harness && npm install
node run.ts full          # 最初から最後まで。workspace/app/ ができる
(cd ../workspace && npm test)

# 3. 途中で落ちても続きから終わるか
rm -rf ../workspace/app ../run.sqlite*
node run.ts crash         # テストの実行中に SIGKILL (終了コード 137)
node run.ts resume        # 同じストレージを開き直して、完了まで

# 4. 本物の LLM に書かせる (API の利用料がかかる。Linux だけ。作業フォルダは、リポジトリの外に写したものを使う)
W=/path/to/empty-dir
cp -r ../workspace/design ../workspace/model ../workspace/acceptance ../workspace/package.json ../workspace/package-lock.json $W/
(cd $W && npm ci)         # 依存は、前もって入れる (エージェントのシェルには、ネットワークが無い)
ANTHROPIC_API_KEY=... WORKSPACE=$W STORAGE=/path/to/run.sqlite node run.ts llm
#   CRASH_AFTER=6 … 6 回めのツールの実行中に強制終了する      RESUME=1 … 同じ STORAGE の続きから
#   TASK=/path/to/task.md … 依頼文を差し替える

# 5. 出来上がったものを、あとから外で検査し直す
WORKSPACE=$W node run.ts gate
```

## 中身

- `workspace/design/` … untie から書き出した設計の材料。`design.md` は「設計書を書き出す…」(`exportDesignBrief`)、`sys_pms.sou` は「書き出す…」(`exportSouther`) で書き出したもの
- `workspace/model/` … Souther のモデルを WebAssembly にしたものと、TypeScript の呼び出しコード (`build-model.sh` が作る)
- `workspace/acceptance/` … untie が設計から作った受け入れテスト (ケースの一覧・テストの本体・説明)。`driver.ts` は、実装する側が書く
- `workspace/package.json` … 作業フォルダの土台 (依存と、`npm test`・`npm start` の決まり)
- `harness/run.ts` … Pi Durable の実行基盤を開き、依頼を出して、完了を待つ。完了の検査も、ここにある。ストレージは SQLite、実行環境は Node
- `harness/sandbox-shell.sh` … エージェントのシェルの隔離
- `harness/script.ts` … 台本 (モデルの応答)。書くアプリケーションのコードも、ここにある
- `harness/task.md` … 本物の LLM に渡す依頼
- `results/sonnet-5-5-acceptance/` … A の結果 (アプリ `app/`、ドライバー、記録 `run.txt`、検査の結果 `gate.json`)
- `results/sonnet-5-5-resume/` … B の記録 (落とすまで・再開してから、依頼文)
- `results/sonnet-5-5-sent-back/` … C の結果 (アプリ、ドライバー、記録、検査の結果)
- `results/sonnet-5-5-brief/` … D の結果 (untie が書き出した設計書で作ったもの)
- `results/sonnet-5-5/` … 書き出しを直す前のモデルで動かしたときの結果
- `workspace/app/` … 台本で出来上がるアプリケーション (コミットしない)
