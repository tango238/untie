design/design.md は、宿泊施設の「宿泊管理システム」の設計です (業務分析ツール Untie から書き出したもの)。この設計から、予約まわりの操作の HTTP API を app/ に作ってください。

## 作るもの

設計の「操作」のうち、次の 7 つを HTTP で行える API:

- 予約を確定する
- 予約を変更する
- 予約を取り消す
- チェックインを記録する
- 部屋の割り当てを記録する
- 追加料金を登録する
- チェックアウトを記録する

確かめるのに要る最小限の操作 (予約や部屋を用意する・今の状態を見る) も足してください。

## 決まり

- TypeScript。Node 22 で、ビルドせずにそのまま動かす (`npm start` = `node app/src/server.ts`)。
- **ネットワークは使えません。** パッケージは、作業フォルダの node_modules に入れてあるもの (package.json のもの) と、Node の標準のものだけを使う。`npm install` はできない。
- **業務ルールを、アプリケーションのコードに書き直さない。** 操作の前提の状態・状態の移り変わり・条件のときの別の結果は、model/pms.wasm (design/sys_pms.sou を Souther でコンパイルしたもの) が答える。TypeScript から呼ぶコードは model/pms.ts にある (そのまま import できる。写さなくてよい)。使い方は、まずこの 2 つと node_modules の @souther-lang/wasm を読んで確かめること。
- データは、プロセスのメモリに持てばよい (データベースは要らない)。
- アプリのテストは app/test/ に `*.test.ts` で書き、作業フォルダで `npm test` で動くようにする。設計のシーケンス図の、ふだんの流れと、すべての分岐 (条件のときにどうなるか) を、HTTP を通して確かめる。前提の状態が違う操作・無い予約・入力の誤りも確かめる。
- 設計で決まっていないこと (条件を何で判断するか、など) は、勝手に決めずに、呼び出す側が渡す値にするか、app/README.md の「決まっていないこと」に書く。
- design/・model/ と、acceptance/ の `*.cases.json`・`run.test.ts`・`README.md` は、書き換えない (書き換えても、検査の前に元に戻されます)。

## 受け入れテスト

acceptance/ に、Untie が設計から作った受け入れテストがあります (acceptance/README.md を読むこと)。あなたが書くのは **acceptance/driver.ts** だけです。

- driver.ts は、**アプリケーションの HTTP API を通して** 操作を行う (アプリを起こして、HTTP で呼ぶ)。モデル (model/pms.ts) を driver.ts から直に呼んで答えを作らない。
- 操作のあとの状態は、アプリケーションに保存されているものを、HTTP で読み直して返す。
- ケースは、操作の前の状態 (states) を指定してきます。その状態のものを用意する手段を、API に足してよい (確かめるための操作であることが分かるようにする)。

## 完了の検査

あなたが「できた」と答えると、実行基盤が、あなたの外で次の 2 つを実行します。どちらかが落ちると、結果と一緒に戻ってきます。

```sh
node --test acceptance/run.test.ts
npm test
```

先に自分で実行して、すべて通ることを確かめてから答えてください。通っていないのに「できた」と言わない。

## 終わりに

app/README.md に、動かし方・テストの仕方・API の一覧・決まっていないことを書いてください。最後の答えには、作ったもの・テストの結果 (件数)・気づいた設計の抜けを、短くまとめてください。
