# 宿泊管理システム 予約まわりの API

## 動かし方
リポジトリの直下 (model/ と同じ場所) で:

    npm install                  # @souther-lang/wasm と @raoh/core だけ
    node app/src/server.ts       # PORT=3000 (環境変数 PORT で変更)。ビルド不要 (Node 22)

データはプロセスのメモリだけ。再起動で消える。

## テスト
    npm test                     # = node --test app/test/api.test.ts   (26 件)

## 業務ルールの扱い
状態の移り変わり・条件の分かれ目の答えは、すべて model/pms.wasm を呼んで得る。
アプリは (1) 「どの状態から始められるか」「結果がどの状態か」をモデルの宣言 (surface) から読み、
(2) 条件の真偽は呼び出し側から受け取ってモデルに渡し、(3) モデルの答えを保存するだけ。
モデルの入力型は状態ごとに値が 1 つしかなく、別の状態の値も受け付けてしまう (後述)。
そのため前提の状態の確認だけは、モデルが宣言した前提の型と現在の状態を突き合わせてアプリ側で行う (409)。

## API
JSON。成功は 200 (作成は 201)。
操作の応答: `{ outcome, changed, reservation, room? }`。`outcome` はモデルが答えた結果の名前、`changed` は状態を動かしたか。
エラー: 400 `invalid_input` / `invalid_json`、404 `reservation_not_found` / `room_not_found` / `not_found`、
409 `wrong_state` (`current`, `required` 付き) / `already_exists`。

| 操作 | メソッドと道 | 本文 |
|---|---|---|
| 予約を確定する | POST /reservations/:id/confirm | — |
| 予約を変更する | PUT /reservations/:id | `details` (オブジェクト) |
| 予約を取り消す | POST /reservations/:id/cancel | `cancellationFeeApplies` (真偽値) |
| チェックインを記録する | POST /reservations/:id/check-in | `earlyCheckInAllowed` (真偽値), `guest` (任意のオブジェクト) |
| 部屋の割り当てを記録する | POST /reservations/:id/room-assignment | `roomId`, `roomFull` (真偽値) |
| 追加料金を登録する | POST /reservations/:id/charges | `description`, `amount` (数) |
| チェックアウトを記録する | POST /reservations/:id/check-out | — |
| (用意) 予約を作る (仮予約) | POST /reservations | `guestName`, `details`? |
| (用意) 部屋を作る | POST /rooms | `status` (清掃待ち/清掃中/準備完了/使用中), `id`? |
| (参照) | GET /reservations, GET /reservations/:id, GET /rooms/:id | — |

条件 (取消料・早めのチェックイン・満室) は、何で判断するかが設計に無いので、呼び出し側が真偽値で渡す。

## 決まっていないこと
- **条件の判断のしかた**: 取消料が発生するか / 早めのチェックインができるか / 満室か。上記のとおり呼び出し側が渡す。
- **取消料が発生するとき**: モデルは `取消` ではなく分岐の名前 `予約を取り消す_取消料が発生する` を答える。設計の文は
  「取消料を請求に加えてから取り消す」だが、金額も請求の持ち方も無い。アプリは何も変えず (予約は確定のまま、`changed:false`) 分岐名を返す。
- **早めのチェックインができないとき / 満室のとき**: 同じく状態を変えず分岐名を返す (宿泊客も保存しない)。
- **予約の変更内容**: 何を変えられるかが無いので、`details` を任意のオブジェクトとして置き換えるだけ。
- **追加料金**: 金額の単位・負の値 (値引き) ・上限・請求との結び付け (請求という情報の中身) が無い。有限の数なら受け付け、予約に積む。
- **宿泊客**: 項目が無いので、任意のオブジェクトを保存するだけ。
- **部屋の割り当て**: モデルは部屋の状態しか見ない。予約がチェックイン済であること、予約に既に部屋があるとき (上書きする) 、部屋のタイプや日付の一致は決まっていない。
- **チェックアウト**: 予約に部屋が割り当てられていなければ、部屋は動かさず予約だけ進める。部屋が使用中かは確かめない (モデルは確かめない)。
- 請求・料金プラン・請求金額の計算・請求書・決済・売上は対象外 (設計の「実装を始める準備」にもあるとおり、料金プランの出どころなどが未決)。

## 気づいた設計の抜け
- モデルの入力は「前の状態」の型だが、型の値が 1 つしかないので別の状態も通る。前提の状態違反をモデルは弾けない。
  (状態の列挙 `予約の状態` を入力にして `guard` する形なら、モデルが答えられる。)
- 予約を確定する・変更する・追加料金・チェックアウトに分岐が無く、取消料などの金額や請求への反映を表す値が出てこない。
- 追加料金を登録する の結果は「完了」で、状態が `チェックイン済 → —` のまま。
