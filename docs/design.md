# Untie PoC 設計書

Untie は、現場担当者が自分の業務を言語化するための業務可視化ツールである。人・作業・情報・ルール・判断をカードにし、図の上で関係を整理する。将来は RDRA モデルに展開して要件定義につなげる。

この PoC では「カードと図で業務要素と関係を編集する体験」を確かめる。モデルは JSON ファイルに保存・読み込みできる。AI エージェント (会話でモデルを直す・初期要望からモデルを作る) を持つ (6.2)。RDRA 出力は対象外だが、データモデルはそれに耐える形にしておく。

その後、ログインしたユーザーがクラウドにファイルを置き、共有し、同時に編集できるようにした。クラウド版 (ユーザー・ファイル管理・権限・ログイン・同時編集・サーバー・モノレポ構成) の設計は [docs/collab-design.md](collab-design.md) にあり、この文書には要点と参照だけを書く。この文書の 2〜4 章 (要素・関係・データモデル) と 6〜7 章 (操作・サンプル) は、ローカルファイルでもクラウドファイルでも同じである。

## 2. 要素 (カード) の種類

17 種。イベント・画面・非機能要件はモデルの形式 0.2.0 で足した (2.4)。イベントストーミングのポリシー・集約は、分析の要素としては持たない (分析は RDRA のままにする)。集約・コマンド・ポリシーなどの DDD の判断は、分析とは別の入れ物のドメインモデル (`domain`。4.6) に持つ。メモカードは入れず、各要素の説明欄で代用する。

| kind | 表示名 | 役割 | 種類固有の項目 |
| --- | --- | --- | --- |
| `actor` | アクター | 業務を行う社内の人・役割 | なし |
| `externalActor` | 外部アクター | 顧客・取引先など、社外の人や組織 | なし |
| `system` | システム | 情報システム (自社・社外を問わない)。操作の対象・イベントの発生元になり、画面と非機能要件を持てる。作業の担当にはならない (0.2.0 から)。情報の置き場所 (取得元・保存先) は、対象にした操作が扱う情報から導く (0.4.0 から) | なし |
| `ledger` | 帳票 | 紙の台帳・伝票。操作の対象になる。情報の置き場所 (取得元・保存先) は、対象にした操作が扱う情報から導く (0.4.0 から) | なし |
| `business` | 業務 | 業務のまとまり。ボード上では枠 (グループノード) | なし |
| `buc` | 活動 (BUC) | 業務の中の作業のまとまり (Business Use Case)。任意 | `businessId`、`isDefault` |
| `activity` | 作業 (アクティビティ) | 業務の中の個々の作業 | `bucId` (null 可)、`links` (リンク、任意)、`hours` (時間、任意)、`triggerNote` (起点のうち作業・イベント以外の 1 行、任意。空文字は持たない。0.4.1) |
| `usecase` | 操作 (ユースケース) | システムに期待する振る舞い | `links` (リンク、任意)、`hours` (時間、任意) |
| `context` | コンテキスト | 役割の同じ情報と、関係の深い状態・条件・バリエーションをまとめる親カテゴリ。関係は持たない | なし |
| `information` | 情報 | 業務で扱う情報 | `contextId` (null 可) |
| `state` | 状態 | 情報やモノの状態 | `group` (状態グループ、任意)、`contextId` (null 可) |
| `variation` | バリエーション | 種別・区分と、その値の一覧 | `values: string[]`、`contextId` (null 可) |
| `condition` | 条件 | 判断の条件・ルール | `contextId` (null 可) |
| `issue` | 課題 | 現場で困っていること。自由ボードには置かない | `severity` (1〜5)、`targetIds`、`analysis` (分析、任意) |
| `event` | イベント | 操作の実行やシステムが発生させる出来事 (人の動きは含めない)。操作のきっかけになる | `contextId` (null 可)、`timing` (発生タイミング、任意。0.5.4) |
| `screen` | 画面 | システムの画面。操作が使う。扱う情報は、使う操作が扱う情報から導く (0.4.0 から) | `systemId` (必須。システムだけ) |
| `nfr` | 非機能要件 | システムに求める、機能以外の品質 | `systemId` (必須。システムだけ)、`category` (IPA の 6 分類、任意)、`verification` (検証方法、任意) |

画面の表示名は RDRA の用語と変えている: `buc` は「活動」、`activity` は「作業」、`usecase` は「操作」と出す (現場担当者に通じる言葉にするため)。この設計書とコード・スキーマは RDRA の用語 (BUC・アクティビティ・ユースケース) のまま書く。

全要素に共通: `id` (安定した文字列)、`kind`、`name`、`description` (任意の説明文)。

### 2.1 業務 ⊃ BUC ⊃ アクティビティ

- 業務・BUC・アクティビティ・ユースケースの 4 段をモデルに持つ。BUC は任意。
- 業務を作ると、その業務の **既定 BUC** (`isDefault: true`、名前は業務名と同じ) が自動で 1 つ作られる。既定 BUC はボードにも要素一覧にも出さない。
- アクティビティは `bucId` で BUC を 1 つ指す。業務の枠に直接置いたアクティビティは、その業務の既定 BUC に入る。
- 業務ごとに、作業は「すべて業務に直接 (既定 BUC)」か「すべてどれかの活動 (既定でない BUC)」のどちらかにする (混ぜない)。業務に初めて活動を作ると (活動の固定ボードの「＋活動」)、業務に直接あった作業はその活動へ移る (作成と移動で 1 件の履歴)。プロパティ欄の活動のセレクトは、活動のある業務では「(業務に直接)」を出さない。スキーマとコマンドは混ざったデータも受け付ける (古いファイルや AI の作成のため) が、作業のボードで知らせる。
- BUC を作りたい人は、業務の枠の中に BUC の小枠を作り、アクティビティをそこへドラッグして移す。
- `bucId` が null のアクティビティ (未所属) も許す。現場担当者が業務を決める前に作業を書き出せるようにするため。rdra 出力では未所属を出せないので、出力時に警告する (将来の TODO)。
- 既定 BUC は削除できない。既定でない BUC を削除すると、所属アクティビティは業務の既定 BUC に戻る。業務を削除すると、その BUC は全て消え、所属アクティビティは未所属になる。

### 2.2 担い手と置き場所 (システム・帳票) とコンテキスト

役割で 2 つに分け、種類をこれに合わせる。

| | 作業をする (担い手) | 操作の対象 | 情報を取り出す・残す (置き場所。操作の対象から導く) | イベントを発生させる・画面と非機能要件を持つ |
| --- | --- | --- | --- | --- |
| アクター | ○ | – | – | – |
| 外部アクター | ○ | – | – | – |
| システム | – | ○ | ○ | ○ |
| 帳票 | – | ○ | ○ | – |

- システムは情報システム。自社のものも社外のもの (予約サイト・決済サービスなど) も含む。0.2.0 から作業の担当にはならず、操作の対象 (`usecaseSystem`) として結ぶ。人が担当しない自動の処理は作業にせず、イベントをきっかけにした操作で表す (2.4)。0.1.0 のファイルの「システム → 作業 (担当)」は、開くときにその作業が使う各操作の「対象」へ変換する (システムだけが担当だった作業は担当が空になり、検証で知らせる)。
- 帳票は紙の台帳・伝票。操作の対象と置き場所になる (画面では破線で描く)。紙はイベントも画面も持たないので、システムとは別の種類にした。関係のルールは種類だけで決まる。
- 外部アクターとシステムの線引きは「人か仕組みか」の 1 本にする。社外の人・組織は外部アクター、仕組みは自社・社外を問わずシステム。予約サイトのように両方に読めるものは、契約や電話でやり取りする相手なら外部アクター、データをやり取りする仕組みならシステムとする。自社か社外かの印は持たない (RDRA のシステム境界を描くときに要れば足す)。
- **置き場所は関係にせず、操作から導く** (0.4.0 から。`packages/core/src/model/placement.ts`)。情報の置き場所 (取得元・保存先のシステム・帳票) は、その情報を扱う操作 (`usecaseInformation`) の対象 (`usecaseSystem`。画面 `usecaseScreen` ならその画面のシステム) から決まる。取得・保存の区別は `usecaseInformation` の `access` で持つ: `read` は取得だけ、`write` は保存だけ、省略は取得も保存もする。取得元 = `read` か省略の操作の対象、保存先 = `write` か省略の操作の対象。同じ事実を操作・画面・システムの 3 か所で入力させず、ずれも起きないようにするため。どの操作にも扱われない情報は置き場所を持てない (検証 5.6 でも情報は置き場所からは辿らないので、方針は揃う)。プロパティ欄では、情報に「置き場所」、システム・帳票に「ここにある情報」、画面に「扱う情報」を導いた一覧として出し (根拠の操作も添える)、変えるには操作のプロパティ欄で扱う情報・取得・保存・対象を直す。0.3.0 までの `systemInformation` (取得元)・`informationSystem` (保存先)・`screenInformation` (画面が扱う情報) は、開くときに `access` へ変換して外す (4 章)。
- コンテキストは RDRA のコンテキストに合わせる。中心は情報で、役割の同じ情報と、それに関係の深い状態・条件・バリエーションをまとめる。この 4 種類は `contextId` で 1 つを指す (null は未分類)。状態は状態グループごとに属する (グループ内の状態はまとめて移し、既にあるグループに足した状態はそのグループのコンテキストになる)。
- 所属は人が決める。条件やバリエーションは複数のコンテキストにまたがりやすく、どこに入れるかは設計上の判断だから。代わりに、つながりから候補を出す (`packages/core/src/model/contexts.ts`)。直接つながる所属要素 (関連する情報、参照する状態・バリエーションなど) は重み 2、操作を介してつながる情報は重み 1 で数え、いちばん重いコンテキストを候補にする。
- コンテキスト自体はほかの要素と関係を持たない。コンテキストどうしの関係 (結合度) は、所属する要素の関係から導く。コンテキストを削除すると、所属していた要素は未分類になる。

### 2.3 課題

- 独立した要素で、`targetIds` に対象の id を複数持てる (0 件も可)。課題を先に書き出し、あとから対象を付けて紐解けるよう、対象なしで作れる。
- 対象の種類で 2 つの区分に分かれる。区分は保存せず、対象から決める (`issueScope`)。
  - **全体的な課題**: 登場人物 (アクター・外部アクター・システム・帳票) が対象。その登場人物全体にかかわる課題。
  - **具体的な課題**: 業務・作業・操作・画面が対象。特定の業務や操作で起きている課題。
  - 対象がまだ無い課題は **未整理** とする。
- 1 つの課題の対象に、登場人物と業務・作業・操作・画面を混ぜない (コマンドで拒否し、検証でエラーにする)。区分を変えるときは、いまの対象を外してから別の区分の対象を付ける。
- `severity` は 1 (低) 〜 5 (高) の整数。
- `analysis` (任意) は深掘りの結果。現象 (`phenomenon`)・所在 (`location`)・理由 (`cause`)・影響 (`impact`) の 4 項目で、すべて任意の文字列。担当者が書いた `description` (原文) は分析で上書きせず、突き止めた内容をここに分けて持つ。AI との深掘り (6.3) で埋まるが、プロパティ欄で手でも書ける。項目ごとに変えられ、空文字で項目が消え、全部消えれば `analysis` 自体が消える。
- ボードには置かない。課題一覧パネル (5.5) で作り、区分ごとに見る。対象カードにはバッジ (件数と最高重要度) を出す。
- 対象要素を削除すると、その id は `targetIds` から外れる。課題自体は残る。

### 2.4 イベント・画面・非機能要件 (0.2.0)

- **イベント**: 操作の実行 (`usecaseEvent`) やシステム (`systemEvent`) が発生させる出来事で、操作のきっかけ (`eventUsecase`) になる。人の動き (「お客様が電話した」など) は含めない。名前は「予約が確定した」のような過去の形で書く。コンテキストに任意で属する。
- **作業の起点** (0.4.1): 作業が何をきっかけに始まるかを持つ。起点は 3 種類で、1 つの作業に複数あってよい。別の作業 (`activityTrigger`)、イベント (`eventActivity`)、その他の 1 行 (作業の `triggerNote`。例: 電話)。起点が無い作業は警告にせず、起点の循環もエラーにしない (業務では起こりうる)。担い手へのトレース・レイヤーの上下には使わない。既存の操作の「きっかけ」(`eventUsecase`) と「次に」(`usecaseNext`) はそのまま残る。作業ボードで作業を選ぶと、プロパティ欄の「起点」の節で足す・外し、「起点 (その他)」を書く (5.4。どちらも固定ボードだけ)。作業ボードのカードには「起点: 受注の確認 / 入荷が登録された (イベント) / 電話」と要約を出す (4.2)。後の設計モードで、作業のつながりから画面遷移を導くための材料になる。
- **操作の順番**: 作業の中の操作は「次に」(`usecaseNext`) でつなぐ。枝分かれ・合流・輪を許し、自分自身へは結べない。順番は作業ではなく操作どうしの関係で持つので、同じ操作を使う作業が複数あっても、作業の中の並びはその作業が使う操作どうしの「次に」だけで組み立てる。
- **操作の対象は 1 つだけ** (0.3.0): 1 つの操作が持てるのは、対象 (システム・帳票。`usecaseSystem`) か画面 (`usecaseScreen`) のどちらか 1 本まで (0 本も可)。コマンドは 2 本目を「操作の対象は 1 つだけです。今の対象を外してから結んでください」と断り、検証は 2 本以上をエラーにする。プロパティ欄では「対象」の選択欄 (システム・帳票・画面) で選び、選ぶと前の対象と入れ替わる (`setUsecaseTarget`)。0.2.0 のファイルで 2 本以上あるものは、開くときに画面を優先し、同じ種類では先にあるものを残して、外した本数を知らせる。同時編集で 2 本になったときは、サーバーの修復 (`repairModel`) が同じ規則で 1 本にする。
- **自動の処理**: 人が担当しない処理は作業にせず、「イベント → 操作 (対象: システム) → …」で表す。きっかけのイベントから辿れれば、作業に属さなくてよい。
- **画面**: 1 つのシステムに属する (`systemId`)。操作が使う (`usecaseScreen`)。画面を結んだ操作は、その画面のシステムを対象とみなす。画面を使う操作は 1 つだけで、入力の時点で断る (`addRelation`・`setUsecaseTarget` は別の操作が使う画面を「画面「○○」は操作「△△」が使っています。先にその操作の対象を外してください」と断る)。画面側からは `setScreenUsecase` で使う操作を入れ替える (今の操作の対象を外し、新しい操作の前の対象を画面に置き換える。1 回の履歴)。検証 (`screenSharedByUsecases`) は、古いファイルや同時編集で重なったときのために残す。画面が扱う情報は関係にせず、その画面を使う操作が扱う情報から導く (0.4.0 から。2.2)。システムを消すと、属する画面も消える。帳票は画面を持たない。
- **非機能要件**: 1 つのシステムに属する (`systemId`)。名前・分類 (IPA 非機能要求グレードの大項目: 可用性・性能・拡張性・運用・保守性・移行性・セキュリティ・システム環境・エコロジー。任意)・説明・検証方法 (任意) を持つ。求める人 (アクター・外部アクター) は `actorNfr` で結ぶ。システムを消すと一緒に消える。
- **ペルソナ** (0.5.3): アクター・外部アクターに任意で持てる人物像 (`persona`)。AI のヒアリング (6.4) で、この人になりきって答える材料になる。項目はすべて任意で、全部空なら `persona` ごと持たない (コマンド `setPersona` と `repairModel` で正規化する)。
  - `handle` 呼び名 (例「田中さん (店長・45歳)」。名前と同じ 200 文字まで)、`attributes` 属性 (年代・経験年数・勤務形態などを 1 行。200 文字まで)、`background` 背景と役割 (何を任され、何を気にしているか。4000 文字まで)、`goals` 目標 (この人が達成したいこと。4000 文字まで)、`itSkill` IT の習熟 (`comfortable` 慣れている / `normal` 普通 / `uncomfortable` 苦手)、`notes` 備考 (4000 文字まで)。
  - コマンド `setPersona` で置き換える (null か全項目が空で消す。同じなら変えない)。長すぎる文字列は `truncateModelStrings` が切り詰める。`repairModel` は列挙に無い `itSkill` を「…のペルソナの IT の習熟を外した (値が正しくない)」と知らせて外し (要素は外さない)、全項目が空 (`{}` を含む) なら知らせなしで `persona` ごと消す。Y.Doc の読み (`readModel` / `readElements` の形の検査) は、画面の `shell` と同じく不正な `itSkill` を落としてから扱う (`dropBadPersonaSkill`)。Y.Doc では要素の項目として値ごと運ぶ (同時に別の項目を書くと後勝ち)。

- **イベントの発生タイミング** (0.5.4): イベントに任意で持てる、いつ起きるか (`timing`)。種類 (`type`) は 2 つ。
  - `scheduled` 定期: 決まった周期で繰り返すバッチ処理。周期 `every` (`month` 毎月 / `day` 毎日 / `hour` 毎時) と、周期に合う時刻 (`day` 毎月の何日 1〜31・`hour` 何時 0〜23 は毎月と毎日・`minute` 何分 0〜59)。決めていない時刻は持たない。
  - `adhoc` 不定期 (随時): Webhook などから API が呼ばれたときのような、決まった時刻の無い処理。周期と時刻は持たない。
  - どちらも `note` 補足 (4000 文字まで) を持てる。定期なら「営業日だけ」など、不定期ならいつ起きるか (例「決済サービスから入金の Webhook を受けたとき」)。
  - コマンド `setEventTiming` で置き換える (null で消す。同じなら変えない)。`normalizeEventTiming` で正規化し、周期に合わない項目は持たない (周期を変えると外れる。周期が無い定期は毎日)。種類・周期が列挙の外、日・時・分が範囲外の整数でなければ失敗。表記は `describeEventTiming` (「定期: 毎月 25日 9:00」「定期: 毎時 15分」「不定期: Webhook を受けたとき」。決めていない時刻は `--`)。`repairModel` は、種類の分からないタイミングを「…の発生タイミングを外した (種類が正しくない)」と知らせて外し、周期に合わない・範囲外の項目は外して知らせる (要素は外さない)。長すぎる補足は `truncateModelStrings` が切り詰める。Y.Doc の読みは、壊れたタイミングのせいでイベントが消えないよう、正規化してから形を検査する (`fixEventTiming`)。

## 3. 関係 (線) の種類

関係は RDRA に沿った型付きのみ。両端の要素の種類から関係の種類が自動で決まり、表にない組み合わせは引けない。自由な線はない。

| relation kind | 始点 → 終点 | 意味 (RDRA での対応) |
| --- | --- | --- |
| `actorBusiness` | アクター → 業務 | 業務の主担当 (`business.main_actor`) |
| `actorActivity` | アクター / 外部アクター → アクティビティ | 作業を行う担い手 (`activity.used_by`)。0.2.0 からシステムは担当にならない |
| `activityUsecase` | アクティビティ → ユースケース | 作業で使うユースケース (`activity.usecase`) |
| `usecaseInformation` | ユースケース → 情報 | 扱う情報 (`usecase.information`)。`access` (任意) で取得・保存を区別する (0.4.0): `read` 取得だけ、`write` 保存だけ、省略は両方。情報の置き場所はこれと操作の対象から導く (2.2) |
| `usecaseCondition` | ユースケース → 条件 | 判断に使う条件 (`usecase.condition`)。任意の `alternate` (代替パターン。0.6.1): 条件を満たすとき (`when: "met"`) か満たさないとき (`"unmet"`) に、ふだんと違う流れになる。`then` はどうなるか、`eventId` はそのとき起きる出来事 (任意)。省略は未定 (5.7 のシーケンス図で決める) |
| `informationRelated` | 情報 ↔ 情報 | 関連する情報 (`information.related`)。無向 |
| `informationVariation` | 情報 → バリエーション | 情報の種別 (`information.variation`) |
| `conditionVariation` | 条件 → バリエーション | 条件が参照する種別 (`condition.variation`) |
| `conditionState` | 条件 → 状態 | 条件が参照する状態 (`condition.state`) |
| `stateUsecase` | 状態 → ユースケース | この状態で実行できるユースケース |
| `usecaseState` | ユースケース → 状態 | 実行後に遷移する次の状態 (`next_state`) |
| `usecaseSystem` | ユースケース → システム / 帳票 | 操作の対象 (0.2.0)。`usecaseScreen` と合わせて 1 つの操作に 1 本まで (0.3.0) |
| `usecaseEvent` | ユースケース → イベント | 操作を実行すると発生するイベント (0.2.0) |
| `systemEvent` | システム → イベント | システムが発生させるイベント (0.2.0) |
| `eventUsecase` | イベント → ユースケース | 操作のきっかけ (0.2.0) |
| `usecaseNext` | ユースケース → ユースケース | 作業の中の次の操作 (0.2.0)。自分自身へは不可 |
| `activityTrigger` | アクティビティ → アクティビティ | 作業の起点となる作業 (0.4.1)。始点が起点、終点が起点を持つ作業。ラベルは「起点」。自分自身へは不可。循環は許す |
| `eventActivity` | イベント → アクティビティ | 作業の起点となるイベント (0.4.1)。ラベルは「起点」 |
| `usecaseScreen` | ユースケース → 画面 | 操作で使う画面 (0.2.0)。`usecaseSystem` と合わせて 1 つの操作に 1 本まで (0.3.0) |
| `actorNfr` | アクター / 外部アクター → 非機能要件 | その要件を求める人 (0.2.0) |

ルール:

- 関係は `id`、`kind`、`sourceId`、`targetId` を持つ。`kind` は両端の種類から一意に決まり、保存時も冗長に持つ (スキーマ検証とエクスポートを単純にするため)。`access` は `usecaseInformation` だけが持て、ほかの種類に付いていれば検証はエラーにし、修復 (`repairModel`) は外す。
- 0.3.0 まであった `systemInformation`・`informationSystem`・`screenInformation` は 0.4.0 で無くし、操作から導く (2.2)。
- 同じ `(kind, sourceId, targetId)` の関係は 1 本まで。`informationRelated` は無向なので `(a, b)` と `(b, a)` を同一とみなし、重複を拒否する。
- 自己参照 (`sourceId === targetId`) は不可。
- 線はボードごとではなくモデル全体の関係である。両端がボードに置かれていれば、どのボードでも同じ線が表示される。
- 画面では、`informationRelated` は矢印なし、それ以外は終点に矢印。線の上に関係名の短いラベルを出す (例: 「担当」「使う」「次の状態」)。
- 状態遷移は `stateUsecase` と `usecaseState` の 2 本で表す。1 つのユースケースに前の状態と次の状態がそれぞれ複数ある場合、組み合わせが曖昧になる。rdra 出力の TODO で、3 項関係 (前状態・ユースケース・次状態) への拡張か、全組み合わせとして出力するかを決める。

### 3.1 関係の自動判定

`relationKindFor(sourceKind, targetKind)` が上の表を引き、該当なしなら `null` を返す。React Flow の `isValidConnection` でこの判定を使い、引けない組み合わせはドラッグ中に接続不可として扱う。接続時にすでに同じ関係があればトーストで知らせて何もしない。

## 4. データモデル

スキーマは `schema/untie.schema.json` (JSON Schema 2020-12) に定義し、`json-schema-to-typescript` で `packages/core/src/model/schema.d.ts` を生成する。型とスキーマがずれないよう、CI で生成結果の差分を検査する (json-gantt と同じ方式)。

```
UntieModel
├ version: "0.6.1"           … モデルの形式 (スキーマ) のバージョン。semver の文字列
├ meta: { name, description? }
├ elements: Element[]      … 17 種を kind で判別する
├ relations: Relation[]    … 型付きの関係 { id, kind, sourceId, targetId, access? }
├ boards: Board[]
│  └ nodes: BoardNode[]    … { elementId, x, y, width?, height? }
├ designs: SystemDesign[]  … システムごとの設計 (設計モード。0.5.0)。systemId は一意
├ databases: Database[]    … 設計をまたいで共有するデータベース (0.5.0)。id は一意
└ domain: DomainModel      … ドメインモデル (DDD の判断。0.6.0。4.6)。モデルに 1 つ
```

設計方針:

- **形式のバージョンとマイグレーション**: JSON の `version` にモデルの形式のバージョン (semver。現行は `0.6.1` で、`MODEL_VERSION`) を持つ。変換は 0.1.0 → 0.2.0 (システムの作業の担当を操作の対象へ移す。2.2)、0.2.0 → 0.3.0 (操作の対象を 1 つにする。2.4)、0.3.0 → 0.4.0 (置き場所と画面の情報の関係を外し、取得・保存の区別を `usecaseInformation` の `access` に移す。操作 → 情報ごとに、その操作の対象に旧データで取得元だけがあれば `read`、保存先だけなら `write`、両方かどちらも無ければ省略。扱う操作の対象になっていない置き場所は導けず消えるので、件数を知らせる。2.2)、0.4.0 → 0.4.1 (作業の起点を足す。足すだけなので変換は空)、0.4.1 → 0.5.0 (設計モードの入れ物 `designs`・`databases` を空配列で足す)、0.5.0 → 0.5.1 (画面ごとのレイアウトの上書き `DesignScreen.shell` を足す。足すだけなので変換は空)、0.5.1 → 0.5.2 (組み込みの画面にホーム `home` を足す。列挙に値を足すだけなので変換は空)、0.5.2 → 0.5.3 (アクター・外部アクターに任意のペルソナ `persona` を足す。足すだけなので変換は空)、0.5.3 → 0.5.4 (イベントに任意の発生タイミング `timing` を足す。足すだけなので変換は空)、0.5.4 → 0.6.0 (ドメインモデルの入れ物 `domain` を空で足す。必須のトップレベルの項目なので minor を上げる。4.6)、0.6.0 → 0.6.1 (操作が判断する条件の関係に、任意の代替パターン `alternate` を足す。足すだけなので変換は空) の 11 個。版の来歴は、0.4.0 = 情報の置き場所の導出、0.4.1 = 作業の起点、0.5.0 = 設計データ、0.5.1 = 画面ごとのレイアウト、0.5.2 = 組み込みの画面ホーム、0.5.3 = ペルソナ、0.5.4 = イベントの発生タイミング、0.6.0 = ドメインモデル、0.6.1 = 代替パターン。変換で中身を外したときは、開いたときの知らせに出す。スキーマを変えるときは必ずバージョンを上げ、前の版から変換するマイグレーションを `packages/core/src/model/migrate.ts` の `MIGRATIONS` に足す (手順は AGENTS.md)。ファイルを開く・取り込むときは `loadModelJson()` が、古い版の JSON を順に変換して現行の版にしてから検証する。新しい版の JSON (新しいアプリで作られたもの) は、古いアプリで開いて壊さないよう「Untie を更新してください」と断る。0.1.0 より前のファイルは `version` が整数の `1` で、中身は 0.1.0 と同じなので `"0.1.0"` に読み替える。
- **安定 id**: 要素・関係・ボードは作成時に `kind の短い接頭辞 + ランダム文字列` の id を得る (例 `act_k3f9x2ab`)。名前を変えても id は変わらない。参照は全て id で行う。
- **座標の分離**: 要素は業務データ (`elements`) に、座標はボード (`boards[].nodes`) に持つ。1 モデルに複数ボード、同じ要素を複数ボードに置け、座標はボードごと。
- **座標はボード内の絶対座標**で持つ。React Flow は親ノードの子に相対座標を要求するので、ボードを描画するときに親 (業務・BUC の枠) の座標を引いて相対にし、ドラッグ終了時に足し戻す。親の有無でモデルの座標の意味が変わらないようにするため。
- 業務・BUC の枠は `width`・`height` を持つ。それ以外のカードは省略し、表示側の既定サイズを使う。
- 課題はボードに置けない。既定 BUC もボードに置けない (業務の枠の中に直接アクティビティを置く)。
- 参照整合性 (存在しない id を指さない、`bucId` の BUC・`contextId` のコンテキストが存在する、`targetIds` が 業務/アクティビティ/ユースケース を指す、など) は JSON Schema では表現できないので、`validateModel()` でスキーマ検証に続けて検査する。

### 4.0 設計データ (`designs`・`databases`。0.5.0)

設計モード (5.7) が使う入れ物。モデルのトップレベルに必須 (空配列可) で持つ。形は 0.5.0 で定め (画面ごとのレイアウトの上書き `DesignScreen.shell` は 0.5.1、組み込みの画面ホームは 0.5.2 で足した)、中身を編集する画面は段階的に作る (サイトマップの `screens`・`transitions` は 5.7 のサイトマップで、`databases` と `databaseIds` は 5.7 のデータで、`layout` は 5.7 のナビゲーションで、`view`・`bindings` は 5.7 の画面で編集できる)。

```
SystemDesign                 … システムごとの設計。systemId は一意
├ systemId: string           … elements の system の id
├ databaseIds: string[]      … 使うデータベース (databases の id)。空なら既定のデータベース
├ screens: DesignScreen[]    … サイトマップの画面
├ transitions: Transition[]  … 画面遷移
└ layout: Layout

DesignScreen
├ id: string                 … 一意 (例 "ds_...")
├ source: { kind: "screen", screenId }          … 分析の画面 (同じシステムの screen) への参照
│       | { kind: "builtin", builtin: "signIn" | "top" | "home" | "signUp" | "passwordReminder" }  … 組み立て済みの画面 (top = 未ログインの最初の画面、home = サインインした人の最初の画面。home は 0.5.2 から)
├ shell?: "shell" | "plain"  … この画面のレイアウト (枠)。省略 = 設計のレイアウト (Layout.shell) に従う (0.5.1 から)
├ view?: object              … 画面 UI (mokkun v2 の ViewV2 を JSON で持つ。中身は検証しない)
└ bindings?: { item, databaseId, table, column }[]  … 画面の項目 → テーブルの列

Transition                   … id、from / to (DesignScreen.id)、via? ("button" | "row" | "nav" | "afterSubmit"。省略 = 未定)、label?
                               via は遷移のきっかけ: button = 画面のボタン・リンク、row = 一覧の行を選ぶ、nav = メニュー (ナビゲーション)、
                               afterSubmit = 入力を送信したあと。label は、そのボタンやリンクの文言
Layout                       … shell ("shell" | "plain")、header? { systemName?, userName?, tenantName? }、
                               navigation: NavGroup[]
NavGroup                     … id (ナビゲーションのグループの id)、group (名前)、items: { screenId (DesignScreen.id), label? }[]
Database                     … id、name、dsl (Prisma のスキーマ言語の一部。5.7 のデータで解析する。200000 文字まで)、
                               tables: { table, informationIds[] }[] (テーブル → 表す情報。1 つの情報に複数のテーブルがあってよい)
```

- **参照整合性** (`validateModel`): `designs[].systemId` が system を指す・同じ `systemId` は 1 つだけ・`databaseIds` と `bindings[].databaseId` が `databases` を指す・`source.screenId` が**同じシステムの** screen を指す・遷移の `from` / `to` とナビゲーションの `screenId` が同じ設計の `screens` を指す・`tables[].informationIds` が information を指す・データベースの id が重複しない・画面 (`DesignScreen.id`)・遷移・ナビゲーションのグループの id は**設計をまたいで**一意 (同時編集で 1 つの Y.Map に置くため)。メッセージにはシステム名を添える。
- **サイトマップのコマンド** (commands.ts。引数は他のコマンドと同じ payload): `addDesignScreens` (画面と遷移を足す。設計が無ければ `ensureDesign` で作る。画面の id は `ds_` + ランダム文字列、遷移の id は `tr_` + ランダム文字列で、どちらも id を渡せば使う。同じ分析の画面・同じ組み込みの画面を 2 つ足せず、分析の画面は同じシステムのものだけ)、`addTransition` (同じく設計が無ければ作る)。`removeDesignScreensById` (画面を外す。それを指す遷移・ナビの項目も `removeDesignScreens` で外す)・`updateTransition` (`via`・`label` だけ。`via: null`・空の `label` で消す)・`removeTransition` は設計を作らず、設計が無ければ失敗にする。`addDesignScreens` と `removeDesignScreensById` に空の配列を渡すと元のモデルを返す。遷移は from ≠ to で、同じ from / to は 2 本持てず、両端は設計の画面でなければ失敗にする。id は設計をまたいで一意で、重なれば失敗にする。文言は `limits.ts` の `transitionLabel` (200 文字)。画面と導いた遷移を一度に足す `addSitemapScreens`・外す `removeSitemapScreens` は sitemap.ts (5.7)。
- **コマンド**: `ensureDesign(model, systemId)` はその system の設計が無ければ空の設計 (`layout` は `shell` / ナビなし) を足し、データベースが 1 つも無ければ既定のデータベース (`db_default` / 「既定のデータベース」/ 空の DSL) も足す。設計モードに入るだけでは呼ばない: 最初の編集 (次の段階のコマンド) が内部で呼んで作る。`effectiveDatabaseIds(model, design)` (design.ts) は、設計が使うデータベースを返す: `databaseIds` が空なら、`db_default` があればそれ、無ければ `databases` の先頭、それも無ければ無し。`removeDesign(model, systemId)` は設計だけを消す。
- **削除の連鎖** (`removeElement`): system を消すと、その設計も消える。screen を消すと、それを参照する設計の画面と、その画面を参照する遷移・ナビゲーションの項目が消える (`bindings` は画面と一緒に消える)。画面を別のシステムへ移す (`moveToSystem`) ときも、設計の画面は同じシステムの画面しか指せないので、同じ範囲を外す。この連鎖は `removeDesignScreens` (design.ts) 1 つにまとめ、`removeElement`・`moveToSystem`・`repairModel` が使う。information を消すと、テーブルの `informationIds` から外れる。データベースは消えない。`clearAll` は設計とデータベースも空にする。
- **`designReferences(model, elementId)`** (selectors): system / screen / information を消したときに一緒に消える設計データの要約 (「「予約システム」の設計 (画面 3、遷移 4、画面 UI 2、ナビゲーション 2)」「テーブルとの対応 2」)。空なら設計から参照されていない。画面も遷移も無い空の設計は参照に数えない。プロパティ欄の削除・所属 (システム) の変更の確認と、AI の `remove_element` の結果に使う。
- **データのコマンド** (commands.ts。引数は payload): `addDatabase({ id?, name })` (`db_` + ランダム文字列の id。DSL は空)、`renameDatabase({ id, name })`、`removeDatabase({ id })` (全設計の `databaseIds` から外し、そのデータベースを指す `bindings` を消す)、`setDatabaseDsl({ id, dsl })` (上限は `DSL_MAX_LENGTH`。解析エラーがあっても保存する)、`setTableInformation({ id, table, informationIds })` (置き換え。重複は除き、空ならテーブルの項目を消す。存在しない情報は失敗)、`setDesignDatabases({ systemId, databaseIds })` (`ensureDesign` を呼ぶ。存在しないデータベースは失敗)、`setDatabaseDesign({ id, dsl, tables })` (DSL と対応を 1 回の変更で置き換える。雛形・AI が使う)。名前の上限は要素の名前と同じ (`name`)。
- **画面 UI のコマンド** (commands.ts。5.7 の画面): `setDesignScreenView({ systemId, id, view, bindings? })` は画面の `view` を丸ごと置き換える。`view` はオブジェクトで、JSON にしたときの大きさの上限は `VIEW_JSON_MAX_LENGTH` (200000。超えたら失敗)。深さ (64 段) と節の数 (5 万)、`__proto__` / `constructor` / `prototype` のキーも断る (`viewShapeProblem`)。中身 (mokkun v2 の形) はコマンドでは検証せず、呼ぶ側 (画面ボード・AI の道具) が `parseV2Document` で調べる。`bindings` は省くと今のまま、渡すと置き換える (空なら消す): `item` の重複なし・空でない `item` / `table` / `column`・`databaseId` が存在するデータベースであること (テーブルと列が DSL にあるかは見ず、検証のエラー (d) が見る)。`clearDesignScreenView({ systemId, id })` は `view` と `bindings` を消す。`setDesignScreenBindings({ systemId, id, bindings })` は対応だけを置き換える。`setDesignScreenShell({ systemId, screenId, shell })` は画面ごとのレイアウトの上書きを置く (`undefined` で項目を消す。値は `shell` / `plain` だけ)。どれも設計と画面が無ければ失敗にし、設計は作らない。
- **同時編集**: 画面の `view` と `bindings` は画面ごとに 1 つの値なので、同じ画面を同時に直したときは丸ごと後勝ち。上限を超える `view` は `repairModel` が捨てる (collab-design 6 章の修復の規則)。Y.Doc の `designs`・`designScreens`・`designTransitions`・`designNav`・`databases` ルートに、入れ子の Y.Map を使わず平らな「キー → JSON の値」で置く (collab-design 4.1)。読むときはスキーマの検証関数で部品ごとに検査し、合わないものを読み飛ばす。長すぎる name 型の文字列 (ナビの group / label、遷移の label、header.*、bindings の item / table / column、テーブル名、データベース名) と DSL は、`truncateModelStrings` が上限まで切り詰める。

### 4.1 ボードの種類

ボードは**固定ボード**と**自由ボード**の 2 種類。

- **固定ボード**: レイヤーごとに 1 枚ずつ、計 12 枚。上位の要素を枠にして、その下に下位の要素を自動で並べる。位置は動かせない。上のレイヤーから順に下のレイヤーを詳細化するための場所で、要素の作成・削除、所属と関係の変更はここで行う。モデルには保存せず、毎回モデルから組み立てる (スキーマは変えない)。id は `fixed:<レイヤー>`。
- **自由ボード**: モデルの `boards`。レイヤーに関係なく要素を置き、位置と大きさを自由に決める。変えられるのは配置 (置く・外す・位置・大きさ) と名前・説明だけで、所属・関係・要素の作成と削除はできない。

### 4.2 固定ボード

| レイヤー | 枠 (上位) | 枠に並ぶもの | 枠との結びつき |
| --- | --- | --- | --- |
| 登場人物 | 「アクター」「外部アクター」「システム」「帳票」 | アクター / 外部アクター / システム / 帳票 | なし |
| 業務 | アクター | 主担当の業務 | 関係 `actorBusiness` |
| BUC | 業務 | BUC (既定 BUC は出さない) | 所属 `businessId` |
| アクティビティ | 活動の無い業務 (業務 (活動なし) の枠) と活動 | アクティビティ | 所属 `bucId` |
| ユースケース | アクティビティ (BUC ごとの段落に分ける) | 使うユースケースと、そのきっかけ・発生するイベント (連鎖の順) | 関係 `activityUsecase` |
| 画面 | システム | 属する画面 | 所属 `systemId` |
| コンテキスト | コンテキスト | 属する情報・条件・状態・バリエーション (この順) | 所属 `contextId` |
| 情報 | コンテキスト | 情報。カードに置き場所 (取得元・保存先のシステム・帳票。扱う操作から導く) を出す | 所属 `contextId` |
| 条件 | ユースケース | 判断に使う条件 | 関係 `usecaseCondition` |
| 状態 | 状態グループ (`group`) | 状態 | 属性 `group` |
| バリエーション | 情報 | 種別のバリエーション | 関係 `informationVariation` |
| 非機能要件 | システム | 属する非機能要件 | 所属 `systemId` |

- 関係で結ぶ枠では、同じ要素が複数の枠に出る (例: 複数のアクティビティから使われるユースケース)。どの枠にもつながらない要素は「主担当なし」「アクティビティなし」などの枠にまとめる (中身があるときだけ出す)。アクティビティの「未所属」、情報の「未分類」も同じ。状態の「グループなし」は、新しいグループを始める場所として常に出す。
- 登場人物のボードのアクター・外部アクターのカードには、ペルソナの呼び名と属性を「呼び名 / 属性」の 1 行で薄く出す (どちらも無ければ出さない)。
- イベントのカードには、発生タイミングがあるとき「定期: 毎日 0:05 (…)」「不定期: …」の 1 行で薄く出す (`describeEventTiming`。長いときは省略)。
- 作業のカードには、起点があるとき小さく要約を出す (「起点: 前の作業 / イベント名 (イベント) / その他」の順。長いときは省略)。
- 作業のボードは、活動の無い業務には業務の枠 (活動なし) を、活動のある業務には活動の枠だけを出す。活動のある業務に業務直下の作業が残っているときだけ、業務の枠を「活動に移してください」の知らせ付きで出し、その枠では「＋作業」を出さない。
- ユースケースのボードは、アクティビティの枠を所属する BUC ごとの段落に分け、見出しと区切り線を付ける。段落の並びはアクティビティのボードと同じ (業務ごとに既定 BUC → BUC)。アクティビティの無い BUC の段落は出さない。BUC に属さないアクティビティは「未所属」、どのアクティビティにも使われていないユースケースは「アクティビティなし」の段落にまとめる。段落の見出しをクリックすると、その BUC (既定 BUC なら業務) を選ぶ。絞り込みで段落の見出しが一致したときは、その段落の枠をすべて出す。
- ユースケース (操作) のボードでは、アクティビティの枠の中に、きっかけのイベント → ユースケース (「次に」の順) → 発生するイベント の順に並べ、1 つ前とつながっている要素の前にだけ矢印を出す。イベントは色と形 (破線・角丸) を分ける。イベントは並べるだけで、枠の × では外さない (プロパティ欄で関係を消す)。作業に属さない自動の処理は「作業なし (イベントから)」の枠に、すべてのイベントは最後の「イベント」の段落の枠に並べ、そこから「＋イベント」で作る。ユースケースのカードには対象のシステム・帳票 (直接結んだ対象か、使う画面のシステム) を出し、画面を使うときはそのシステムの隣に画面名を添える (長い名前はカードの中で折り返す)。
- 画面・非機能要件のボード: システムごとの枠に並べる。枠の「＋」で作るとそのシステムに属する。システムが無ければ、登場人物のボードで先に作るよう案内する。
- コンテキストのボード: コンテキストごとの枠に、属する情報・条件・状態・バリエーション・イベントを並べる。見出しの「＋コンテキスト」でコンテキストを作る (枠の見出しを押すと選んでプロパティ欄で編集する)。枠には 4 種類それぞれの「＋」と、別のコンテキスト (または未分類) の要素を移す「別のコンテキストから移す…」を出す。× で外すと未分類になる。状態は状態グループごとに属するので、移す・外すとグループの状態がまとめて動く。未分類の枠は中身があるときだけ出す。
- ボードの選択肢では、画面を操作の下に、コンテキストをバリエーションの下に、非機能要件を最後に置く。情報・条件・状態・バリエーションをまとめて見る場所なので。トレースやグローバルフィルターのレイヤーの並びは変えない。
- グローバルフィルター: すべての固定ボードに共通の絞り込み。各固定ボードの上に置き、レイヤーごとに要素を 1 つ以上選べる (選んだ要素はチップで出し、× で外せる。「リセット」で全部消す)。選んだ要素からトレースと同じく上下へ辿って届く要素だけを出す。レイヤーの中は「どれかにつながる」(OR)、レイヤーどうしは「すべてにつながる」(AND)。コンテキストは分類なので、選ぶと属する要素から上へも辿る。合う要素のコンテキストと、合う操作の対象 (システム・帳票。情報の置き場所) も出す。見出しの要素が合う枠は中身が無くても残し、それ以外の枠は中身が無ければ出さない。名前の絞り込みとも併用できる。保存せず、履歴にも入れない (ファイルを開くと消える)。
- すべての固定ボードの見出しの下に「書き方のヒント」を出す。ボードで扱う要素と取り違えやすい要素を並べた表 (何を書くか・粒度の目安・書き方・例・大きすぎる例・細かすぎる例) と、迷ったときの問いで、今のボードの種類を強調する。並べる組は、登場人物 = アクター・外部アクター・システム・帳票 (4 種類ともボードに出るので強調しない)、業務 = 業務・活動・作業、活動・作業・操作 = 活動・作業・操作、コンテキスト・情報・バリエーション = コンテキスト・情報・バリエーション、状態・条件 = 状態・条件。大きすぎる例・細かすぎる例には「何に当たるか」を書き、どこへ移せばよいかわかるようにする。最初は閉じておき、開閉の状態は固定ボード全体で覚える (履歴に入れない)。文言は `packages/ui/src/components/granularity.ts` にまとめる。プロパティ欄でも、課題以外の要素の名前欄の下に書き方を 1 行出す。
- 枠の「＋<種類>」で、その枠に結びついた要素を作る (作成と結びつけで 1 件の履歴)。作ったら選択し、プロパティ欄の名前欄にフォーカスする。
- 関係で結ぶ枠では、「既存から足す」で既にある要素を結べ、カード横の × で枠から外せる (関係を消すだけで、要素は残る)。所属で決まる枠 (BUC・アクティビティ・情報・状態) の移動はプロパティ欄で行う。
- 枠の見出し (上位の要素) やカードをクリックすると、その要素を選択してプロパティ欄に出す。
- 上部の「絞り込み」で名前を絞り込む。見出しが一致した枠は中身をすべて出し、それ以外の枠は一致した要素だけを出す。何も一致しない枠は出さない。絞り込みの文字列は固定ボードごとに覚え、履歴には入れない。
- 業務・アクティビティのカードには担当アクター名のラベルを出す (4.4 参照)。

### 4.3 自由ボード

- 業務は枠 (グループノード)。枠の中に BUC の小枠と、既定 BUC のアクティビティを描く。
- アクティビティ・BUC は、所属先の業務の枠 (BUC なら BUC の小枠) が同じボードにあれば、その枠の子として描く。枠がなければ単独のカードとして描き、業務名 (BUC なら「業務名 / BUC 名」) をカードのラベルに出す。
- 所属は変えられないので、枠の外へドラッグしても、別の枠に入れても、要素一覧から枠の上に置いても所属は変わらない。枠を動かすと、所属する子孫も同じ量だけ動く。
- 枠のリサイズ (左端・上端を含む) は枠の位置と大きさだけを変え、子孫の位置 (絶対座標) は動かさない。
- 線 (関係) は表示するだけで、引くことも消すこともできない。接続ハンドルは見せない。
- 線の付け根はボードごとに変えられる。既定は始点の右の辺から出て終点の左の辺に入る。線を選ぶとプロパティ欄に「線の付け根 (このボードだけ)」が出て、始点・終点それぞれ左・右・上・下の辺を選べる (「入れ替え」で両端を入れ替える)。`boards[].edges` に `{ relationId, sourceSide?, targetSide? }` で持ち、既定の辺は省略し、両方とも既定なら項目ごと消す。関係を消すと各ボードの項目も消す。
- 同じ要素を同じボードに 2 回置くことはできない。座標はボードごと。

### 4.4 アクターの担当のラベル

- アクターの担当 (`actorBusiness`・`actorActivity`) は線を引かず、相手の業務の枠のタイトル行・アクティビティのカードに担当名のラベルで出す (固定ボードでは業務・アクティビティのカード)。業務とアクティビティを結ぶ線が多く、図が読みにくくなるため。
- ラベルはアクターがボードに置かれているかに関係なく出る。外部アクターは色を分ける。カードでは 1 行に収め、入りきらない名前は省略する (マウスを乗せると全文)。

### 4.5 分析ボード

固定ボードと同じく中央を広く使い、2〜3 レイヤーをまたいで見渡す表。モデルには保存せず、毎回モデルから組み立てる (`packages/core/src/model/analysis.ts`)。id は `analysis:<種類>`。要素名をクリックすると選択してプロパティ欄に出す。分析ボードで変えられるのは、自由ボードと同じく名前・説明・時間・リンクだけ。

| ボード | 見渡すレイヤー | 何がわかるか |
| --- | --- | --- |
| 課題の分布 | 業務 → 作業・操作 → 課題 | 業務ごとに、業務・その作業・作業が使う操作に付いた課題 (具体的な課題) を重要度順に集める。どの業務にも辿れない具体的な課題は最後にまとめる。全体的な課題は下に別の表で登場人物ごとに、未整理の課題 (対象なし) はその下に別の表で出す |
| 担当別の作業一覧 | 担い手 → 業務・活動 → 作業 → 操作 | 担い手 (アクター・外部アクター) ごとの作業と、作業・操作のリンク (マニュアルなど)。担い手で絞り込める。担当の無い作業は最後にまとめる |
| 情報の所在 | 情報 → システム・帳票 → 操作、システム → 画面 → 情報、システム → イベント → 操作 | 情報 × 置き場所の表に取得・保存を出す (置き場所は扱う操作の対象と `access` から導く。2.2)。置き場所なし・紙だけ・保存先が複数 (二重管理の可能性) に印を付ける。その下に「画面と情報」の見出しで、システムごとに画面 × 情報の表を並べる (列はそのシステムの画面のどれかが扱う情報だけ。画面が扱う情報は、その画面を使う操作が扱う情報から導き、セルに取得・保存を出す)。情報を扱わない画面には「扱う情報なし」の印を付け、画面ごとに使う操作を添える。画面の無いシステムは表を作らず 1 行にまとめる (`screenInformationTables`)。さらにその下に「システムのイベント」の見出しで、システムごとに、システムから発生するイベントを並べる。発生のしかたは「直接」(システム → イベント) と「操作から」(そのシステムを対象にした操作が発生させる。対象が画面なら、画面が属するシステム。帳票はシステムではないので数えない) を分けて出し、イベントごとにきっかけにする操作とその作業 (作業に属さない自動の処理なら「作業なし」) を添える。イベントの無いシステムと、どのシステムにもつながらないイベントは、最後にそれぞれ 1 行にまとめる (`systemEventLists`) |
| イベントストーミング | 操作 → 情報・状態・条件・イベント、イベント → 操作・作業、コンテキスト → 情報 | 分析からドメインモデル (DDD) の候補を導く (`packages/core/src/model/domainModel.ts`。`deriveDomainModel`)。**コマンド候補** = 情報を書く (`access` が `write` か省略) か、イベントを発生させるか、次の状態へ遷移させる操作 (書かないものは「取得だけ」の印を付ける)。複数の作業が使う操作は、作業ごとに意図が違いうるので (作業 × 操作) の組ごとに候補を分ける (キーは `usecase:<id>/activity:<id>`)。作業に属さず、きっかけのイベントがある操作は「自動」(作業にもきっかけにも結んでいない書きかけの操作は自動にしない)。**クエリ候補 (読み取りモデル)** = 扱う情報がすべて `read` で、イベントも状態の遷移も持たない操作 (純粋な問い合わせ) と、その画面。**ドメインイベント** = 分析のイベント (発生元の操作・システム、属性の候補 = 発生元が書く情報、受け手の操作・作業。`timing` が定期 (`scheduled`) のものは時間のイベント。不定期 (`adhoc`) は外からの呼び出しなので時間のイベントにしない)。**ポリシー候補** = イベント → 操作 (`eventUsecase`。作業に属さなければ自動。イベントのコンテキストと操作が書く情報のコンテキストが違えば「コンテキストをまたぐ」)。**集約候補** = 情報ごとに、状態グループの持ち主なら「ルート候補」、書く操作があれば「集約候補」、無ければ「参照データ」。状態グループの持ち主は、その状態へ遷移させる操作 (`usecaseState`) が最も多く書く情報 (同数なら決めない。`stateGroupOwners`)。関連する情報 (`informationRelated`) は ID 参照とみなし、同じ操作で一緒に書かれる情報だけを「同じ集約か」の問いにする。**コンテキスト候補** = 分析のコンテキストごとの所属要素・状態グループ・関わる業務 (未分類は入るものがあるときだけ)。上から「気づき」(下記)、`担い手 (Actor) | コマンド (候補) | 集約 (候補) | イベント | 備考` の表 (操作から出ないイベントはコマンド無しの行)、集約の候補 (コンテキストごと)、ポリシーの候補、読み取りモデルの候補の順に出す。候補と根拠を出すだけで、決めるのは人。ドメインモデルを保存する入れ物は無い (まず導出と気づきだけ。保存と設計モードのボード、外部コンテキストの候補、コンテキストマップの方向、用語一覧、業務の流れ、イベントの属性への集約 ID と `occurredOn` の付与は将来)。要素 数千・関係 数万でも使えるよう、関係は種類ごとの索引を 1 回作って引く |

**気づき** (`packages/core/src/model/domainNotices.ts`。`domainNotices(model)`): ドメインモデルの候補を導く途中で見つかる、境界やあるべき姿の判断を「問い」として、知っておくことを「情報」として、イベントストーミングのボードの上に種類ごとにまとめて出す (問いは開いて、情報は畳んで)。分析の検証 (5.6) の警告とは別の枠で、ほとんどは分析の誤りではないので警告にはしない (サンプルの検証の警告は空のまま)。行の要素名を押すと選択してプロパティ欄に出す。コマンド候補に付く気づきは、表の備考にも見出しで出す。種類は次のとおり。

- 問い: **別のシステムの操作が状態を変えている** (状態グループの持ち主の情報を保存しないシステムの操作が、その状態を変える。例: 決済サービスの画面で注文の状態を「入金済」にする。分析の誤りではなく、別のコンテキストの出来事をイベント + ポリシーで受ける境界の候補。`access` は変えなくてよい。対象が帳票なら境界にせず、持ち主の問いにする)、**状態を変える操作が、その持ち主の情報を書いていない**、**状態グループの持ち主が決まらない** (書く情報が同数で分かれる、または遷移させる操作が情報を書いていない)、**状態の遷移の組み合わせが曖昧** (同じ状態グループで、実行できる状態と次の状態がどちらも 2 つ以上)、**1 つのコンテキストに状態グループが複数ある** (分割の候補)、**読むだけの操作が状態を変えている** (境界の問いが出ていない操作)、**読むだけの操作がイベントを発生させている** (境界の問いが出ている操作には重ねない)、**複数の作業が同じ書く操作を使っている**、**課題の対象の操作がコマンド候補になっている** (現状の手順の写し)、**同じ操作で一緒に書く情報がある** (組ごとに 1 件。同じ集約か、結果整合か)、**条件を満たさないときの結果が無い** (条件があり、結果のイベントがちょうど 1 つ)、**同じ語が別のコンテキストに出ている** (情報の名前が、別のコンテキストの情報・状態・条件・バリエーション・イベントの名前に含まれる。同じコンテキストは数えず、組は 1 回だけ。状態やイベントが情報を指しているだけのものも拾うので、問いにとどめる)。コマンド候補に付く問いは、表の備考にも見出しで出す。
- 情報: **受け手の無いイベント**、**イベントを発生させない書く操作** (帳票への記入は除く)。イベントが 1 つも無いモデルでは **イベントがまだ無い** の 1 件に、書く操作 (帳票への記入を除く) のうちイベントを出さないものが 5 件以上かつ半分以上のモデルでは **イベントがまだ少ない** の 1 件にまとめる。

### 4.6 ドメインモデル (`domain`。0.6.0)

分析 (RDRA) から導けるドメインモデル (DDD) の候補 (4.5 のイベントストーミング) に対して、**人の判断と、分析に無いあるべき姿の振る舞いだけ**を保存する入れ物。モデルのトップレベルに必須で 1 つ持つ (空でよい。`emptyDomain()`)。導けるもの (コマンド・イベント・ポリシー・読み取りモデル・用語の一覧の候補) は保存せず、毎回導く。分析の要素 (`elements`・`relations`) は変えない。

境界づけられたコンテキスト・コンテキストマップ・用語集は、システムを選ぶ前に全体で決めるものなので、設計 (`designs`。システムごと) の中ではなくトップレベルに置き、コンテキストが実装するシステムを指す。配列はすべて平らで、親は id で指す (同時編集で 1 つの Y.Map に部品ごとに置くため。collab-design 4.1)。

```
DomainModel
├ contexts: BoundedContext[]   … 境界づけられたコンテキスト
│   └ id ("bc_...")、name、english?、description?、subdomain? ("core" | "supporting" | "generic"。1 コンテキスト = 1 サブドメインとみなす)、team? (所有チーム)、
│     contextIds[] (言語の範囲にする分析のコンテキスト。0 件も複数も可)、systemIds[] (実装するシステム。空 = 未割り当て。社外のシステムだけを指し集約を持たなければ、中身の無い外部のコンテキスト)
├ aggregates: Aggregate[]      … 集約
│   └ id ("ag_...")、boundedContextId、name、english?、rootInformationId (ルートの情報)、memberInformationIds[] (中に入れる情報 = 同じトランザクションで整合させるもの。
│     それ以外の関連は ID で参照するものとみなす)、stateGroup? (ライフサイクルの状態グループ名)、invariants[] ({ id ("inv_...")、text、conditionId? (もとにした分析の条件) })
├ commands: DomainCommand[]    … コマンド。source ({ usecaseId, activityId? }) があれば分析の操作 (と作業) から採用したもので、同じ出どころの候補を置き換える。無ければあるべき姿のコマンド
│   └ id ("cm_...")、aggregateId、name、english?、source?、emits[] (発生させるドメインイベントの id)
├ events: DomainEvent[]        … ドメインイベント。eventId があれば分析のイベントを指し、同じイベントの候補を置き換える。無ければあるべき姿のイベント
│   └ id ("de_...")、boundedContextId、aggregateId? (同じコンテキストの集約。外部のコンテキストのイベントは持たない)、name、english?、eventId?、properties?[] ({ name, informationId? })
├ policies: DomainPolicy[]     … ポリシー (イベントが起きたらコマンドを実行する)。分析から導けるもの (イベント → 操作) は保存しない
│   └ id ("po_...")、eventId (domain.events の id)、commandId、auto (true = 自動、false = 人の判断をはさむ)
├ excluded: string[]           … 導いた候補のうち、あるべき姿から外したもの (出どころのキー: usecase:<id>、usecase:<id>/activity:<id>、event:<id>、policy:<関係の id>)
├ relations: ContextRelation[] … コンテキストマップ
│   └ id ("cr_...")、upstreamId (上流)、downstreamId (下流)、kind ("partnership" | "sharedKernel" | "customerSupplier" | "conformist" | "acl" | "ohs" | "publishedLanguage" | "separateWays" | "bigBallOfMud")、
│     integration? ("messaging" | "rest" | "rpc" | "file" | "manual"。省略 = 未定)、note?
└ terms: DomainTerm[]          … 用語集のうち人が決めた分。分析の要素の名前と説明から導ける分は保存しない
    └ id ("tm_...")、term、english?、definition、boundedContextId (null = 全体で共通)、elementId? (分析の要素の用語なら、その要素。その要素の英語名と定義を持つ)
```

- **英語名** (`english`): コンテキスト・集約・コマンド・イベントは識別子 (英字で始まる英数字とアンダースコア。100 文字まで。スキーマの `englishName`)。distill-ddd の形式で書き出すときの名前になる。用語の `english` は名前と同じ 200 文字までの文字列。
- **id** は domain の中で一意 (種類をまたいでも。不変条件の id も)。
- **コマンド** (`packages/core/src/model/domainCommands.ts`。`commands.ts` と同じく純粋関数で、失敗は `{ ok: false, reason }`): `addBoundedContext` / `updateBoundedContext` / `removeBoundedContext`、`addAggregate` / `updateAggregate` / `removeAggregate`、`addDomainCommand` / `updateDomainCommand` / `removeDomainCommand`、`addDomainEvent` / `updateDomainEvent` / `removeDomainEvent`、`addDomainPolicy` / `updateDomainPolicy` / `removeDomainPolicy`、`addContextRelation` / `updateContextRelation` / `removeContextRelation`、`setDomainTerm` (id か elementId のどちらか一方で既にあれば変え、無ければ足す。要素の用語の語 `term` は要素の名前の写しで、渡しても使わない。要素の用語は、英語も定義もコンテキストも無くすと消える) / `removeDomainTerm`、`setCandidateExcluded` (候補を外す・戻す。キーの形が正しくないもの、外すときにもとの操作・作業・イベント・関係が無いものは断る)、`includeInformation` / `excludeInformation` (情報を集約の中へ入れる・外す。同じコンテキストのほかの集約のルートなら、その集約を畳んで、中の情報・不変条件・コマンド・イベントを引き継ぐ)、`setDomainModel` (まるごと置き換える。部品の形がスキーマに合わないか (`domainShapeProblem`)、参照が壊れていれば断る)。更新は patch で、空文字・null は省略できる項目を消す。名前を省くと、集約はルートの情報、コマンドは出どころの操作、イベントは分析のイベントの名前になる。壊れた参照を作る入力 (無い要素、別のコンテキストの集約を指すイベント、同じ出どころのコマンドの二重の採用、同じ向きの同じ組の関係、対等な関係 (パートナーシップ・共有カーネル・別々の道) のある組の逆向きの関係など) は断る。不変条件の id は、形が正しくないもの・ほかと重なるもの (その集約の id も) を作り直す。同じコンテキストのほかの集約に入っている情報は入れられない (別のコンテキストなら、別のモデルとして持ってよい)。
- **参照の規則は 1 か所** (`packages/core/src/model/domain.ts` の `inspectDomain(domain, elements)`。壊れた箇所の一覧と、直したドメインモデルを返す): 検証 (`validateModel`。エラーにする)・修復 (`repairModel`。直して、id だけの知らせを出す)・要素を消したときの掃除 (`removeElement` → `sweepDomain`。ドメインモデルが空なら何もしない)・すべて消す (`clearAll` は空に戻す) が同じ規則を使う。
  - コンテキストが無い集約・ルートの情報が無い集約は消す。集約が無いコマンドは消す。コンテキストが無いイベントは消す。イベントかコマンドが無いポリシーは消す。どちらかのコンテキストが無い関係・両端が同じ関係は消す。
  - 参照だけ外すもの: コンテキストの `contextIds`・`systemIds`、集約の中の情報・状態グループ・不変条件のもとの条件、イベントの集約 (無いとき)・分析のイベント・属性のもとの情報、コマンドの出どころ (操作が無ければ出どころごと、作業が無ければ作業だけ。コマンドはあるべき姿のものとして残る)・`emits`、用語のコンテキスト (全体で共通にする)・要素、`excluded` のキー (形が正しくないもの、もとの操作・作業・イベントが無いもの。ポリシーのキーは関係を見ないのでそのまま)。
  - 合わせるもの: イベントの集約が別のコンテキストにあれば、イベントを集約のコンテキストへ移す (同時編集で、集約の移動とイベントの編集が重なったとき)。要素の用語の語が要素の名前と違えば、名前に合わせる (名前が空のときはそのまま。要素の名前を変えると `updateElement` が追従させる)。
  - 重なり (同時編集で 2 人が同じ候補を採用したときなど) は後のものを消す: 同じ id、同じ出どころのコマンド、同じ分析のイベントを指すイベント、同じ組のポリシー、同じ向きの同じ組の関係 (対等な関係は逆向きも同じ組)、同じ要素の用語、同じ `excluded` のキー。重なりで消したコマンド・イベントを指す `emits` とポリシーは、残したものへ付け替える (採用した人が足したポリシーを失わない)。消した部品の id は、ほかの部品が使ってよい。
  - 同じコンテキストの 2 つの集約に同じ情報が入っている、などの設計上の問題は参照の規則では見ない (コマンドは断るが、同時編集では起こりうる。設計の検証で知らせる)。
- **削除の連鎖**: コンテキストを消すと、その集約 (とコマンド・ポリシー)・イベント・関係が消え、用語は全体で共通になる。集約を消すと、そのコマンド (とポリシー) が消え、イベントは集約の参照だけ外れる。イベントを消すと、コマンドの `emits` から外れ、それをきっかけにするポリシーが消える。集約を別のコンテキストへ移すと、その集約のイベントも一緒に移る。分析の要素を消したとき (情報・コンテキスト・システム・操作・作業・イベント・条件・状態) は上の規則どおりで、プロパティ欄の削除の確認と AI の `remove_element` の結果に、一緒に消える・外れるものの要約 (`domainReferences`) を出す。
- **状態グループ**: 集約の `stateGroup` は状態グループの名前で持つ。状態の `group` を変えていき、もとの名前の状態が 1 つも残らなくなった時点で、集約の `stateGroup` も新しい名前に付け替える (`updateElement`)。どの状態にも無い名前になったら外す。
- **長すぎる文字列・形の合わない項目** (`truncate.ts` の `cleanDomain`・`cleanDomainPart`): 名前・説明・不変条件などは上限に切り詰め、形の合わない英語名・列挙の外の分類 (`subdomain`)・統合の方式 (`integration`) は、部品を残して項目だけ外す (1 つの項目のせいで、コンテキストや集約ごと全員の画面から消えないようにするため)。

### 5.0 ホーム

起動するとホーム (`#/`) が開く。画面はハッシュで分ける (`#/` ホーム、`#/local` ローカルのエディタ、`#/f/<id>` クラウドファイル、`#/invite/<token>` 招待、`#/link/<token>` リンク閲覧。collab-design 8.1)。

- **ローカル**: 「ローカルファイルを開く」「新規作成 (ローカル)」と、最近開いたローカルファイル。ログインは要らず、編集は 5.1 以降のとおり。

### 5.1 ツールバー

- 左端の「ホーム」: ホームへ戻る。保存していない変更があれば確認する。
- 「ファイル」メニュー: 新規作成・開く・最近開いたファイル・モード (分析・設計。5.7)・保存・別名で保存 (6.1)、ログイン中は「クラウドへ保存」(いま開いているモデルをクラウドファイルとして複製する)、プロンプトから作成・AI の設定 (6.2)。ショートカットは Cmd/Ctrl+O、Cmd/Ctrl+S、Shift+Cmd/Ctrl+S (入力欄の中でも効く)。「ショートカット一覧 (Cmd/Ctrl+B)」の項目もある (5.1.2)。
- 「AI」: 下に AI エージェントのペインを開閉する (6.2)。
- ボード切替 (セレクト)。分析モードは「固定ボード」(10 枚)・「分析ボード」(3 枚。開発モード (5.1.3) では「イベントストーミング」を足した 4 枚。課題の分布を先頭に置く)・「自由ボード」のグループに分ける。設計モードは「設計ボード」(6 枚)・「自由ボード」で、隣に「設計: ○○」(対象システムの切り替え) を出す (5.7)。
- 「＋ボード」は自由ボードを追加して切り替える。名前変更・ボード削除は自由ボードだけ (最後の 1 枚は削除できない。確認ダイアログあり)。
- 要素の作成は固定ボードの枠で行うので、ツールバーに「追加」メニューは置かない。
- Undo / Redo ボタン。ショートカットは Cmd/Ctrl+Z と Shift+Cmd/Ctrl+Z (Ctrl+Y も Redo)。
- 「検証」: 右側に検証パネルを出す (プロパティ欄と切り替え)。アクター／外部アクターに辿り着けない要素があれば、その件数をボタンに出す。1 つの業務に複数のアクターが付いている警告は、別の色で件数を並べる (5.6)。
- 「課題一覧」: 右側に課題一覧パネルを出す (プロパティ欄と切り替え)。
- ツールバーの下に、開いているファイル名 (サンプルなら「サンプル (まだ保存していません)」) と、保存していない変更があればその印を出す。

### 5.1.1 クラウドファイルを開いているとき

ツールバーとペインがローカルと変わるところだけを書く。詳細は collab-design 8 章。

- タイトルの横に、接続の状態 (接続中 / 切断。再接続します)、自分の役割、一緒に開いている人の色玉を出す。他の人が選んでいる要素は、その人の色の縁と名前のラベルで固定ボード・自由ボードに出る。プロパティ欄には「○○さんも選択中」を出す (ロックはしない)。
- Undo / Redo は使えない (ボタンは無効、ショートカットも効かない)。共有中の Undo は他の人の変更と絡んで結果が読めないため。誤って消したときは、書き出した JSON と、サーバーに残る 1 時間ごとのスナップショットから戻す。
- 「ファイル」メニューは「ホーム」「JSON に書き出す」「ドメインモデルを書き出す (distill-ddd)」(保存したコンテキストがあるとき)「クラウドへ保存 (複製)」「モード」だけ。Cmd/Ctrl+S は JSON への書き出しになる。
- 所有者は「共有」ダイアログを開ける (メンバーの役割、メール招待、所有者を譲る、リンクを知っている人の閲覧)。
- `viewer` とリンクで開いた人 (ゲスト) は、上に「閲覧専用です」の帯が出て、編集・AI エージェントが使えない。選ぶことはできる。ゲストは「複製して自分のファイルにする」(ログインが要る) ができる。

### 5.1.3 開発モード

内部のドメインモデル (4.5・4.6) を直に見る・直す画面は、利用者には見せない (覚えることが増えすぎるため。ドメインモデルは、実装のために裏で持つ内部の表現として扱う)。開発者が中身を確かめるための切り替えが開発モードで、**開発サーバーを起動するときの設定で決まり、既定は off、build したものは必ず off** にする。

- **設定**: 環境変数 `UNTIE_DEV_MODE` (`1`・`true`・`on` で on)。起動のときに渡すか、リポジトリの直下かアプリのフォルダの `.env.local` に書く。各アプリ (`apps/web`・`apps/cloud`・`apps/desktop`) の `vite.config.ts` が `scripts/dev-mode.mjs` の `untieDevMode(env, appDir)` で値を決め、`define` で `__UNTIE_DEV_MODE__` に埋める。`untieDevMode` は、vite の `command` が `serve` (開発サーバー) のときだけ設定を見て、`build` では必ず `false` を返す (デプロイしたもの・リリースビルドに、開発用の画面を出さない)。
- **画面側** (`packages/ui/src/devMode.ts`): `isDevMode()`。埋め込まれていないところ (テスト) では off。テストは `setDevModeForTest(true)` で切り替える。画面からは切り替えられない。
- **開発モードのときだけ出すもの**:
  - 分析ボード「イベントストーミング」(`DEV_ONLY_ANALYSIS_KINDS`)、設計ボード「ドメイン」「コンテキストマップ」「業務ルール (Souther)」(`DEV_ONLY_DESIGN_KINDS`)。ボードの選択肢 (`visibleAnalysisKinds()`・`visibleDesignKinds()`) とショートカット (E・M・K・U。`analysisEntries()`・`designEntries()`) に出さず、`setCurrentBoard`・`enterDesign` でも開けない (`isBoardAvailable`)。ドメインボードからしか始められない「AI で下書き」「AI と決める」も、一緒に隠れる。
  - 検証パネルの「検証: ドメインモデル」の節と、検証のバッジへのエラーの加算。
  - 「ファイル」メニューとコンテキストマップの「ドメインモデルを書き出す (distill-ddd)」。
  - 関連ボードの集約の枠 (`buildRelationFlow` の `aggregates`)。
  - 要素を消す確認の、ドメインモデルから消える・外れるものの内訳 (off のときは「実装のための内部の設計 (この要素を使っているところ)」の 1 行にまとめ、集約などの言葉を出さない)。
- **利用者にも見せるもの**: 設計ボード「シーケンス図」(5.7)。業務の流れと、条件で流れが変わるところ (分岐) を出し切らないと、開発するための代替パターンを網羅できないため。図に出すのは、担当・システム・操作・出来事・条件など分析の言葉だけにする。
- **off でも動き続けるもの**: 保存の形 (`domain`) と参照の規則・掃除、導出、データボードの雛形と AI の下書きが集約に合わせる動き、サンプルのドメインモデル。画面に出さないだけで、内部の表現としては使い続ける。

### 5.1.2 キーボードショートカット

修飾キーは macOS が Cmd (⌘)、Windows / Linux が Ctrl (Windows キーは使わない)。画面の表示も OS に合わせて「⌘」「Ctrl+」にする。キーの表は `packages/ui/src/shortcuts.ts`、一覧ダイアログとキーの処理は `components/ShortcutsDialog.tsx` にある。ボードの並びと名前は `packages/core` の定義から取る。

| キー | 動作 |
| --- | --- |
| Cmd/Ctrl+B | ショートカットの一覧ダイアログを、開く。ファイルメニューの「ショートカット一覧」も同じ。一覧が開いている間は、下の表のキーを押すだけでそのボードへ移る |
| Cmd/Ctrl+O・S、Shift+Cmd/Ctrl+S、Cmd/Ctrl+Z、Shift+Cmd/Ctrl+Z (Ctrl+Y)、Delete | 5.1 と 6.1 のとおり (既存) |

一覧が開いている間に押すキー (Esc で閉じる。表に無い文字キーは無視する):

| 組 | キー |
| --- | --- |
| モード | A 分析 / D 設計 |
| 固定ボード (分析) | 1 登場人物、2 業務、3 活動、4 作業、5 操作、6 画面、7 情報、8 条件、9 状態、0 バリエーション、C コンテキスト、N 非機能要件 |
| 分析ボード | I 課題の分布、W 担当別の作業一覧、L 情報の所在。開発モード (5.1.3) では E イベントストーミング も |
| 設計ボード | S サイトマップ、V ナビゲーション、G 画面、T データ、R 関連、Q シーケンス図。開発モード (5.1.3) では M ドメイン、K コンテキストマップ も |
| 自由ボード | キーなし。一覧に名前で並べ、押すと移る |

- 一覧の各行は押せる。押すとその行き先へ移ってダイアログを閉じる。いまのモード・ボードの行は強調する。
- 固定ボード・分析ボードのキーは分析モードへ切り替えてそのボードへ移る。設計ボードのキーは、設計の対象システムが決まっていればそのボードへ、未定なら「システムの選択」を出して、選んだあとにそのボードへ移る (`enterDesign(systemId, boardId)`)。モードのキーは、ファイルメニューの「モード」と同じ。自由ボードはそのボードへ移る (モードは変えない)。閲覧専用でも移動できる。
- 一覧が開いている間は、いつでもキーを受け付ける (タイマーは無い)。見出しの下には「キーを押すとそのボードへ移ります (Esc で閉じる)」と常に出す。修飾キーだけの押下は無視し、Tab・Enter・Space は横取りしない (Tab で行のボタンへ移り Enter / Space で押せる)。Cmd/Ctrl+B をもう一度押しても何も変わらない。Cmd+S のような修飾キー付きのキーは、移動せず閉じるだけで、処理したキーは `preventDefault` / `stopPropagation` して既存のキー処理 (`useKeyboard`。`defaultPrevented` なら何もしない) には渡さない。
- 文字を打つ入力欄 (`textarea`・`contenteditable`・文字や数を入れる `input`。`select` は含めない)にフォーカスがあるとき、IME で変換中、Alt が付いているとき、ほかのモーダルなダイアログが出ているときは、Cmd/Ctrl+B を拾わず、ブラウザの既定の動作もそのまま残す。拾うときは既定の動作 (Chrome の Ctrl+B など) を `preventDefault` で止める。
- 一覧ダイアログは `role="dialog"`・`aria-modal`・`aria-label="ショートカット"`。Esc・幕のクリック・「閉じる」で閉じ、開いたらパネルへ focus を移し、閉じたら元に戻す (戻り先が無ければ「ファイル」のメニューボタンへ)。Tab はパネルの中で折り返す。「そのほか」の欄は OS の表記 (macOS は `⇧⌘S`、ほかは `Ctrl+Shift+S`) で、クラウドファイルでは開く・元に戻す・やり直すを出さず、保存を「JSON に書き出す」にする。ツールバーのファイルメニューの表記も同じ。一覧が出ている間は `aria-modal` により、Cmd/Ctrl+O・S・Z などの既存のキーは効かない。
- デスクトップ (Tauri) は独自のメニューを定義しておらず、既定のメニューにも Cmd+B は無いので、そのまま WebView に届く。

### 5.2 要素一覧 (左)

- 自由ボードのときだけ出す。固定ボードは上位の要素から順に辿るので一覧は出さず、中央を広く使う。
- 左上の「‹」で閉じられる。閉じると左端に細い帯だけ残して「要素一覧」と縦書きで出し、帯か「›」で開き直す。右のペインと同じく、開閉は保存せず、履歴にも入れない。
- 種類ごとに折りたたみ。各行は名前と、課題バッジ (あれば)。BUC の行には「業務: 業務名」を添える。
- 行をクリックすると選択し、現在のボードにあればそのカードへスクロールする。
- 自由ボードでは、現在のボードに置かれているかの印を出し、行をキャンバスへドラッグするか、右クリック・行末の「置く」で現在のボードに置ける (すでにあれば何もしない)。固定ボードでは置く操作は出さない。
- 既定 BUC は出さない。

### 5.3 中央

- 固定ボード: 4.2 のとおり、枠を格子状に並べた HTML。上部に見出し・説明・絞り込み。
- 自由ボード: React Flow。ノード種別は `frame` (業務・BUC の枠)、`card` (その他の要素)。カードは種類ごとに色を変え、左上に種類名、中央に名前、右上に課題バッジ (対象になれる種類のみ) を出す。業務の枠はタイトル行に業務名と主担当のラベル、BUC の小枠はタイトル行に BUC 名。枠はリサイズできる。
- 自由ボードの Delete キーは選択中のノードをボードから外す (要素は残る)。線は消せない。固定ボードでは Delete キーは何もしない。
- 線は枠・カードより上に描く。枠の中やカードの上を通る線もクリックで選べる (その分、線が重なる所ではカードより線が先に当たる)。

### 5.4 プロパティ欄 (右)

- 右のペイン (プロパティ欄・課題一覧・検証) は右上の「›」で閉じられる。閉じると中央を広く使い、右端に細い帯だけ残して、いま何のペインかを縦書きで出す。帯か「‹」で開き直す。ツールバーの「検証」「課題一覧」を押したときも開く。開閉は保存せず、履歴にも入れない。

選択中の要素の内容を編集する。固定ボードではすべて編集でき、自由ボードでは名前と説明だけを編集できる (他の欄は無効にし、その旨を出す)。

- 共通: 種類 (表示のみ)、名前、説明。
- アクター・外部アクター: 「説明」の下に「ペルソナ」の節。呼び名・属性 (1 行)、背景と役割・目標・備考 (複数行)、IT の習熟 (セレクト。未設定 / 慣れている / 普通 / 苦手) を編集する (`setPersona`)。名前・説明と同じく自由ボードでも編集でき、閲覧専用では読み取りだけ。その下に、答え方のセレクト (ラベル「ヒアリングの答え方」。人間が聞いて、AI が答える (既定) / AI が聞いて、人間が答える) を上に、「困りごとをヒアリングする」ボタンを下に、縦に並べて出す (閲覧専用では出さない)。押すと下のペインがヒアリングモードで開く (6.4)。AI の設定 (API キー) が無ければボタンを無効にして「AI の設定」を案内し (画面ボードの「AI で作る」と同じ)、そのアクターをヒアリング中は「ヒアリング中…」で無効にする。
- イベント: 「説明」の下に「発生タイミング」の節。種類 (セレクト。決めていない / 定期 / 不定期 (随時))。定期なら周期 (毎月 / 毎日 / 毎時) と、周期に合う日・時・分のセレクト (`--` は決めていない)。種類を選ぶと補足 (定期は「補足」、不定期は「いつ起きるか」。複数行) と、表記 (`describeEventTiming`) を出す。1 項目の変更が 1 件の履歴 (`setEventTiming`)。種類を「決めていない」にすると消える。閲覧専用では読み取りだけ。
- 作業・操作: 時間 (時間単位、小数点第一位まで。0 以上。空にすると消す)。作業では、使う操作の時間の合計を「操作の合計」として作業自身の時間とは分けて出す (時間の入った操作が無ければ出さない)。固定ボードのカードと分析ボードの担当別の作業一覧 にも、作業自身の時間と操作の合計を分けて出す。同じ操作を複数の作業が使う場合は、それぞれの作業の合計に入る。名前・説明と同じく自由ボードでも編集できる。
- 作業・操作: リンク (表示名と URL。マニュアルなど)。複数持て、並べ替え・削除でき、名前をクリックすると既定のブラウザで開く (デスクトップは opener プラグイン)。URL は http / https だけ。名前・説明と同じく自由ボードでも編集できる。固定ボードのカードにはリンクの件数を出す。
- 画面: 「システム」の下に「使う操作」のセレクト (なし / 操作を 活動 (BUC) ・作業 ・作業なし のグループにまとめ、作業の名前を添える)。選ぶとその操作の対象をこの画面に入れ替え、前にこの画面を使っていた操作の対象は外れる (`setScreenUsecase`)。閲覧専用では無効。操作の「対象」のセレクトでは、別の操作が使っている画面を「画面名 (システム名) — 使用中: 操作名」として選べなくする (自分が使っている画面は選択中のまま)。
- アクティビティ: 業務と BUC のセレクト (未所属を含む)。
- 作業: 「起点」の節。この作業の起点 (起点の作業・イベント。関係名・向き・種類付きで一覧し、相手をクリックで選択) と、「起点を追加…」のセレクト (固定ボードだけ。作業は業務 (活動があれば「業務 / 活動」) ごと、イベントは別のグループに分けて出し、自分自身と既にある起点は除く)、「起点 (その他)」の 1 行入力 (固定ボードだけ。空にすると項目ごと消える)、「この作業を起点にする作業」(後続の作業。読み取りだけで、名前をクリックで選択) を出す。起点が無いとき、足せる固定ボードでだけ案内を出す。自由ボード・分析ボード・閲覧専用では読み取りだけ。起点の関係 (`activityTrigger`・`eventActivity`) は、下の関係一覧・「関係を追加」には出さない。
- BUC: 業務のセレクト。
- 情報・状態・条件・バリエーション: コンテキストのセレクト (未分類を含む。状態は状態グループごと)。つながりから見た候補が今の所属と違えば、候補と「〇〇にする」ボタンを出す。状態: 状態グループ。バリエーション: 値の一覧 (追加・削除・並べ替え)。
- 課題: 重要度 (1〜5)、区分 (全体的・具体的・未整理)、対象の一覧 (種類・名前・そのレイヤーの固定ボードへ移る「移動」・外す)。「対象を追加」はレイヤーごとに分けて出し、対象があるときは同じ区分の候補だけを出す。別の区分に付け替えるときは、いまの対象をすべて外してから追加する。
- 関係一覧: この要素が始点または終点になっている関係を、関係名・向き・相手の種類 (レイヤー名) 付きで一覧し、相手をクリックで選択する。固定ボードでは × で関係を消せ、「関係を追加」のセレクトで結べる要素 (関係名・向き・種類ごと。既にある関係は除く) を選んで関係を足せる。固定ボードの枠で表せない関係 (担当アクター、情報どうしの関連、条件とバリエーション・状態、状態とユースケース) はここで編集する。操作では、対象 (システム・帳票・画面) は上の「対象」の欄で選ぶので、一覧には重ねて出さない。操作の「扱う」の行には取得・保存の区別 (`access`: 取得・保存 / 取得 / 保存) のセレクトを出す (`setRelationAccess`)。
- 導いた一覧 (関係とトレースの間): 情報には「置き場所」(取得元・保存先のシステム・帳票)、システム・帳票には「ここにある情報」、画面には「扱う情報」を、扱う操作から導いて出す (2.2)。役割 (取得元・保存先) と、根拠の操作を添え、クリックで選ぶ。ここでは変えられず、変えるには操作のプロパティ欄で扱う情報・取得・保存・対象を直す。
- トレース (関係と課題の間): 要素から上 (担い手の側) と下 (詳細の側) へ、直接つながっていない要素まで辿り、レイヤーごとに 1 行で表にする (`packages/core/src/model/lineage.ts`)。列はレイヤー・要素・移動。上は登場人物の側から、下は近い順に並べ、自分の行を間に置く。要素名をクリックするとその要素を選ぶ。「移動」はそのレイヤーの固定ボードへ、今の要素を選んだまま移り、その要素のカードか、その要素が見出しの枠 (無ければ所属先や関係で結ばれた要素) までスクロールする。要素が枠や段落の見出しになっているボードでは、その枠・段落を選択中として出す。1 行に 7 件以上あるときは 6 件まで出し、「ほか N 件」で開く。辿る向きは、業務 → 主担当、活動 → 業務、作業 → 活動 (業務に直接なら業務)・担当、操作 → 作業・きっかけのイベント・対象 (システム・帳票・画面)、情報 → 操作・コンテキスト (置き場所へは操作を通って届く)、条件 → 操作・コンテキスト、状態 → 操作・条件・コンテキスト、バリエーション → 情報・条件・コンテキスト (下へはこの逆)。情報どうしの関連は同じレイヤーなので辿らない。コンテキストは分類なので、上へは属する要素から辿る。 つながる要素が無くても、その種類の上下に来うるレイヤーは「(未設定)」(灰色) の行で出し、「移動」でそのレイヤーの固定ボードへ移れる (結ぶ相手を作りに行けるように)。来うるレイヤーは種類で決める (例: 画面の下には何も来ない (扱う情報は操作から導く)、外部アクターは業務の主担当にならないので下に業務を出さない)。
- 課題: この要素を対象にしている課題の一覧と「課題を追加」ボタン (登場人物・業務・作業・操作のみ。固定ボードだけ)。見出しに区分 (登場人物なら全体的な課題、業務・作業・操作なら具体的な課題) を添える。
- 自由ボードでは「ボードから外す」(ボードにある場合)、固定ボードでは「削除」。
- 課題では左端に「削除」を出し、課題を削除すると課題一覧へ戻る。右端は作ったばかりかどうかで変える。
  - 追加フォーム (「＋課題」「課題を追加」で作った直後): 「次の課題を登録する」。作ったときと同じ対象で次の課題を作り、名前の入力へ移る。続けて書き出せるようにするため。
  - 編集フォーム (既存の課題を選んだとき、または別の要素を選んでから戻ったとき): 「課題一覧に戻る」。
- 関係 (線) を選択したときは、関係名と両端の要素を出す (削除は無い)。

### 5.4.1 スマートフォン (狭い画面)

幅 768px 以下 (`packages/ui/src/viewport.ts` の `MOBILE_MAX_WIDTH` と、`app.css` の末尾の `@media` を同じ値にそろえる) では、3 カラムをやめて、キャンバス (固定ボード・分析ボードを含む) が画面いっぱいを使う。広い画面の見た目・挙動は変えない。

- 左右のペインは画面の上に重なるドロワーにする。開いている間は外側に暗い幕 (`.pane-backdrop`) を出し、幕を押すか、ペインの「‹」「›」で閉じる。
- 起動時・新規作成・ファイルを開いたときは、ペインを両方閉じておく (広い画面では右ペインを開く)。開閉の状態 (`rightPanelOpen`・`elementListOpen`) は広い画面と同じものを使う。
- ツールバーに、狭い画面だけ「要素一覧」(自由ボードのみ)・「プロパティ」のボタンを出して、ペインを開閉する。「検証」「課題一覧」は、ペインが閉じているときは (すでにその内容でも) 押すと開く。ボードの選択は 1 行に広げ、固定ボード・分析ボードでは使えない「名前変更」「ボード削除」は隠す。
- 設計ボード (サイトマップ・ナビゲーション・画面・データ・関連・ドメイン。コンテキストマップは左のペインを持たない) の左のペイン (`.sitemap-tree`) はドロワーにせず、キャンバスの上に縦に積む (左のペインが 36dvh、キャンバスが 64dvh。`.main.with-tree` の `@media`)。右のペインは広い画面と同じくドロワー。
- ダイアログは画面の幅と高さに収め、入力欄は 16px (iOS で拡大されない)、ボタンは指で押せる高さにする。ミニマップは出さない。キャンバスのパン (1 本指) とピンチ (2 本指) は React Flow の標準のまま使える (枠の上から始めた 1 本指のドラッグは、枠を動かす)。

### 5.5 課題一覧パネル

最初に課題を書き出し、それを紐解くように整理するための場所。

- 見出しの「＋課題」で対象のない課題を作り、選んでプロパティ欄の名前の入力へ移る。どのボードからでも作れる。
- 課題を 未整理・全体的な課題・具体的な課題 の 3 段に分ける。課題の無い段には、何を入れる段かの説明を出す。
- 並べ方は「課題ごと」と「対象ごと」を切り替えられる (保存しない)。
  - 課題ごと: 段ごとに重要度の高い順 (同じなら名前順)。各行は重要度、名前、対象要素の種類と名前。
  - 対象ごと: 全体的・具体的の段を、対象の要素ごとにまとめる。まとまりの見出しに種類・名前・そのレイヤーの固定ボードへ移る「移動」・その要素を対象にした課題を作る「＋課題」を出す。対象は 登場人物 → 業務 → 作業 → 操作 の順、同じ種類は名前順。対象が複数ある課題は、それぞれのまとまりに出る。未整理の段はいつも課題ごとに並べる。
- 行をクリックするとその課題を選択してプロパティ欄に切り替える。対象名をクリックすると対象要素を選択する。
- 課題はどのボードにも出ないので、プロパティ欄では自由ボード・分析ボードでも重要度・対象を編集でき、削除できる。

### 5.6 検証パネル (担い手まで辿れるか)

設計モードでは、同じ「検証」ボタンとパネルが設計の検証 (5.7) に切り替わる。以下は分析モードの検証。 ドメインモデルの候補から見つかる問い・情報 (4.5 の「気づき」) は検証ではなく、分析ボード「イベントストーミング」に出す。

すべての要素が担い手 (アクター／外部アクター／システム) まで辿れるかを調べる (`packages/core/src/model/trace.ts`)。つながりは必須にしない。上から順に書き出していく途中の状態 (担当の決まっていない作業など) を作れるようにするため。代わりに、辿り着けない要素とどこで途切れているかを知らせる。

- 要素ごとに「担い手に近い側」を決め、担い手から下へ広げて届いたものを「辿り着ける」とする。

| 要素 | 担い手に近い側 |
| --- | --- |
| 業務 | 主担当のアクター |
| 活動 (BUC) | 業務 |
| 作業 | 担当のアクター／外部アクター (必須。所属の活動・業務からは辿らない) |
| 操作 | 使う作業、きっかけのイベント |
| イベント | 発生させる操作・システム |
| 画面・非機能要件 | 属するシステム |
| 情報 | 扱う操作、関連する情報 (置き場所からは辿らない。置き場所は扱う操作から導く) |
| コンテキスト | 入っている情報 |
| システム | 担い手なので辿り着く先。ただし操作の対象・イベントの発生元のどちらでもなく、画面も無ければ途切れとする |
| 帳票 | 対象にする操作 |
| 条件 | 判断に使う操作 |
| バリエーション | 種別にしている情報・条件 |
| 状態 | 実行可・次の状態で結んだ操作、状態を参照する条件 |

- 作業は担当を必ず持つ。業務に属していて業務に主担当がいても、作業に担当が無ければ途切れとする。
- 情報は置き場所 (システム・帳票) からは辿らない。0.4.0 からは置き場所自体を扱う操作から導くので、扱う操作の無い情報は置き場所も持たず、途切れになる。
- **エラー: 1 つの画面を複数の操作が使っている** (`TraceResult.errors`。種類 `screenSharedByUsecases`)。「1 操作 = 1 画面」の約束で、画面を対象にする操作 (`usecaseScreen` でその画面を結ぶ操作) が 2 つ以上あればエラーにする。辿れるかの途切れとは別の一覧で、ボタンの件数には辿り着けない要素の数に足す。パネルには見出し「エラー: 1 つの画面を複数の操作が使っている (n)」(`TRACE_ERROR_TITLES`) を付け、「画面「○○」を複数の操作が使っています (A、B、C)」と、画面と操作のリンク、直し方 (操作ごとに画面を分ける) を出す。ファイルを開くときの検証 (`validateModel`) のエラーにはせず (既存のファイルが開けなくなるため)、`repairModel` も触らない。関係を結ぶコマンド (`addRelation`) も止めない。
- **警告 (エラーではない)** (`traceWarnings`)。辿れるかの件数には数えず、直さなくても編集・保存はできる。パネルでは種類ごとに [警告] の見出しと案内を付けて、要素と関わる要素をリンクにして出し、ボタンには警告の数をエラーとは別の色 (黄) で並べる。
  - **1 つの業務に複数のアクター**: 業務に結ぶのは主担当の 1 人で、ほかの人は作業の担当として作業に結ぶ。案内は「業務をアクターごとに分解できるか検討してください」。外部アクターは業務に結べないので、対象はアクターだけ。
  - 操作の連鎖 (「次に」でつないだ並び) がイベントで終わらなくても警告しない。結果をイベントで表さない操作もあるため。
- 課題 (対象の要素に付くもの) と既定 BUC (業務と一体) は検証の対象にしない。
- 対象のない課題 (未整理) は、エラーではなく [情報] に「対象のない課題」として出す。紐解きの残りが見えるようにするため。
- 辿り着けない要素のうち、アクターに近い側がまったく無いものを「途切れ箇所」とし、種類ごとの理由 (例: 「どの作業にも使われていません」) を出す。関連する情報どうしのように、互いにつながっているだけで外へ出られないものも途切れ箇所にする。
- パネルには途切れ箇所だけを並べ、理由と直し方 (その要素自身で何をすればよいか) を出す。その先で辿り着けない要素 (上へさかのぼるとその途切れ箇所に行き着く要素) は、種類ごとの件数だけを出す。別のレイヤーの要素を開いても直せない (例: 業務の主担当は操作からは結べない) ので、迷わないようリンクにしない。
- 途切れ箇所の要素名をクリックすると、その要素を編集できる固定ボードへ移って選択し、プロパティ欄に出す。
- [情報] として、コンテキストの所属の見直し候補も出す (エラーではないので、ボタンの件数には数えない)。コンテキストに属していない要素 (候補があれば添える) と、属するコンテキストの要素とつながらず別のコンテキストの要素とだけつながる状態・条件・バリエーションを挙げ、候補のコンテキストへ 1 クリックで移せる。情報どうしの関連はコンテキストの結合そのものなので、情報は「未分類」のときだけ挙げる。状態グループは 1 件にまとめる。
- モデルが変わるたびに計算し直す。

### 5.7 設計モード

分析で出てきたシステムごとに、サイトマップ・ナビゲーション・画面 UI・データ (DB) を設計するモード。土台 (モードの切り替え・対象システムの選択・設計データの入れ物・削除の連鎖) と、サイトマップ・ナビゲーション・画面・データ・関連・ドメインの 6 つのボードができている (関連は読み取り専用で、ほかのボードの結果を図で見せる。ドメインも読み取り専用で、分析から導いたドメインモデルの候補を対象のシステムにしぼって見せる)。

設計は次の順に進める。**サイトマップ**で画面と遷移を決め、**データ**でデータベース (DSL) と、テーブルが表す情報を決め、**ナビゲーション**で共通の枠とナビゲーションを決め、**画面**で 1 つずつの画面 UI を作る (項目や一覧の列を、データのテーブルの列に結ぶ)。前のボードの結果が次のボードの材料になる: 画面ボードは、サイトマップの画面と遷移、データボードのテーブルと列、レイアウトのナビゲーションを使い、プレビューにはレイアウトの枠が付く。どのボードからでも始められ、足りないものは検証 (下の「設計の検証」) が知らせる。

- **モード**: `analysis` (分析。既定) と `design` (設計)。`ui.mode` と、設計の対象のシステム `ui.designSystemId` をストアに持つ (どちらもファイルには保存せず、履歴に積まない)。新規作成・開く・クラウドで開く・閉じるで分析に戻り、対象も忘れる (クラウドのつなぎ直しだけ引き継ぐ)。「ファイル」メニュー (ローカル・クラウドの両方) の「モード」サブメニューで「分析」「設計」を切り替え、今のモードに ✓ を付ける。
- **対象システムの選択**: 設計に切り替えるとき、対象が未定なら「システムの選択」ダイアログを出す。モデルのすべてのシステムを名前順に並べ、設計データがあるものには「設計あり」を付ける。選ぶと設計モードへ移る (最初のボードはサイトマップ)。**モデルには書かない**: 設計と既定のデータベースは、最初の編集 (次の段階のコマンド) が `ensureDesign` を内部で呼んで作る。ダイアログの「設計あり」は、そのシステムの設計 (`designs` の項目) があるときに付ける。選ぶ操作はキーボードだけでもできる (選ばれているラジオ、無ければ先頭にフォーカスし、Enter で決定)。キャンセルしたら分析のまま。システムが無ければ「システムがまだありません。登場人物ボードでシステムを足してください。」と出して選べない。最後に設計したシステムの id を localStorage (`untie.design.lastSystemId`) に覚え、初期選択にする (モデルにあるときだけ。切り替え中はいまのシステム)。設計モードの間は、ボードの select の隣に「設計: ○○」のボタンを出し、同じダイアログで切り替えられる (キャンセルなら今のまま)。閲覧専用のファイルでは設計データを書けないが、設計モードに入って見ることはできる。
- **ボードの出し分け**: 分析モードは固定ボード + 分析ボード + 自由ボード (今までどおり)。設計モードは設計ボード + 自由ボード。モードと合わないボード (分析モードの `design:*`、設計モードの `fixed:*`・`analysis:*`) が選ばれたら、そのモードの最初のボード (分析は `analysis:issues`、設計は `design:sitemap`) へ戻す (モデルの変更や同時編集のあとの `reconcileUi`)。一方、`setCurrentBoard` に固定ボード・分析ボードの id が渡されたら分析モードへ移し (設計モードから要素の場所へ飛べる)、設計ボードの id が渡されたら設計モードへ移す (対象のシステムが未定なら何もしない)。自由ボードはモードを変えない。設計モードに入ったら課題一覧のペインをプロパティに替えて右のペインを開き、ツールバーの「課題一覧」ボタンは設計モードでは出さない (分析に戻しても自動では開き直さない。「検証」はそのまま)。
- **設計ボード** (`packages/core/src/model/design.ts`。id は `design:<種類>`。固定ボード・分析ボードと同じく、モデルには保存せず、左の要素一覧も出さない):

| ボード | id | 中身 |
| --- | --- | --- |
| サイトマップ | `design:sitemap` | 画面と画面遷移 (`screens`・`transitions`) |
| ナビゲーション | `design:navigation` | 共通の枠・ヘッダー・ナビゲーション (`layout`) |
| 画面 | `design:screen` | 画面 UI (`view`) と、項目 → テーブルの列の対応 (`bindings`) |
| データ | `design:data` | データベースの DSL とテーブル → 情報の対応 (`databases`) |
| 関連 | `design:relation` | 情報 ↔ テーブル ↔ 画面の関連の図 (読み取り専用。保存するものは無い) |
| ドメイン | `design:domain` | 分析から導いたドメインモデル (DDD) の候補を、対象のシステムにしぼった図・表・用語 (読み取り専用。保存するものは無い) |

  6 つのボードすべてに中身がある (下の「サイトマップ」「ナビゲーション」「画面」「データ」「関連」「ドメイン」)。
- **サイトマップ** (`design:sitemap`。`packages/core/src/model/sitemap.ts` と `packages/ui/src/components/design/`): 画面の追加・削除の木、画面と遷移の図、選んだ画面のプロパティの 3 列。設計の対象システムを以下「対象」と呼ぶ。保存するのは設計の `screens`・`transitions` だけで、チェックの状態・入口・注記・位置はその都度導く。
  - **左の木** (`SitemapTree`): 上に「組み込みの画面」のチェックボックス (トップページ・サインイン・ホームの順。トップページは未ログインの人が最初に見る画面、ホームはサインインした人が最初に遷移する画面 = メニューの起点。サインアップ・パスワードリマインダーは出さない)、その下に分析の木 (業務 → 活動 → 作業 → 操作。既定の活動は出さず、その作業を業務の直下に置く。活動に入っていない作業は最後。作業に使われていない操作は出さない)。操作の行には、その操作の画面名 (対象の画面のみ) を小さく添える。
  - **チェックの意味**: 「対象の画面に届く」とは、操作が `usecaseScreen` で対象の画面 (`screen.systemId` が対象) に結ばれていること。節 (操作・作業・活動・業務) ごとに「部分木が届く画面の集合」を持ち、それがすべてサイトマップにあれば checked、一部なら indeterminate、無ければ unchecked。届く画面が無い節は薄く表示してチェックできない。チェックを入れると、部分木の届く画面のうちまだ無いものを足し、あわせて遷移を導いて足す (1 回の変更)。外すと、部分木の届く画面をすべて消す (ほかの操作と共有している画面も消える。残したい側は再チェックで戻る)。消える画面に `view` か `bindings` があるとき (画面設計に進んでいる) は、確認ダイアログ (danger) に画面名を並べて「次の画面の設計も一緒に消えます」と出し、無ければ確認しない。画面が消えると、それを指す遷移・ナビの項目も消える。組み込みの画面も同じ。閲覧専用ではチェックできない。
  - **遷移の導出** (`deriveTransitions(model, systemId, screens, existing)`): 遷移は from ≠ to・重複なしで、`existing` にある同じ from / to は足さない。導いた遷移の `via` は未定のまま (組み込みの画面からのものを除く)。足すときは `addSitemapScreens` が、**足した画面にかかわる遷移だけ**を導いて足す (ユーザーが消した遷移を、別の画面を足すたびに戻さない)。
    1. 作業の中: 操作 A → (「次に」) → 操作 B、または A → イベント (`usecaseEvent`) → きっかけ (`eventUsecase`) → B で、A の画面 X と B の画面 Y がどちらもサイトマップにあり X ≠ Y なら X → Y。A と B が別の作業でも同じ扱い。
    2. 作業の間 (起点): 作業 B の起点が作業 A (`activityTrigger`) なら、A の「最後の画面」→ B の「最初の画面」。起点がイベント (`eventActivity`) なら、そのイベントを出す操作 (`usecaseEvent`) の画面 → B の最初の画面。イベントを出すのがシステムだけ (`systemEvent`) なら遷移にしない。作業の「最初の画面」は、作業の中の連鎖で前が無い操作の画面、「最後の画面」は次が無い操作の画面。その操作に (サイトマップにある) 画面が無いときは、連鎖を先 (最後は手前) へ辿って画面のある操作まで進める。連鎖が輪で、前 (次) が無い操作が無いときは、輪の中で作業の中の関係の並び順が最初の操作を使う。
    3. 遷移にしない: 担当のアクターが交わらないとき (外部アクターは数えない。どちらかの担当が空なら違うとは言えないので通す)、A の画面が別のシステムのとき (対象外の画面はそもそもサイトマップに無い)。遷移にしなかったものは、入口の注記にする。
  - **入口と注記**: 入口は**作業ごと**に判定する。作業の最初の画面のうち、その作業の起点から遷移で入れないもの (起点が無い・その他だけ・担当が違う・別システム・システムが出すイベント) が入口。いずれかの作業で入口なら、画面として入口 (`entryScreenIds`)。作業に使われていない操作の画面は入口にならない。`entryNotes(model, systemId, design)` は入口の画面ごとに、その作業の判定から注記を返す: 「作業「○○」から引き継ぎ」(担当が違う)、「○○から」(起点の作業・イベントを出す操作の画面か、対象 (`usecaseSystem`) が別のシステム。システム名はそのまま)、「イベント「○○」から」(`systemEvent` で出すイベント、または出す操作が無いイベント)、「起点: ○○」(作業の `triggerNote`)。注記が無い入口は空の配列。
  - **組み込みの画面** (入口に合わせて付け直す。`builtinTransitions`): 入口 = 分析の画面の入口 (`entryScreenIds`)。**ホームがあるとき**: トップページとサインインの両方があればトップページ → サインイン (`via: "button"`)、サインイン → ホーム (`afterSubmit`)、ホーム → 入口の画面すべて (`nav`)、サインインが無くトップページがあればトップページ → ホーム (`nav`)。トップページ → 入口の `nav` とサインイン → トップページは付けない。**ホームが無いとき**はトップページが起点の役 (これまでの規則。トップページ → サインインの button は付けない): トップページ → 入口の画面すべて (`nav`)、サインイン → トップページ (`afterSubmit`)。トップページも無ければサインイン → 入口の画面すべて (`afterSubmit`)。画面を足す・外すたびに (`addSitemapScreens`・`removeSitemapScreens`。`syncBuiltinTransitions`)、組み込みの画面からの遷移のうち、自動で付けたもの (`via` が `nav` / `afterSubmit` のまま、またはトップページ → サインインの `button` で、`label` が無いもの) を今の入口と組み込みの画面の有無に合わせて付け直す (足りないものを足し、不要になったものを消す)。**自動で付けた遷移 (label 無し) は、付け直しで消えることがある。残したい遷移には文言 (`label`) を付ける**。手で足した遷移のうちホーム → トップページ・サインイン → トップページの button などは対象外で、そのまま残る。
  - **中央** (`SitemapCanvas`): React Flow で画面をノード、遷移をエッジに描く。位置は保存せず、入ってくる遷移が無い画面から幅優先で層を決め、左から右へ並べる (同じ層は縦に並べ、遷移が 1 本も無い孤立した画面は最後の列。動かせない。ズーム・パンはできる)。ノードは画面名、「入口」の印、画面 UI の有無の印 (「UI あり」/「UI なし」)、注記 1 行 (`data-sitemap-node`)。エッジは `via` の表示 (未定は破線。ボタン / 一覧の行 / メニュー / 送信のあと) と文言。エッジを押すと from の画面を選び、プロパティの該当の遷移を強調する。ノードはキーボードで選べる (Tab で止まり、Enter / Space)。画面の集合か対象のシステムが変わると全体が見えるよう合わせ直す (`fitView`)。画面が 1 つも無いときは案内を出す。選んだ画面は `ui.designScreenId` (保存しない・履歴に積まない。対象のシステムやモードが変わるか、画面が設計から無くなると `reconcileUi` が消す)。
  - **右のペイン** (`SitemapProperties`): 選んだ画面の名前 (読み取り。分析の画面なら「分析の画面ボードで見る」)、画面 UI の有無、レイアウト (読み取りで 1 行。上書きが無ければ「設計に従う (shell)」のように設計の値を括弧で添え、あれば `shell` / `plain`)、分析の画面の説明、この画面を使う操作 (作業名つき)、この画面が使う情報 (その画面を使う操作が扱う情報から導く。`screenInformations`)、この画面が判断する条件 (その画面を使う操作が判断する条件 (`usecaseCondition`) から導く。`screenConditions`。条件名と小さく根拠の操作名、説明は `title`。無ければ「なし」。組み込みの画面には出さない)、入口の注記、出ていく遷移 (遷移先・きっかけ (未定 / ボタン / 一覧の行 / メニュー / 送信のあと)・文言・削除)、「遷移を追加…」、入ってくる遷移 (読み取り。押すとその画面を選ぶ)。「画面ボードで開く」で `design:screen` へ移り (選択はそのまま)、「サイトマップから外す」は木のチェックを外すのと同じ (確認の規則も同じ)。閲覧専用では編集できない。
- **ナビゲーション** (`design:navigation`。`packages/ui/src/components/design/Navigation*.tsx`・`Mokkun*.ts(x)`・`mokkunDoc.ts`・`ai/designNav.ts`): 共通の枠・ヘッダー・ナビゲーションメニューを決め、mokkun で描いた画面のプレビューで確かめる。左のナビゲーションメニュー、中央のプレビュー、右の枠の設定の 3 列。保存するのは設計の `layout` だけ (画面ごとの上書き `DesignScreen.shell` は画面ボードで決める。下の「画面」。プレビュー中の画面が上書きしているときは、ツールバーに「この画面はレイアウトを上書きしています (○○)。画面ボードで変えられます」を出す。左のナビゲーションメニューの「メニューは出ません」の案内は、メニューが出る画面 (`hasMenuScreen(design)`。レイアウトが `shell` の画面が 1 つでもあるか。検証 (h) と共有) が無いときだけ出し、設計が `plain` でも上書きで `shell` にした画面があれば、その旨の案内に替える。コマンドは `setDesignLayout`・`setDesignNavigation`。どちらも `ensureDesign` で設計を作る)。
  - **左** (`NavigationMenuPane`。ナビゲーションメニュー): グループの一覧 (名前、↑↓ で並べ替え、×)。各グループの中に項目 (画面の select = サイトマップの画面 (トップ・サインイン・ホームも選べる)、表示名 (空なら画面名)、↑↓、×)。「＋グループ」「＋項目」。閲覧専用では編集のボタンを出さない。グループの id は `nav_` で始まり、設計をまたいで一意 (`setDesignNavigation` が重なりを断る)。
  - **中央** (`NavigationBoard`。`React.lazy` + `Suspense` で読み込み、mokkun (約 750KB) はナビゲーションを開くまで読まない): 上の select でプレビューする画面を選ぶ (サイトマップの画面)。何も選んでいなければ、選択中の画面 (`ui.designScreenId`) → ホーム → トップページ → 最初の画面の順。プレビュー内のメニュー・ボタンで移ると select も変わる (`selectDesignScreen`)。画面が 1 つも無ければ「サイトマップで画面を足すとプレビューできます」、画面 UI (`view`) が mokkun の検証に通らない画面は、その画面だけ仮の画面にして理由をその画面に出す (ほかの画面は見られる)。画面の外の問題で文書全体が検証に通らないときは、その理由を出す。
  - **プレビューの仕組み** (`MokkunPreview`): mokkun (`mokkun@0.2.2`。React に依存しない v2 形式のライブラリ) の `renderViewV2(schema, 画面の id)` (options は渡さない) で、ルートが `.mokkun-v2` の HTML 文字列にし、iframe の `srcdoc` に入れる。iframe は `sandbox="allow-same-origin"` だけを付け、スクリプトは動かさない。
    - **CSS**: v2 の描画に要る CSS (DADS のスタイルと v2 のスタイル) は、npm パッケージの CSS ファイル (`mokkun/style.css`。v1 用で、アプリには読み込まない) には入っていない。mokkun 0.2.2 からは `MOKKUN_V2_CSS` (文字列) と `mokkun/v2.css` で公開されているので、`mokkunCss()` が `MOKKUN_V2_CSS` を使う。DADS の CSS は `html`・`a`・`:focus-visible` などの要素セレクタを含み、親の画面には差せないので、srcdoc の `<style>` に入れる。CSS の先頭には Google Fonts の `@import` が入っている。CSP に反し、ローカル専用の Web 版でも外部へ通信してしまうので、`@import` はすべて取り除く (フォントは端末のものになる)。そのほかの外部参照は無い (アイコンは inline の SVG)。
    - **CSP**: srcdoc の iframe は親の CSP を継承する。inline の `<style>` には `style-src 'unsafe-inline'` が要るが、Web 版 (`apps/web/public/_headers`)・クラウド版 (`apps/server/public/_headers`)・デスクトップ (`tauri.conf.json` の `csp`) とも、すでに `style-src 'self' 'unsafe-inline'` なので変えていない (`script-src` は iframe の中にスクリプトを入れないので不要。`frame-src` は `default-src 'self'` に従うが、`about:srcdoc` は対象外)。
    - **遷移**: iframe の中にスクリプトは入れず、親が `onLoad` で `iframe.contentDocument` にクリックの listener を付ける (srcdoc は同一オリジン)。mokkun の v2 の描画は、遷移先を次の属性で持つ: グローバルナビ・パンくず・一覧のリンク・値のリンクは `data-nav-view="<view>"` (`href="#<view>"`)、遷移のボタンは `data-navigate-to="<view>"` (`navigate` と、送信のあとの遷移先を持つ `submit`)。ナビのグループのボタン (`data-submenu-toggle`) は mokkun ではスクリプトが開閉するので、同じ処理 (`aria-expanded` と、メニュー本体の `hidden`) を listener で行う。そのほかのリンク (`href="#..."` も相対 URL も) は、iframe が親のページへ移らないよう、すべて既定の動作だけ止める。タブ・確認ダイアログ・入力の条件表示など、スクリプトで動く部品はプレビューでは動かない。iframe の中の要素は親と別の `window` の `Element` なので、`instanceof` ではなく `nodeType` で判定する。
  - **文書の組み立て** (`buildMokkunSchema(model, systemId, design)`。純粋。`cachedMokkunDoc` が設計の参照とモデルが同じなら結果を使い回す): `app.name` は設計の layout の `header.systemName` (空なら対象システムの名前。mokkun の `header.systemName` は小さな補足なので使わず、`app.name` に出す)、`layout` は設計の layout (画面ごとの上書き `DesignScreen.shell` は文書に入れない。mokkun の `app.layout` は文書で 1 つなので、戻り値の `shellOf(viewName)` で画面ごとの実際のレイアウト (`effectiveShell(design, screen)`。上書きがあればそれ、無ければ設計の値) を渡し、`MokkunPreview` / `previewSrcDoc(schema, viewName, shell?)` がその画面を描くときだけ `app` の `layout` を差し替えて `renderViewV2` する。ナビゲーションボードも画面ボードも同じ経路)、`header` は利用者名・テナント名、`navigation` は設計のナビゲーション (view は画面の id、label は省略時は画面名。項目の無いグループは出さない)。`views` は設計の画面ごとに、キーは画面の id、`title` は画面名、`goal` は `view` の goal、無ければ分析の画面の説明 (それも無ければ title)。`title` は画面名が正 (`view` の title は上書きされる)。`sections` などは `view` があればその中身をそのまま、無ければ仮の 1 セクション (`kind: "readonly"`・「画面 UI はまだありません」。分析の画面が使う情報を readonly の text で 1 つずつ、情報が無ければ `note` だけ。組み込みのサインインだけは、ID・パスワードの必須項目を持つ `form` (id `signin`))。メニューに載っている画面には、現在地を示す `nav` を付ける。ロールは付けない (5.7 の画面の「ロール」)。遷移は、画面 UI の `submit` / 一覧の行の `to` に写せるときは写し (5.7 の画面の「遷移の写し方」)、そうでなければ (`afterSubmit` を除く) `secondaryActions` に `navigate` で足す (同じ遷移先への遷移が複数あるとき (button と row など) は最初の 1 つだけを写す。`to` は遷移先の画面の id、label は遷移の文言か遷移先の画面名。操作の id は遷移の id で、`view` の操作 (主・副・セクション・一覧の行・一括) の id と重なるときは `_2` のように付け直し、遷移は捨てない)。ただし、きっかけ (`via`) がメニュー (`nav`) の遷移は足さない (メニューで行く)。組み立てた文書は mokkun の `parseV2Document` に通す。エラーの path (`views.<id>…`) から壊れた画面を見つけ、その画面だけ仮の view に替えてもう一度検証し、理由は `viewErrors` (画面の id → 理由) に入れる。それでも通らないときだけ理由を `error` に入れる。
  - **右** (`NavigationLayoutPane`。枠の設定): 「レイアウト」のラジオ (`shell` = ヘッダー + グローバルナビ + パンくず、`plain` = 枠なし) と、「ヘッダー」のシステム名・利用者名・テナント名 (`CommitField`)。システム名はヘッダーに出す名前で、空のときは対象システムの名前を出す (placeholder にも出す)。空にした項目はモデルから消える。閲覧専用では変えられない。
  - **ナビの作り方**: 「サイトマップから作る」(`navigationFromSitemap`。AI 不要) は、画面を、その画面を使う操作の業務ごとにグループ化する (業務の並び順、画面は左の木の順。複数の業務に使われる画面は先に出た業務)。ホームは「ホーム」グループの先頭 (ホームが無ければトップページ)。トップページは未ログインの画面なので、ホームがあるときはメニューに入れず、サインインも入れない。業務に入らない画面は最後の「その他」。「AI で考える」(`ai/designNav.ts`。6.2) は一回きりの生成。既にナビがあるときはどちらも置き換えの確認ダイアログ (danger) を出す。
- **画面** (`design:screen`。`packages/ui/src/components/design/Screen*.tsx`・`BindingPicker.tsx`・`screenForm.ts`・`viewValidate.ts`・`mokkunDoc.ts` と `ai/designScreen.ts`、`packages/core/src/model/designView.ts`): サイトマップの画面 1 つずつの画面 UI (`DesignScreen.view`。mokkun v2 の `ViewV2` を JSON で持つ) を組み立て、項目と一覧の列をデータベースの列に結ぶ (`bindings`)。
  - **画面構成** (3 列): 左 (`ScreenListPane`) はサイトマップの画面の一覧。名前に、画面 UI のある画面は「UI あり」、無い画面は「UI なし」、入口の画面は「入口」の印を付け、押すと `ui.designScreenId` を選ぶ (画面が無ければ「サイトマップで画面を足してください。」)。中央 (`ScreenBoard`。`React.lazy`。mokkun を使う) は選んだ画面を `MokkunPreview` で描く (ナビゲーションボードのプレビューと同じ文書。遷移で選びも変わる)。何も選んでいなければ案内を出し、画面 UI が mokkun の検証に通らなければ、上に「この画面の問題」(`buildMokkunSchema` の `viewErrors`) を出して仮の画面を描く。右 (`ScreenBuilder`。`React.lazy`) が画面の組み立て。
  - **画面の組み立て** (右): 一番上に画面の名前 (見出し) と、その下に「画面の目的」(`goal` の `CommitField`。placeholder は分析の画面の説明か画面名。空にすると項目ごと消す。フォーム / YAML のどちらの編集でも出す。画面 UI が無い画面では代わりに「画面の目的 (分析の説明)」のラベルつきで分析の説明を読み取りで出し、無ければ出さない)。mokkun は view の `goal` (必須) を見出しの上 (`dads-heading__shoulder`) に必ず描くので、プレビューでは `mokkunCss()` の末尾の CSS で隠す (goal は画面には出さず、ここで編集する)。その下に「レイアウト」の select (`setDesignScreenShell`。「設計のレイアウトに従う (shell / plain のどちらか)」と、ラベルの表 `SHELL_LABELS` (sitemap.ts。「ヘッダー + グローバルナビ + パンくず (shell)」「枠なし (plain)」。サイトマップのプロパティは短い呼び名 `SHELL_SHORT_LABELS` で「設計に従う (枠なし)」「枠なし (上書き)」のように出す)。画面 UI (`view`) が無い画面でも設定できる。閲覧専用では無効)。その下に「この画面が判断する条件」(`screenConditions`。条件名と根拠の操作名を読み取りで並べる。条件で変わる表示 (`visibleWhen` など) の材料。条件が無ければ出さない)。YAML で編集中に、検証を通らない書きかけがある間に目的欄を確定し、あとで YAML を確定すると、YAML の goal が勝つ (YAML は下書きを優先する作りのため)。次に「AI で作る」と、フォームと YAML の切り替え (「YAML で編集」。コンポーネントの state で、store には持たない)。画面 UI が無い画面には「画面 UI を作る」(画面の名前と分析の説明を目的にした、空の入力セクション 1 つ) を出す。下に「画面 UI を消す」(確認あり。`view` と `bindings` を消す)。閲覧専用では読み取りだけ (入力・ボタン・AI を無効にする)。編集の 1 回 (CommitField の確定・select の変更・ボタン) は、最新の `view` と `bindings` の写しを書き換えて `setDesignScreenView` で 1 回の dispatch (1 件の履歴) で置く。`view` に無い項目の対応は置くときに外す (項目や列を消す・YAML で名前を変えたとき)。
  - **フォームの編集** (既定): 「画面の基本」は `layout` (stack / tabs / sectioned) だけ (`goal` は右のペインの上、画面の名前の下で編集する)。「セクション」は一覧 (見出し `title`・種類 `kind` (form / list / readonly / summary)・列数 `columns` (1〜3)・注記 `note`、↑↓・×、「＋セクション」)。セクションの id は自動 (`section1` …)。`form` / `readonly` / `summary` は項目 (`fields`) の一覧で、識別子 `item`・ラベル `label`・例 `example` (mokkun の `FieldV2.example`。「例: …」とサポートテキストに出る。空にすると項目ごと消す。一覧の列には無い)・部品 `component` (mokkun の部品 19 種)・必須・読み取り専用・列の対応・↑↓×、「＋項目」。`list` は `list.columns` (id・見出し・型 (text / status / date / number)・遷移先 `to` (画面の select)・列の対応・↑↓×。最後の 1 列は消せない: mokkun は列を 1 つ以上要る) と、検索 `search`・行の選択 `selection`・1 ページの行数 `paging.pageSize`。「操作」は主の操作 `primaryAction` と補助の操作 `secondaryActions` (文言・種類 (submit / navigate / custom / reset)・遷移先・見た目 (primary / secondary / tertiary / danger))。セクションの種類を list にすると `fields` を消し (項目があれば確認する)、list 以外に戻すと `list` を消す。列の対応の対象も `kind` で決まる (`viewBindingSlots` は list なら列だけ、ほかは項目だけを数え、遷移の写しの row も `kind` が list のセクションだけを見る)。項目の識別子・列の id を変えるときは、空と重複を断ってトーストで知らせ、条件 (`visibleWhen` / `requiredWhen`) の `item` と代表行 (`list.rows`) のキーも一緒に書き換える。編集は添字ではなく、セクションの id・項目の `item`・列の id・操作の id で対象を探して書き換える。**同時編集では、同じ画面の `view` は 1 つの値なので、同時に直したときは丸ごと後勝ち**になる (編集の途中で並びが変わっても、別のものを直さないための id 検索)。操作は、種類が navigate のとき遷移先の「なし」を出さず、種類を省いた操作は submit として扱う。種類を navigate にしたとき行き先が無ければ最初の画面を入れ、navigate でも submit でもなくなれば `to` を外す。mokkun の検証に通らない状態にもなりうる (列が空など): 保存は止めず、中央に「この画面の問題」を出す。
  - **列の対応**: 方針は「入力の項目 (form) と一覧の列は、列に結ぶ (検索語は検索する列に結ぶ)。readonly / summary の計算した値は結ばなくてよい」。項目と一覧の列を、設計が使うデータベース (`effectiveDatabaseIds`) の列に結ぶ。3 つの select (データベース → テーブル → 列。他のテーブルを指す関連の列は選択肢に出さない) を順に選ぶと、3 つ揃った時点で `bindings` に入る。データベースを「列の対応: なし」にすると外れる。キーは `bindings[].item`: 項目は `fields[].item`、一覧の列は `<セクションの id>.<列の id>` (`columnBindingKey`)。項目や列の名前を変えると対応のキーも付いてくる (変え先に対応があれば元を捨てる)。いまの対応が無いデータベース・テーブル・列を指していれば、その旨の選択肢を出す。
  - **YAML で編集**: `view` を YAML (`js-yaml` の `dump`。JSON_SCHEMA で読み書きして、日付のような文字列が日付型にならないようにする) で textarea に出す。blur か Cmd+Enter で読み、`parseV2Document` に通ったときだけ保存する (`view` 単体なので、`{ mokkun: 2, app: { name }, views: { <画面の id>: view, <ほかの画面の id>: 仮の view } }` に包んで検証する: 遷移先 `to` が設計のほかの画面を指せるように。`title` と `goal` が無ければ画面の名前と説明で補って検証する)。読んだあと検証の前に、節の数 (5 万) と深さ (64) と使えないキーを上限つきで数え、超えたら「大きすぎます」などで断る (YAML のエイリアスで小さな入力が膨らむのを防ぐ。`setDesignScreenView` も同じ上限で断る)。通らなければ理由 (YAML が読めない・キーと値の形でない・上限・mokkun のエラー) を下に出し、保存せずに下書きを残す。下書きは DslEditor と同じ扱い: 入力中は外の更新 (同時編集) に追従せず、画面を離れるときに検証に通れば確定し、通らなければ捨てる。別のファイルを開いたあとは (文書の世代 `docSeq` が変わったので) 書かない。`bindings` は YAML に含めない (フォームで付ける)。保存するときは `view` に無くなった項目の対応を外し、外した件数をトーストで知らせる。
  - **AI で作る** (`ai/designScreen.ts`。`designData.ts`・`designNav.ts` と同じ流儀の一回きりの生成): 渡すのは、画面 (名前・説明・入口か・使う操作とその作業・業務・使う情報。操作ごとに、情報を書く (`command`) か読むだけ (`query`) かと、ドメインモデルで決めたコマンドの意図の名前。読むだけなら検索条件と一覧、書くなら入力と送信を既定にし、意図の名前を送信のボタンの文言にする)、使うデータベースのテーブルと列 (テーブルが表す情報の名前つき。他のテーブルへの関連の列は除く)、この画面からの遷移 (遷移先の画面の id と名前・きっかけ・文言)、ナビゲーションの有無、mokkun v2 の形式の要点 (セクションの `kind`・`component` の一覧・list と action の形・遷移の書き方。JSON Schema 全体は渡さない)。返させるのは `submit_screen` の `{ view, bindings: [{ item, databaseId, table, column }] }` (文章で JSON を返したときも読む)。`title` は画面の名前にそろえる。`view` は `parseV2Document` で調べ (遷移先 `to` は設計の画面の id だけ許す)、エラーがあれば理由を返して 1 回だけ出し直させ、まだ通らなければ失敗のトースト (画面は変えない)。`bindings` は、使うデータベースに無いデータベース・テーブル・列、`view` に無い項目、重複を捨てる (`databaseId` が無くても、使うデータベースが 1 つなら補う)。捨てた数はトーストで伝える。画面に `view` か `bindings` が既にあれば置き換えの確認を出し (空なら確認なし)、キーが無い・閲覧専用ならボタンを無効にして「AI の設定」を案内する。
  - **遷移の写し方** (`buildMokkunSchema`): 画面 UI を持つ画面は、その中身をそのまま使い (`title` は画面名)、サイトマップの遷移 (`via` が `nav` 以外) を次のように写す。**view 自身が同じ遷移先の `to` (主・補助の操作・セクションの操作・一覧の行/一括の操作と列・項目) を持っていれば足さない**。`afterSubmit` (補助の操作の `navigate` にはしない。最初の 1 つだけ写し、残りは捨てる): 主の操作が `submit` で `to` が無ければ、その `to` にする。画面 UI の無い仮の画面は、`submit` の主の操作 (id は遷移の id、label は遷移の文言、無ければ組み込みのサインインは「サインイン」、ほかは「送信」) を持たせて `to` に写す。画面 UI はあるが主の操作が無い・`submit` でない・すでに `to` があるときは何も足さない (設計の検証の警告 `transitionViaUndecided` とは別で、検証は変えない)。`row`: `list` セクションの最初の列に `to` が無ければ、その `to` にする (最初の 1 つだけ)。当てはまらない `row` と、`button`・きっかけ未定は、補助の操作の `navigate` として足す (操作の id が重なれば `_2` を付ける)。きっかけが `nav` の遷移はメニューで行くので足さない。サイトマップから外された画面を指す `to` は、プレビューの文書を作るときに外す (遷移の操作は丸ごと、ほかは `to` だけ。保存した画面 UI は変えない)。
  - **ロール**: 付けない (`app.roles` も画面の `role` も導かない。mokkun の v2 では `view.role` は描画に使われず、検証が厳しくなるだけなので。将来、描画のオプションで切り替える)。view 自身が `role` を持っていればそのまま使う。

- **データ** (`design:data`。`packages/core/src/model/prisma.ts`・`prismaCache.ts`・`prismaEdit.ts`・`designData.ts` と `packages/ui/src/components/design/Data*.tsx`・`dataDiagramFlow.ts`・`DslEditor.tsx`): データベースの DSL を図かテキストで書き、テーブルが表す情報を結ぶ。左のデータベースとテーブルの一覧、中央の図 (ER 図) か DSL のエディタ、右のテーブルのプロパティの 3 列。データベースは設計をまたいで共有する。
  - **画面構成**: 左 (`DataLeftPane`) は「データベース」の一覧。名前、この設計で使うかのチェックボックス (`designs[].databaseIds`)、選んだデータベースの強調 (`ui.designDatabaseId`)、「＋データベース」(名前を入れて追加)、選んだデータベースの名前変更と削除。その下に、選んだデータベースの DSL から読めたテーブル (model) の名前と、対応する情報の数 (選ぶと `ui.designTableName`)。対応はあるのに DSL に無いテーブルは薄く「DSL にありません」と出す。削除は、DSL が空でなく、または情報の対応・画面の項目の対応 (`bindings`) で参照されていれば、確認ダイアログ (danger) に消えるものと使っている設計の名前を並べる。空なら確認しない。中央 (`DslEditor`) は、上の「図」「テキスト」の切り替えと「情報から作る (AI)」「雛形を足す」、その下に図 (下の「図」) か、テキストの monospace の textarea と、下の解析エラーの一覧 (`行:列 メッセージ`。押すとその行にカーソルを移す)。テキストの入力中は下書きで、blur か Cmd/Ctrl+Enter で `setDatabaseDsl` する (下書きが無いときだけ外の値に追従し、同時編集の更新で書きかけを壊さない。ほかへ移るときも確定する)。右 (`DataProperties`) は、選んだテーブルの名前 (`@@map` があれば添える)、列の一覧 (名前と型・`?` / `[]`・`@id` `@unique` `@default` `@relation` の要約)、「表す情報」のチェックボックス (対象システムが使う情報を先に、ほかを「その他の情報」として折りたたむ。チェックで `setTableInformation`)。何も選んでいないときはデータベースの概要 (テーブル数、使っている設計) と、システムが使う情報ごとの対応するテーブル (無ければ赤く「未対応」)。閲覧専用では読み取り。選んだデータベース・テーブルは保存せず、履歴に積まない。モード・対象のシステムが変わると消え、データベースが無くなると既定の規則で使われるデータベースか先頭に代わり、DSL にも対応にも無くなったテーブルの選択は消える (`reconcileUi`)。
  - **図とテキスト**: 中央の上の「図」「テキスト」で見せ方を切り替える (既定は図。選んだ方を localStorage の `untie.design.dataView` に覚える)。保存する値は DSL の文字列だけなので、図の操作も DSL を書き換え、どちらで直してもいつでも行き来できる。テキストの書きかけは、図へ移るときに確定する (確定できなければテキストのまま)。
  - **図** (`DataDiagram`。React Flow): テーブル (model) を、見出しのテーブル名 (`@@map` があれば添える) と列の行 (`PK` / `FK` / `UQ` の印・名前・型) のノードに、enum を値の一覧のノード (見るだけ) に描く。外部キーの列 (右の点) → 参照先の列 (左の点) を線にする。関連のフィールド (型がテーブル) は薄い斜体の行。ノードは動かせるが、位置はモデルに保存せず、ページを開いている間だけデータベースごとに覚える (`dataDiagramFlow.ts`。初めは格子に並べ、並べた位置も覚えるので、テーブルが増えても今のノードは動かない。「並べ直す」で捨てる)。操作: 「＋テーブル」(`Table1` … の id だけの model を、今あるノードの右に空けて置いてそこへ表示を寄せ、名前の入力を開く)、見出しのダブルクリックか ✎ で名前を変える、× で消す (確認あり)、ノードの「＋列」(`column1` … の `String` の列を足して編集を開く)、列の行を押すと、その下に編集 (名前・型 (スカラー型と enum)・主キー・一意・NULL 可・リスト・列を消す) が開く。列の右の点から参照する列の左の点へ線を引くと関連を足し、線を押すと右上に「関連を消す」が出る (関連の列の編集からも消せる)。テーブルを押すと右のペインにそのテーブルが出る。DSL に解析エラーがあれば、読めたところだけ描いて編集はできず、テキストで直すよう案内する。閲覧専用と「情報から作る (AI)」の生成中は見るだけで、開いていた列の編集・名前の入力・選んだ線も閉じる (生成が終わると DSL ごと置き換わり、その間の編集は消えるため)。
  - **図の操作の DSL の書き換え** (`applyPrismaEdit(dsl, edit)`。純粋。`prismaEdit.ts`): 解析エラーのある DSL は書き換えない。触った行のほかは書式とコメントを残す (書き換えるフィールドの行は字下げと行末のコメントを残して 1 行を書き直す。1 行で書いた model は、触るときに 1 行 1 フィールドへ展開する)。テーブルの追加は末尾に `model X {\n  id String @id\n}`、名前の変更は見出しと型として参照するフィールドを直す。テーブルの削除は、ブロックと直前のコメント行、ほかのテーブルからの関連のフィールドと、その関連だけに使っていた外部キーの列を消す (ほかの関連や `@@id`・`@@unique` などの一覧に使う列は残す)。列の追加は最初の `@@` の前 (無ければ `}` の前) に同じ字下げで足す (型がテーブルの列は足せない。関連は線で作る)。列の変更は名前・型・`?`・`[]`・`@id`・`@unique` (`?` と `[]` は同時に付けない。主キー (`@@id` の構成列も) は NULL 可にできない。関連の列は型を変えられない。関連に外部キーか参照先として使う列は、型を変えたりリストにしたりできない (先に線を消す))。列の名前を変えると、自分の `@relation(fields: [...])`・`@@id` などの一覧・ほかのテーブルからの `references: [...]` も合わせる。列を消すと、それを外部キーに使う関連と、それを参照先 (`references`) にするほかのテーブルからの関連 (と対) も消す。`@@id`・`@@unique` などの一覧に使う列は消せない (テキストで一覧から外す)。関連の追加 (`addRelation`) は、型が同じ値の列どうしだけ結び、外部キーの側に `<名前> <相手>(?) @relation(fields: [fk], references: [ref])` (名前は `xxxId` なら `xxx`、ほかは相手のテーブル名の先頭を小文字に。外部キーが NULL 可なら `?`)、相手側に対 (外部キーが一意か主キーなら `<自分>?` の 1 対 1、ほかは `<自分>[]` の 1 対多) を足す。同じ 2 つのテーブルの間に関連が既にあるときと、自分への関連は `"<テーブル>_<外部キー>"` の名前を付ける。関連の削除は両側のフィールドを消し、外部キーの列は残す。

    3. `information` 操作が扱う情報が決まっている: このシステムの操作のすべてに、扱う情報 (`usecaseInformation`) がある。
    4. `origins` 情報と出来事の出どころが決まっている: このシステムが使う情報のすべてに、保存する操作 (`access` が `write` か省略。ほかのシステム・帳票の操作でもよい) がある。このシステムの操作のきっかけのイベントには、起こす操作・システム (`usecaseEvent`・`systemEvent`) か、発生タイミングがある。
    5. `rules` 条件と区分の中身が決まっている: このシステムの操作が判断する条件に、説明か、区分・状態との結びつき (`conditionVariation`・`conditionState`) がある。その条件と、扱う情報に結んだバリエーションに、値がある。
    6. `states` 状態の移り変わりがつながっている: このシステムの操作が前提にしている状態 (`stateUsecase`) に、その状態になる操作 (`usecaseState`。どのシステムのものでも) がある。
    7. `flow` 業務の流れが決まっている: `sequenceGaps` が空 (条件で流れが変わるときの中身・作業の担当・操作の対象)。
    8. `screens` 画面がそろっている: 設計がある。このシステムの操作が使う画面がサイトマップにある。画面 UI がある (画面ごとに数える)。項目の対応が、ある列を指している (設計の検証の `bindingInvalid`・`bindingUnmapped`)。
    9. `navigation` 画面の行き来が決まっている: 設計の検証の `transitionViaUndecided`・`screenUnreachable` が無い。
    10. `data` データの置き場所が決まっている: 設計がある。設計の検証の `noDatabase`・`informationUnmapped`・`tableMissing`・`dslError` が無い。このシステムが使う情報のテーブルが、ひな形のままでない (名前が `Table` + 数字でない・id のほかに列がある)。
  - **UI**: 設計モードの検証パネルの先頭に「実装を始める準備」を出す (`ReadinessSection`)。そろった条件の数と、残りの件数。条件ごとに、そろっていれば ✓、残っていれば件数を出し、開くと、なぜ要るか (`hint`) と残りの行が出る。行を押すと、決めるところへ移る (`revealReadinessItem`): 分析の要素 → その要素を直せる固定ボード、業務の流れ → シーケンス図でその業務、設計の検証と同じもの → 設計の検証の行と同じところ、ほか → 設計ボード。検証パネルとほかの入口が同じ結果を使うよう、`cachedReadiness` で使い回す。
- **対象システムが消えたとき**: 同時編集で他の人が消した場合も含め、`reconcileUi` が分析モード (`analysis:issues`) に戻し、対象を未定にする。
- **削除の連鎖と確認**: system・screen・information を消すと設計データも一緒に消える (4.0)。プロパティ欄の削除ボタンと、画面の所属 (システム) の変更は、`designReferences` が空でなければ確認ダイアログ (danger) に「○○を削除すると、次の設計データも一緒に消えます」と要約の一覧を出し、確認してから消す。空なら今までどおり確認しない。AI の `remove_element` は確認なしで消し、結果に消えた設計データの要約 (`removedDesign`) を含める。
- **同時編集の awareness**: `boardId` は文字列のまま共有するので、設計ボードの id が入ってもそのまま写る。

## 6. 状態管理と操作

- zustand + immer の単一ストア。`model` (UntieModel) と `history` (undo/redo のスタック)、`ui` (現在のボード、選択、パネルの開閉) を持つ。
- モデルを変える操作はすべて `commands` (純粋関数 `(model, payload) => model`) として `packages/core/src/model/commands.ts` に置き、ストアはそれを呼んで履歴に積む。コマンドは Vitest で直接テストする。
- 履歴はモデルのスナップショット (immer の構造共有で安価) を最大 100 件持つ。UI の状態は履歴に入れない。
- ノードのドラッグ中は座標をストアの一時状態に反映し、ドラッグ終了時に 1 件の履歴として確定する。名前や説明の入力は、入力欄からフォーカスが外れたとき (または 500 ms 入力が止まったとき) に 1 件として確定する (IME の変換中は確定しない)。ドラッグ中の Undo / Redo は無視する。
- 要素削除は、関係・ボード上のノード・課題の対象・(業務なら) BUC をまとめて消す 1 件の履歴。

主なコマンド:

| コマンド | 内容 |
| --- | --- |
| `addElement(kind, name, boardId?, position?)` | 要素を作る。業務なら既定 BUC も作る。boardId があればそのボードに置く |
| `updateElement(id, patch)` | 名前・説明・種類固有の項目を変える |
| `removeElement(id)` | 要素と付随するものを消す |
| `moveActivity(activityId, bucId \| null)` | アクティビティの所属を変える |
| `moveBuc(bucId, businessId)` | BUC の業務を変える |
| `moveToContext(elementId, contextId \| null)` | 情報・状態・条件・バリエーションのコンテキストを変える (状態はグループごと) |
| `addRelation(sourceId, targetId)` | 両端から種類を決めて関係を作る。不可なら失敗を返す |
| `removeRelation(id)` | 関係を消す |
| `addBoard(name)` / `renameBoard(id, name)` / `removeBoard(id)` | ボードの追加・名前変更・削除。最後の 1 枚は削除できない。削除してもボード上の要素は残る |
| `placeOnBoard(boardId, elementId, position)` | 要素をボードに置く |
| `removeFromBoard(boardId, elementId)` | ボードから外す |
| `moveNode(boardId, elementId, position, size?)` | 座標・サイズを変える |
| `setIssueTargets(issueId, targetIds)` | 課題の対象を変える |
| `clearAll()` | 全て消す |

### 6.1 保存・読み込み

- モデルをそのまま JSON (2 スペースで整形) で保存する。拡張子は `.json`。ボードの配置も含む。UI の状態 (選択・開いているボード・絞り込み) は保存しない。
- 読み込むときは、古い版のモデルの形式なら現行へ変換してから (`loadModelJson()`。4 章)、JSON Schema の検証と参照整合性の検査 (`validateModel()`) を通す。変換したときは「古い形式 … から … に変換しました。保存すると新しい形式で書き出します」と知らせる。クラウド版の取り込み (`POST /api/files` の `{ model }`) と、サーバーに古い形式で残っている中身の書き出しも同じく変換する。通らなければ理由を最大 3 件出して、今のモデルを残す。読み込むと履歴を捨て、作業の固定ボードを開く。
- 保存すると保存先を覚え、次からは同じファイルに上書きする。「別名で保存」は保存先を選び直す。保存するときは入力中の名前・説明を先に確定させる。
- 保存していない変更の判定は、最後に保存・読み込みしたときのモデルと今のモデルが同じ参照かで行う (immer の構造共有なので、Undo で保存時点に戻れば変更なしになる)。サンプルは一度も保存していなければ、編集したときだけ変更ありとする。
- 保存していない変更があるとき、「開く」「最近開いたファイル」とウィンドウを閉じる前に確かめる。
- 「最近開いたファイル」は、開いた・保存したファイルを新しい順に最大 5 件覚える (同じファイルは先頭へ移す)。項目にフォーカスするか、マウスを載せるとサブメニューが開き、選ぶとそのファイルを開く (→ でサブメニューへ、← で戻る)。読めなかったファイル (消えた・動かしたなど) は一覧から外す。「一覧を消去」で空にできる。デスクトップアプリではパスを localStorage に、ブラウザでは File System Access API のハンドルを IndexedDB に置く。ブラウザでは開くときに読み書きの許可を求め直すことがある。File System Access API の無いブラウザでは開き直せないので、項目を使えなくする。
- 「新規作成」は空のモデル (空の自由ボード「ボード 1」だけ) を、まだ保存していないモデルとして開く。履歴を捨て、作業の固定ボードを開く。手を付けるまでは保存していない変更なしとして扱う。保存していない変更があれば、先に確認ダイアログで「保存して新規作成」「保存せずに新規作成」「キャンセル」を選ばせる。保存を選んで保存先の選択を取り消したり保存に失敗したりしたら、今のモデルを残す。
- **ドメインモデルの書き出し (distill-ddd)**: 「ファイル」メニューの「ドメインモデルを書き出す (distill-ddd)…」(保存したコンテキストがあるときだけ出す) と、コンテキストマップのツールバーから、ドメインモデル (4.6) を distill-ddd (`/ddd` スキル) の成果物の形式で書き出す (`exportDomainDocs(model, { today })`。`packages/core/src/model/domainExport.ts`。純粋)。書き出すのは `event-storming.md`・`bounded-contexts.md`・`context-map.md`・`aggregates.md`・`domain-events.md`・`glossary.md` と `.ddd-session.json` の 7 つで、リポジトリの `docs/domain/` に置く。
  - distill-ddd の `scripts/diagrams.py`・`build_site.py` は md を正規表現で読むので、読まれる箇所の書式を守る: コンテキストは `### 名前 (Core|Supporting|Generic)`、関係は最初の表 (ヘッダに `Upstream`・`Downstream`。種類は英語の綴り)、集約は `### 名前 (Bounded Context: コンテキスト名)` と `**操作**:` の下の `` - `command()`: 説明 → 発行: `Event` ``、イベントは `#### 名前`・`- **発生元 Aggregate**: 集約の名前`・`- **Consumer**: コンテキストの名前`、`## Event Flow (コンテキスト間)` の下の `A --{Event}--> B`、用語集は `## コンテキスト名` の下の `| 用語 | 英語 | 定義 |` の表。名前は、集約・イベントは英語名 (無ければ日本語の名前)、コンテキストは日本語の名前。括弧・縦線・改行など書式を壊す文字は置き換える (名前は `( ) / , 、 { } #` を、本文は `|` `*` `` ` `` と改行を全角などにする。説明や不変条件に `**操作**:` のような文字列があっても、節の区切りと読まれないようにするため)。
  - コマンドとイベントは、保存したものに、分析から導いた候補 (実装するシステムごとの重ね合わせ。5.7) を足して出す。distill-ddd はコマンド名と発行のイベント名を ASCII の識別子しか読まないので、英語名の無いコマンドは `**英語名の無い操作 (図には出ない)**:` に分けて書く。英語名の無いもの・同じ名前の重なりは、書き出したあとに件数を知らせる (`warnings`)。ポリシーは、イベントの `**ポリシー**` と `event-storming.md` の備考に書く (distill-ddd に専用の節は無い)。
  - `.ddd-session.json` は、Untie が書き出したフェーズ (`storming`・`contexts`・`mapping` (関係を決めていない組が無いとき)・`aggregates`・`events`・`glossary`) だけを `completedPhases` に入れ、`currentPhase` は `discover` にする (コアドメインの理由などは人が決めるので、そこから `/ddd --resume` で続ける)。`mapping` は、コンテキストが 2 つ以上あるときだけ判定する。未決のことは `openQuestions` に入れる。このファイルは distill-ddd が進み具合 (済んだフェーズ・キュー・食い違い) を書くものなので、フォルダに既にあれば上書きせずに残し、その旨を知らせる (`saveTextFiles` の `keep`。zip のときは、いつも入れる)。
  - 保存は `Platform.saveTextFiles(files, { zipName, zipFolder })`: フォルダを選んで、その中にファイルを書く (同じ名前は上書き。Web 版は `showDirectoryPicker`、デスクトップは dialog プラグインのフォルダ選択と `write_model_file`)。フォルダを選べないブラウザでは、`docs/domain/` に入れた zip (`packages/ui/src/io/zip.ts` の圧縮なしの zip) をダウンロードする。
  - 形式の保証: Untie は、サンプル (ネットショップ) の書き出しをスナップショットにしている (`packages/core/src/model/__tests__/__fixtures__/domain-export/`)。distill-ddd は、同じファイルを `scripts/fixtures/untie-export/` に持ち、パーサが読めることを確かめる (`test_untie_export_golden`)。形式を変えたら、両方を差し替える。
- **業務ルールの書き出し (Souther)** (`exportSouther(model, systemId)`・`exportSoutherAll(model)`。`packages/core/src/model/southerExport.ts`。純粋。開発モード): 対象のシステムの操作を、[Souther](https://github.com/souther-lang/souther) のソース (`.sou`) に書き出す。Souther は、業務ルールを `data` と `behavior` で書き、`example` の行をコンパイルのときに評価して、どの組み合わせに行が無いかを測る言語。シーケンス図で決めた代替パターンを、コンパイラが確かめられる形にするために使う。書き出すのは、分析から機械的に導けるところまで。
  - **対応**: 状態 → フィールドの無い `data` (同じグループの状態は 1 つの和 `data グループ = 状態 | 状態`。このシステムの操作が触るグループだけ)。操作 → `behavior` (入力は、前提の状態 (グループごとに 1 つ。複数あれば `状態 | 状態`) と、判断する条件の真偽 (`Bool`)。出力は、次の状態と、条件のときの別の結果)。次の状態が無ければ `操作_完了`、複数のグループにまたがれば `data 操作_結果 = { グループ: 状態, … }` にまとめる。代替パターン (`usecaseCondition` の `alternate`) → `guard … else 操作_条件` (満たすときに別の結果になるなら `guard Bool.not(条件)`、満たさないときなら `guard 条件` と `操作_条件_でない`)。作業・担当・扱う情報・起きる出来事・代替パターンの文は、コメントに書く。
  - **例の行** (`example`): ふだんの流れ (前提の状態の組み合わせごと。12 行まで)、代替パターンごとに 1 行 (その条件だけを反対の側にする)。まだ決まっていないものは、答えを `<?>` (答え待ち) にする: 代替パターンの無い条件 (`alternateUndecided`)、同じグループに次の状態が複数ある操作 (`nextStateUndecided`。どのときにどれになるかが分析に無いので、`let` も書かない)。`SoutherExport` の `open` に、業務の言葉の文で返す。
  - **書かないもの**: 条件の式 (何で判断するか)、情報の項目、不変条件、`>->` の合成 (条件を入力に持つ操作は、合成の 2 段目以降に置けない)。前提の状態も条件も無い操作は、確かめる組み合わせが無いので書き出さない (`skipped`。ファイルの末尾にコメントで並べる)。
  - **名前**: 日本語の名前をそのまま識別子にする (`southerIdentifier`。文字と数字と `_` だけにし、予約語と標準ライブラリの名前には `_` を足す)。`data` と `behavior` は同じ名前を持てないので、重なったら番号を足す。モジュールは `untie.<システムの id>`、ファイルは `<システムの id>.sou`。
  - **UI**: 設計ボード「業務ルール (Souther)」(`design:rules`。`SoutherBoard`。ショートカットは U) に、対象のシステムのソース・数 (操作・例の行・答え待ちの行・書き出していない操作)・まだ決まっていない組み合わせを出す。「書き出す…」(`exportSoutherToFolder`) で、すべてのシステムの分を、選んだフォルダ (Web 版で選べないときは zip) へ書き出す。右のペインは、書き出しの読み方 (`SoutherHelp`)。
  - **形式の保証**: サンプルの書き出しをスナップショットにしている (`packages/core/src/model/__tests__/__fixtures__/souther/<サンプル>/<システム>.sou`)。CI の `souther` ジョブ (`scripts/souther-check.sh`) が、同じファイルを Souther のコンパイラ (`souther examples`。JDK 25。版と配布物の SHA-256 はスクリプトに固定) に通し、コンパイルできること・例の行が成り立つことを確かめる。行の無い組み合わせは報告に出るだけで、失敗にしない。Souther はブラウザでは動かない (コンパイラは JVM の上で動く) ので、アプリの中では実行しない。
- デスクトップアプリでは、ファイル選択と保存先の選択に dialog プラグインを使い、読み書きは Rust のコマンド (`read_model_file` / `write_model_file`) で行う。パスはダイアログで選ばれたもの (と、それを覚えた最近開いたファイル) だけを渡す。ブラウザ (Web 版・開発用) では、File System Access API があれば (Chrome・Edge) `showOpenFilePicker` / `showSaveFilePicker` のハンドルを覚えて同じファイルに上書きする (ストアの `file.path` にはハンドルの代わりに `browser:<番号>` を入れる。ハンドルは最近開いたファイルとして IndexedDB にも残す)。無ければファイル選択とダウンロードで代わりにする。
- **クラウドファイル**はファイルではなくサーバーが正本で、保存の操作は無い (つながっている間は常に反映される)。「JSON に書き出す」で同じ形式 (上のローカルファイルと同じ JSON) の中身を取り出し、「クラウドへ保存」でローカルのモデルをクラウドファイルとして複製する。クラウドファイルにはローカルの履歴 (Undo / Redo)・保存先・最近開いたファイル・「保存していない変更」の判定は無い。つながっていない間に溜めた変更だけが、閉じる前の確認の対象になる。読み込み・書き出しとも `validateModel()` を通す。詳細は collab-design 5 章・8.2。
- Web 版 (ローカル専用) は Cloudflare Pages が `apps/web/dist/` を静的なサイトとして配る (`pnpm web:deploy`。手順は README の「Web 版の配信 (Cloudflare Pages)」)。`apps/web/public/_headers` で CSP を付け、スクリプトは自分のオリジンだけ、通信先は自分のオリジンと各 AI プロバイダーの API だけに絞る。クラウド版は Cloudflare Worker (`apps/server`) が `apps/cloud/dist/` を配り (`pnpm cloud:deploy`)、`apps/server/public/_headers` で同じように絞る (通信先は自分のオリジンの WebSocket を含む)。
- アプリの CSP は eval を許さないので、ajv で実行時にスキーマをコンパイルできない。検証関数は `packages/core/scripts/gen-validator.mjs` で事前に生成し (`packages/core/src/model/schemaValidator.gen.js`)、`pnpm gen:types` で型と一緒に作り直す。CI の `check:types` で生成物がスキーマと一致しているかを検査する。

### 6.2 AI エージェント

**使う AI**: Claude (Anthropic)・Codex (OpenAI)・Gemini (Google) から選ぶ。どれも各社の API をアプリから直接呼ぶ (`packages/ui/src/ai/chat.ts`)。会話の履歴は各社の API の形のまま持ち、モデルを読み書きする道具の定義と実行は共通にする。

| AI | API | 既定のモデル | 備考 |
| --- | --- | --- | --- |
| Claude | Anthropic Messages API (`@anthropic-ai/sdk`、beta) | `claude-opus-5-5` | Opus 5.5・Sonnet 5.5 では、安全のための判定で断られたときに別のモデルで続けるサーバー側のフォールバック (`fallbacks: "default"`) を付ける |
| Codex | OpenAI Responses API (`openai`) | `gpt-5-codex` | |
| Gemini | Gemini API (`@google/genai`) | `gemini-2.5-pro` | |

- モデル名は「AI の設定」で自由に入れられる (候補も出す)。プロバイダーとモデルは端末ごとに覚える (localStorage)。
- **API キー**: プロバイダーごとに「AI の設定」で入れ、OS のキーチェーン (macOS のキーチェーン / Windows の資格情報マネージャー) に保存する (Rust の `keyring` クレート、コマンド `get_secret` / `set_secret` / `delete_secret`。ログインのセッションのトークンも同じキーチェーンに置く)。モデルのファイルには入らない。ブラウザ (Web 版・開発用) ではタブを閉じるまでメモリに持ち、「このブラウザに保存する」を選んだときだけ localStorage (`untie.apiKey.<プロバイダー>`) にも置く。保存済みのキーはチェックを変えるとすぐ置き場所を移し、「消す」で両方から消す。保存するときは前の項目を消してから作り直す (署名の違うアプリが作った項目は上書きしても読めないため)。読み出しに失敗したときは「(未設定)」と区別して「(読み出せません)」と理由を出し、保存し直すよう案内する (AI の会話・プロンプトからの作成でも同じ)。macOS のキーチェーンはアプリの署名で読み出しを許すので、手元で作り直すときは固定の証明書で署名する (`pnpm app:build`、README)。
- アプリの CSP は、各社の API (`api.anthropic.com`・`api.openai.com`・`generativelanguage.googleapis.com`) への接続を足す。デスクトップはサーバーの URL を設定で変えられるので、`connect-src` に `https:`・`wss:` も許している (collab-design 8.4)。API キーはクラウドに置かず、サーバーにも送らない。

**会話 (下のペイン)**: ツールバーの「AI」で開閉する。依頼を書いて Enter で送る (Shift+Enter で改行、変換中は送らない)。

- AI は道具 (`packages/ui/src/ai/tools.ts`) でモデルを読み書きする: `get_model` (要素と関係の一覧。既定 BUC は隠し、業務に直接属する作業は業務を示す)、`add_element`、`update_element` (作業の起点のその他は `trigger_note`。空文字で消す。起点の作業・イベントは `add_relation` で結ぶ)、`set_persona` (アクター・外部アクターのペルソナ。指定した項目だけ変わり、空文字で消す。`it_skill` は `comfortable` / `normal` / `uncomfortable`)、`set_event_timing` (イベントの発生タイミングを置き換える。`type` は `scheduled` / `adhoc`、空文字で消す。定期は `every`・`day`・`hour`・`minute`、どちらも `note`)、`remove_element`、`add_relation`、`set_screen_usecase` (画面を使う操作の入れ替え。別の操作が使う画面への `add_relation` は断られる)、`remove_relation`、`move_activity`、`move_buc`、`set_context`、設計のデータベース用の `list_databases` (id・名前・テーブルと表す情報・DSL の解析エラーの数・使っている設計)・`get_database_dsl` (DSL と解析エラー)・`set_database_dsl` (解析エラーがあっても保存し、結果の `parseErrors` に返す)・`set_table_information`、設計の画面 UI 用の `list_design_screens` (画面の id・名前・システム・画面 UI の有無・対応の数・対応が無い項目の数)・`get_design_screen` (画面の `view`・`bindings`・使う情報・判断する条件 (`conditions`)・この画面からの遷移・使うデータベースのテーブルと列)・`set_design_screen_view` (`view` と `bindings` を置く。`view` を mokkun の `parseV2Document` で調べ、通らなければ失敗にして理由を返す。`bindings` を省くと今のまま。`title` / `goal` が無ければ画面の名前と説明で補って検証し、`view` に無い項目の対応は外して結果の `droppedBindings` に数える。`get_design_screen` のテーブルの列は、関連の列を除く。検証は mokkun を遅延読み込みするので、道具の実行は非同期の `executeToolAsync`)。既存の DDL や Prisma スキーマは利用者に会話へ貼ってもらい、AI が DSL に組み立てる (専用のリバースエンジニアリングは無い)。中身は既存のコマンドを呼ぶだけで、整合性の検査はコマンドに任せる。失敗は理由を AI に返し、AI が直してやり直す。
- 設計モードには、会話とは別の一回きりの生成がある (道具の `submit_*` で結果を提出させ、中身を調べてから置く): データボードの「情報から作る (AI)」(`ai/designData.ts`。5.7 のデータ)、画面ボードの「AI で作る」(`ai/designScreen.ts`。5.7 の画面)、ドメインボードの「AI で下書き」(`ai/designDomain.ts`。5.7 のドメイン)、ナビゲーションボードの「AI で考える」(`ai/designNav.ts`)。後者は、サイトマップの画面の一覧 (名前・説明・入口か・使う操作と作業・業務・遷移。サインインは除く) を渡し、利用者にとって自然なナビゲーションのグループ分け (3〜7 グループ、各 1〜6 項目、短い表示名) を `submit_navigation` で `{ groups: [{ group, items: [{ screenId, label }] }] }` として返させる (文章で JSON を返したときも読む)。存在しない画面の id・サインイン・重複は捨て (捨てた数をお知らせのトーストで伝える)、項目の無いグループも捨てる。名前は上限 (200 文字) で切り詰め、空のグループ名は「(名前なし)」にする。キーが無い・閲覧専用ならボタンを無効にして「AI の設定」を案内し、既にナビがあれば置き換えの確認を出す。
- 1 回の返答の間の編集は 1 件の履歴にまとめる (`beginAgentEdit` / `agentApply` / `endAgentEdit`)。元に戻す (Undo) で AI の変更をまとめて戻せる。
- 発言には、開いているボードと選択中の要素を添える (「これを直して」が通じるように)。
- `get_model` は要素をそのまま返すので、ペルソナとイベントの発生タイミングも含まれる。プロンプトからの作成の `submit_model` は、`actors` / `external_actors` に任意の `persona` (`handle`・`attributes`・`background`・`goals`・`it_skill`・`notes`) を受け付けて反映する (長い文字列は切り詰め、不正な `it_skill` は警告してその項目だけ外し、項目の無い `persona` は黙って飛ばす)。
- 指示 (`packages/ui/src/ai/prompts.ts`) には、要素と画面での呼び名、つながりの決まり、書き方のヒントと同じ粒度の説明を入れる。
- 道具を使った回数と成否を会話に小さく出す。中断できる。プロバイダーやモデルを変えると新しい会話になる。途中でエラーになったら、次の発言では会話を作り直す。

### 6.3 課題の深掘り

課題のプロパティ欄の「AI と深掘りする」で、下のペインを **深掘りモード** にして始める (`packages/ui/src/ai/grill.ts`、`agentStore` の `mode`)。独自のダイアログにしないのは、利用者がボードや課題一覧を見ながら答えられるようにするためと、会話の仕組み (道具ループ・中断・1 回の返答 = 1 件の履歴) をそのまま使うため。

- **進め方**は grill-me (mattpocock/skills の grilling) の方式を、現場担当者が答えられる 4 本の軸に当てはめる。現象 (何が・いつ・どのくらい) → 所在 (どの業務・活動・作業・操作、または登場人物) → 理由 (なぜそこで) → 影響 (誰にどう響く) の順に、前提の揃った問いだけをラウンド (3〜4 問) でまとめて出す。各問いに「➡️ 推奨」の見立てを添え、「はい」で推奨を採る。モデルにある事実 (作業の担当、使う操作など) は利用者に聞かず `get_model` で調べる。開いた問いが無くなったら 4 軸でまとめ、重要度と対象の案を示して確認し、了承後に道具で更新する。
- **渡すもの**: 最初の発言に、課題 (名前・説明・重要度・既にある分析) と、対象ごとの所属 (活動・業務) とつながり (担当・使う操作・扱う情報など) を JSON で入れる。この発言は利用者の発言としては表示しない。残りは `get_model` で読む。
- **道具**は 3 つに絞る: `get_model` (共通)、`update_issue_analysis` (その課題の分析と重要度)、`set_issue_targets` (その課題の対象)。書く道具は深掘り中の課題にだけ効く。要素の追加はできない。所在になる作業などがモデルに無ければ、まとめにその旨を書かせ、通常モードで足してから付ける。
- 1 セッション = 1 課題。開始で会話を作り直し、「深掘りを終える」で通常の会話に戻る (表示は残し、次の発言から新しい会話)。プロバイダーやモデルの切り替えは通常の会話と同じ。会話のログはモデルのファイルには残さない。
- 課題の名前と説明 (原文) は AI に変えさせない。更新されるのは `analysis`・`severity`・`targetIds` だけ。

**プロンプトから作成 (ファイル > プロンプトから作成)**: 初期要望の文章から、新しいモデルを作る (`packages/ui/src/ai/generate.ts`)。RDRA ZeroOne (要望の分析から段階を踏んでモデルを作る進め方) を参考に、指示は自前で書く (参考元のリポジトリにはライセンスの表示が無いので、文面は使わない)。

1. 分析: 初期要望を段階 1〜4 (要望の分析、登場人物、業務と活動、情報・状態・条件・バリエーション) で検討し、箇条書きで出してもらう。画面にそのまま流す。
2. 提出: 段階 5 (作業と操作) まで進め、モデル全体を道具 `submit_model` で出してもらう。下書きは名前で参照する形 (`packages/ui/src/ai/spec.ts`) で、AI には id を作らせない。
3. 組み立てと検査: 下書きを既存のコマンドでモデルに組み立て、スキーマ・参照整合性の検査と、担い手まで辿れるかの検査を通す。見つからない名前や担当の無い作業などがあれば、理由を返して出し直してもらう (2 回まで。それ以降は気づいたことが残っていても受け付ける)。
4. 受け付けたら、新しい (まだ保存していない) モデルとして開き、AI エージェントのペインを開く。作成の会話 (初期要望と、分析・作成結果のまとめ) を引き継ぐので、そのまま「〇〇を足して」と続けられる。

### 6.4 困りごとのヒアリング

アクター・外部アクターのプロパティ欄の「困りごとをヒアリングする」で、下のペインを **ヒアリングモード** にして始める (`packages/ui/src/ai/hearing.ts`、`agentStore` の `mode` が `{ kind: "hearing", actorId, answerer }`)。深掘り (6.3) と同じく、会話の仕組み (道具ループ・中断・1 回の返答 = 1 件の履歴) をそのまま使う。深掘りが「すでにある 1 つの課題」を掘るのに対し、ヒアリングは「1 人の登場人物」から困りごとを聞き出し、複数の課題を作る。

**答え方 (`answerer`)**: 開始のときに選ぶ。

- **人間が聞いて、AI が答える (`persona`、既定)**: AI がそのアクターのペルソナになりきって答え、利用者 (分析する人) が質問する。最初の発話で AI が自己紹介し、担当の業務・作業の流れを自分の言葉で辿りながら、困っていそうなところを仮説として挙げ、「気になるところを聞いてください」と促す。ペルソナが無ければ、アクターの名前と担当から無理のないペルソナを仮に作って名乗り、「このペルソナで保存しますか?」と提案する。了承されたら `set_persona` で保存する (了承前に保存しない)。AI の答えはすべて**仮説**で、現場の事実ではない。そのため課題にするときは、説明の最後に「ペルソナ「○○」へのヒアリングからの仮説」と添えさせる (指示で決めている。道具では強制しない)。
- **AI が聞いて、人間が答える (`self`)**: AI が利用者 (現場の人) に、担当する業務・作業の流れに沿って「困っていること → どの作業・操作で → なぜ → 影響」を聞く。深掘りと同じ流儀で、問いはラウンド (Q1… の番号付き、3〜4 問) でまとめて出し、各問いに「➡️ 推奨」の見立てを添える。1 回の会話で複数の困りごとを扱う。ペルソナが無ければ最初のラウンドにペルソナの要点 (属性・役割・目標・IT の習熟) を 1 問にまとめて入れ、了承されたら `set_persona` で保存する。

**渡すもの**: 最初の発言 (利用者の発言としては表示しない) に、アクター (id・種類・名前・説明)、ペルソナ (無ければ null)、主担当の業務、担当する作業 (所属の業務・活動、説明、使う操作と、操作の対象のシステム・帳票・画面)、既にある課題 (このアクター・主担当の業務・担当する作業・使う操作を対象にしたもの。分析と対象つき) を JSON で入れる。残りは `get_model` で読む。途中でエラーになった会話は、この最初の発言をいまのモデルから作り直して先頭に置き、それまでのやり取りを続ける。

**まとめと課題の登録**: 利用者が「まとめて」と言うか、AgentPane の「まとめる」ボタン (固定の発話「ここまでの困りごとをまとめてください」を送る) を押すと、AI が (役を離れて) 困りごとごとに 名前・説明・分析 4 項目 (現象・所在・理由・影響)・重要度・対象 の案を一覧にして「この内容で課題を登録しますか?」と確認する。既存の課題 (材料の「既にある課題」) に近いものは新規にせず「課題「○○」に追記」として案を出す。**利用者が了承するまで、道具でモデルを変えない**。「まとめる」の応答で役を離れる (「役を離れて」) のは、人間が聞いて、AI が答えるときだけ。
- 対象の規則は既存のとおり: 作業・操作・業務まで特定できればその要素 (具体的な課題)、アクター全体の話ならそのアクター (全体的な課題)。混ぜない。所在の要素がモデルに無ければ、まとめにその旨を書き、要素は作らない (対象は空のまま、所在を分析に書く)。
- 担当者が書いた既存の課題の名前と説明 (原文) は変えない。追記するのは分析と重要度と対象だけ。

**道具**は 5 つに絞る (書く道具の定義は `grill.ts` の `issueWriteTools` を深掘りと共有し、ヒアリングでは `issue_id` を引数で受ける。`set_issue_targets` の実行は共有し、`update_issue_analysis` はヒアリングでは追記になる)。
- `get_model` (共通)
- `set_persona`: このアクターのペルソナだけ (指定した項目だけ変わる。別の id は断る)
- `add_issue`: このヒアリングで見つけた困りごとを新しい課題として登録する。名前・説明・分析 4 項目・`severity`・`target_ids`。**課題の追加 (`addElement`) と分析の設定 (`updateElement`) を 1 つのコマンドにまとめて 1 回の `apply` で行う**ので、どれかが断られたら課題は作られない。対象の混在・重要度の範囲外などは `addElement` / `updateElement` の検査で断られる。課題はボードに置かない。
- `update_issue_analysis` / `set_issue_targets`: `issue_id` の既存の課題への追記。**書ける課題は、材料の「既にある課題」(`hearingMaterial` の `existingIssues`) と、このセッションの `add_issue` で作った課題だけ**で、範囲外は断る (作った課題の id は `agentStore` が持ち、会話を捨てると空になる)。`update_issue_analysis` は**既存の分析を置き換えず**、指定した項目の文を既存の文の後ろに改行で足す (置き換える道具は提供しない。重要度は指定すれば置き換わる)。人間が聞いて、AI が答えるときは、足す文の末尾に「(ペルソナ「(呼び名。無ければアクター名)」の仮説)」を道具が自動で添える (文に「仮説」が含まれていれば添えない)。`set_issue_targets` と `add_issue` の対象は、登場人物ならこのアクターだけ (別のアクター・システム・帳票は断る)。

どの道具も、1 回の返答の間の編集は `beginAgentEdit` / `agentApply` / `endAgentEdit` により 1 件の履歴にまとまる。元に戻す (Undo) で、登録した課題とペルソナの保存をまとめて戻せる。要素の追加は課題以外にはできない。

AgentPane のヘッダーには「ヒアリング: 「店長」(人間が聞いて、AI が答える / AI が聞いて、人間が答える)」を出し、「まとめる」「ヒアリングを終える」のボタンを置く。入力欄の placeholder は答え方に合わせる。1 セッション = 1 アクター。「ヒアリングを終える」で通常の会話に戻る (表示は残し、次の発言から新しい会話)。会話のログはモデルのファイルには残さない。

### 6.5 ドメインモデルの対話

設計モードのドメインボード (5.7) の「AI と決める」から始める。AI が、分析から導いた候補と気づきをもとに問いを出し、設計者と一緒に境界づけられたコンテキスト・集約と不変条件・コマンドとイベントの名前と英語名・ポリシー・関係・用語を決めていく (`packages/ui/src/ai/domainTalk.ts`。会話のモードは `{ kind: "domain"; systemId }`)。進め方は課題の深掘り (6.3) と同じで、前提の揃った問いをラウンドでまとめて (3〜4 問まで) 出し、各問いに見立てを「➡️ 推奨」として添え、了承を得てから道具で書く。

- **決める順**: 気づきの問い (どの集約の状態を変えるのか・1 つの操作を分けるか・イベントが要るか・同じ語が別の意味か) → コンテキストと分類 → 集約と不変条件 → コマンド・イベントの名前と、要るのに無いもの・要らない候補 → コンテキスト間の関係 → 用語と英語名。分析から読み取れる事実は聞かず、判断 (境界・整合の単位・名前・チームの関係) だけを聞く。
- **道具**: 読むのは `get_model` と `get_domain` (`domainForAi`。対象のシステムの、保存したものと候補を重ねた一覧 (5.7 の重ね合わせ)・コンテキスト間のつながり・気づきの問い・検証の結果)。書くのは `save_context`・`save_aggregate`・`save_command`・`save_event` (id があれば変え、無ければ足す。分析の候補は `usecase_id`・`event_id`・`root_information_id` で採用する。集約やコンテキストがまだ候補なら一緒に保存する)、`add_policy`、`set_relation`、`set_term`、`exclude_candidate`、`remove_domain_part`、`add_issue`。
- **分析は変えない**: 書けるのはドメインモデル (`domain`) だけで、要素や関係を変える道具は渡さない。分析の誤りや抜けに気づいたら、利用者に伝えて、了承されたら `add_issue` で課題として残す (対象は業務・作業・操作など)。
- 1 回の返答の間の保存は 1 件の履歴にまとまる (6.2)。AgentPane のヘッダーに「ドメインモデルを決める: 「販売管理システム」」を出し、「対話を終える」で通常の会話に戻る。途中でエラーになったら、最初の発言 (対象のシステムと数) を作り直して、やり取りを引き継ぐ。

## 7. サンプル (架空の業務)

サンプルは 4 つ (ホームの一覧から開く。`packages/core/src/sample/` の `SAMPLES`)。ここでは起動時に読み込む宿泊施設 (`hotel.ts`) を説明し、ネットショップは 7.1、店舗は 7.2、経理業務は 7.3 に書く。実在の施設名・実データは使わない。

- **業務 (5)**: 予約受付、チェックイン、滞在中の対応、チェックアウト、清掃・準備
- **アクター (4)**: 予約担当、フロント担当、清掃担当、支配人
- **外部アクター (2)**: 宿泊客、旅行会社

- **情報 (6)**: 予約 (予約)、宿泊客 (顧客)、部屋・清掃記録 (客室)、料金プラン・請求 (料金)。宿泊管理システム・予約サイト・決済サービスから取得し、宿泊管理システム・会計システム・宿泊者名簿・清掃チェック表に保存する

- **イベントの発生タイミング (0.5.4)**: 宿泊施設の「チェックアウトの日になった」に定期 (毎日 0:05。日付が変わったらその日の予約を拾う)、ネットショップの「入金が確認された」に不定期 (決済サービスから入金の通知 (Webhook) を受けたとき)、店舗の業務の「カード・電子マネーで支払われた」に不定期 (決済端末から決済の結果が届いたとき) を入れている。
- **ペルソナ (0.5.3)**: 店舗の業務のサンプルは、アクター 6 人と外部アクター 2 つにペルソナを入れている。宿泊施設のサンプルも、アクター 4 人と外部アクター 2 つ (宿泊客・旅行会社。来訪の頻度や目的が分かる属性) の全員に入れている (すべて架空。ヒアリング (6.4) を試せる)。

サンプルはテストでスキーマ検証と参照整合性検査を通し、検証のエラーと警告が出ないことを確かめる。

### 7.1 ネットショップの業務 (サンプル)

`packages/core/src/sample/netshop.ts`。架空の雑貨のネットショップ (自社サイトとモールで売り、倉庫から出荷する小さな店)。ホームのサンプルの一覧から開く。構成は宿泊施設と同じで、実在の店・実データは使わない。**モデルの形式 0.2.0 の書き方の見本**で、イベント・「次に」・画面・非機能要件を使い、検証のエラーも警告も出ない。

- **アクター (5)**: 受注担当、倉庫担当、カスタマーサポート、店長、経理担当。**外部アクター (3)**: 購入者、仕入先、配送業者
- **システム (5)・帳票 (2)**: 自社サイトのカート、モールの管理画面、販売管理システム、決済サービス、会計システム / 入荷検品表、返品受付票

## 9. テスト

Vitest で以下を検証する。E2E は省く。

- モデル: id 生成、要素の追加・削除と付随処理 (既定 BUC、関係・ノード・課題対象の掃除)、所属の変更。
- 関係ルール: 表にある組み合わせは引け、ない組み合わせは引けない。重複と自己参照の拒否。無向関係の同一視。
- 検証: スキーマに合わない JSON とエラー内容。参照整合性の各ケース。
- Undo / Redo: 連続操作と履歴上限。
- サンプル: スキーマ検証と参照整合性検査を通る。
- 固定ボード: 各レイヤーの枠の組み立て、絞り込み、枠への追加・既存の紐づけ・外す。
- UI: 要素一覧・固定ボード・プロパティ欄・ツールバーの主要な振る舞い (自由ボードで所属・関係を変えられないことを含む) を Testing Library で確認する。キャンバスは React Flow のノード・エッジへの変換 (座標の相対化を含む) を純粋関数として切り出し、その関数をテストする。
- クラウド版 (詳細は collab-design 11 章): 権限の規則 `can` と API の契約 (`packages/api`)、Y.Doc の往復・合流・修復 (`packages/collab`。`rebuildModel(applyModelDiff(a, b)) ≡ b` をランダムなコマンド列で確かめる)、サーバー (`apps/server`。`@cloudflare/vitest-plugin` で workerd の中に本物の D1 と Durable Object を立て、ログイン・セッション・権限・招待・リンク・ルームの接続と kick・cron を確かめる)、クラウドのストアと接続 (2 つの Y.Doc をつなぐ)、ホーム・共有ダイアログ・招待・リンクの画面、デスクトップのログインと Web の Platform。
- 生成物: `pnpm check:types` が、スキーマから生成した型と検証関数が最新かを確かめる。
- `pnpm test` がルートから全プロジェクトを走らせ、`pnpm typecheck` (`tsc -b`) が全パッケージの型を検査する。

## 10. ビルドと配布

- `pnpm dev` で Web 版 (Vite、5174) を、`pnpm dev:cloud` でクラウド版の画面 (Vite、5173) とサーバー (`wrangler dev`、8787) を同時に動かす。`pnpm tauri dev` でデスクトップアプリ、`pnpm app:build` (手元の証明書で署名) か `pnpm tauri build` で Mac 用 .app / .dmg。
- **Web 版**: Cloudflare Pages (プロジェクト `untie`)。`pnpm web:deploy` か、Pages の Git 連携 (Build command `pnpm --filter @untie/web build`、出力 `apps/web/dist`)。手順は README の「Web 版の配信 (Cloudflare Pages)」。
- **クラウド版とサーバー**: 1 つの Cloudflare Worker (`apps/server`、名前は `untie-cloud`) がクラウド版の画面 (`apps/cloud`) の静的ファイル・API・ログイン・Durable Object を持つ。`pnpm cloud:deploy` が画面を build して `wrangler deploy` する。初回の手順 (D1 の作成、OAuth クライアント、秘密の値、`APP_ORIGIN`) は README の「クラウド版の配信 (Cloudflare Workers)」、設計は collab-design 2.3・9 章。
- GitHub Actions:
  - `ci.yml`: PR と main push で `pnpm check:types`、`pnpm typecheck`、`pnpm test`、`pnpm build` (Web 版・クラウド版・デスクトップのフロントの build と `wrangler deploy --dry-run`)。別のジョブで Linux の `cargo check` (Rust 側がコンパイルできるか)。Tauri の Linux 向けライブラリの取得に時間がかかるので、PR では `apps/desktop/**` か `ci.yml` が変わったときだけ動かし (`changes` ジョブが差分で決める。飛ばしたジョブは成功として扱われる)、main への push では常に動かす。
  - `release.yml`: `v*` タグ push で `tauri-apps/tauri-action` を使い、`macos-latest` (aarch64-apple-darwin) で .dmg、`windows-latest` で .msi と .exe (NSIS) を作り、GitHub Releases に添付する。
- Windows 版は CI でしか作れないため、動作確認は CI の成果物で行う。
- 署名なしなので、README に開き方 (Mac は右クリック → 開く、Windows は SmartScreen の「詳細情報」→「実行」) を書く。
