# Untie PoC 設計書

Untie は、現場担当者が自分の業務を言語化するための業務可視化ツールである。人・作業・情報・ルール・判断をカードにし、図の上で関係を整理する。将来は RDRA モデルに展開して要件定義につなげる。

この PoC では「カードと図で業務要素と関係を編集する体験」を確かめる。モデルは JSON ファイルに保存・読み込みできる。AI エージェント (会話でモデルを直す・初期要望からモデルを作る) を持つ (6.2)。RDRA 出力は対象外だが、データモデルはそれに耐える形にしておく。

その後、ログインしたユーザーがクラウドにファイルを置き、共有し、同時に編集できるようにした。クラウド版 (ユーザー・ファイル管理・権限・ログイン・同時編集・サーバー・モノレポ構成) の設計は [docs/collab-design.md](collab-design.md) にあり、この文書には要点と参照だけを書く。この文書の 2〜4 章 (要素・関係・データモデル) と 6〜7 章 (操作・サンプル) は、ローカルファイルでもクラウドファイルでも同じである。

## 2. 要素 (カード) の種類

17 種。イベント・画面・非機能要件はモデルの形式 0.2.0 で足した (2.4)。イベントストーミングのポリシー・集約は持たない。メモカードは入れず、各要素の説明欄で代用する。

| kind | 表示名 | 役割 | 種類固有の項目 |
| --- | --- | --- | --- |
| `actor` | アクター | 業務を行う社内の人・役割 | なし |
| `externalActor` | 外部アクター | 顧客・取引先など、社外の人や組織 | なし |
| `system` | システム | 情報システム (自社・社外を問わない)。操作の対象・情報の取得元・保存先・イベントの発生元になり、画面と非機能要件を持てる。作業の担当にはならない (0.2.0 から) | なし |
| `ledger` | 帳票 | 紙の台帳・伝票。操作の対象と、情報の取得元・保存先になる | なし |
| `business` | 業務 | 業務のまとまり。ボード上では枠 (グループノード) | なし |
| `buc` | 活動 (BUC) | 業務の中の作業のまとまり (Business Use Case)。任意 | `businessId`、`isDefault` |
| `activity` | 作業 (アクティビティ) | 業務の中の個々の作業 | `bucId` (null 可)、`links` (リンク、任意)、`hours` (時間、任意) |
| `usecase` | 操作 (ユースケース) | システムに期待する振る舞い | `links` (リンク、任意)、`hours` (時間、任意) |
| `context` | コンテキスト | 役割の同じ情報と、関係の深い状態・条件・バリエーションをまとめる親カテゴリ。関係は持たない | なし |
| `information` | 情報 | 業務で扱う情報 | `contextId` (null 可) |
| `state` | 状態 | 情報やモノの状態 | `group` (状態グループ、任意)、`contextId` (null 可) |
| `variation` | バリエーション | 種別・区分と、その値の一覧 | `values: string[]`、`contextId` (null 可) |
| `condition` | 条件 | 判断の条件・ルール | `contextId` (null 可) |
| `issue` | 課題 | 現場で困っていること。自由ボードには置かない | `severity` (1〜5)、`targetIds`、`analysis` (分析、任意) |
| `event` | イベント | 操作の実行やシステムが発生させる出来事 (人の動きは含めない)。操作のきっかけになる | `contextId` (null 可) |
| `screen` | 画面 | システムの画面。操作が使い、情報を扱う | `systemId` (必須。システムだけ) |
| `nfr` | 非機能要件 | システムに求める、機能以外の品質 | `systemId` (必須。システムだけ)、`category` (IPA の 6 分類、任意)、`verification` (検証方法、任意) |

画面の表示名は RDRA の用語と変えている: `buc` は「活動」、`activity` は「作業」、`usecase` は「操作」と出す (現場担当者に通じる言葉にするため)。この設計書とコード・スキーマは RDRA の用語 (BUC・アクティビティ・ユースケース) のまま書く。

全要素に共通: `id` (安定した文字列)、`kind`、`name`、`description` (任意の説明文)。

### 2.1 業務 ⊃ BUC ⊃ アクティビティ

- 業務・BUC・アクティビティ・ユースケースの 4 段をモデルに持つ。BUC は任意。
- 業務を作ると、その業務の **既定 BUC** (`isDefault: true`、名前は業務名と同じ) が自動で 1 つ作られる。既定 BUC はボードにも要素一覧にも出さない。
- アクティビティは `bucId` で BUC を 1 つ指す。業務の枠に直接置いたアクティビティは、その業務の既定 BUC に入る。
- 業務ごとに、作業は「すべて業務に直接 (既定 BUC)」か「すべてどれかの活動 (既定でない BUC)」のどちらかにする (混ぜない)。業務に初めて活動を作ると (活動の固定ボードの「＋活動」)、業務に直接あった作業はその活動へ移る (作成と移動で 1 件の履歴)。プロパティ欄の活動のセレクトは、活動のある業務では「(業務に直接)」を出さない。スキーマとコマンドは混ざったデータも受け付ける (古いファイルや AI の作成のため) が、作業のボードで知らせる。
- BUC を作りたい人は、業務の枠の中に BUC の小枠を作り、アクティビティをそこへドラッグして移す。
- `bucId` が null のアクティビティ (未所属) も許す。現場担当者が業務を決める前に作業を書き出せるようにするため。rdra 出力では未所属を出せないので、出力時に警告する (将来の TODO)。
- 既定 BUC は削除できない。既定でない BUC を削除すると、所属アクティビティは業務の既定 BUC に戻る。業務を削除すると、その BUC は全て消え、所属アクティビティは未所属になる。

### 2.2 担い手と置き場所 (システム・帳票) とコンテキスト

役割で 2 つに分け、種類をこれに合わせる。

| | 作業をする (担い手) | 操作の対象 | 情報を取り出す・残す (置き場所) | イベントを発生させる・画面と非機能要件を持つ |
| --- | --- | --- | --- | --- |
| アクター | ○ | – | – | – |
| 外部アクター | ○ | – | – | – |
| システム | – | ○ | ○ | ○ |
| 帳票 | – | ○ | ○ | – |

- システムは情報システム。自社のものも社外のもの (予約サイト・決済サービスなど) も含む。0.2.0 から作業の担当にはならず、操作の対象 (`usecaseSystem`) として結ぶ。人が担当しない自動の処理は作業にせず、イベントをきっかけにした操作で表す (2.4)。0.1.0 のファイルの「システム → 作業 (担当)」は、開くときにその作業が使う各操作の「対象」へ変換する (システムだけが担当だった作業は担当が空になり、検証で知らせる)。
- 帳票は紙の台帳・伝票。操作の対象と置き場所になる (画面では破線で描く)。紙はイベントも画面も持たないので、システムとは別の種類にした。関係のルールは種類だけで決まる。
- 外部アクターとシステムの線引きは「人か仕組みか」の 1 本にする。社外の人・組織は外部アクター、仕組みは自社・社外を問わずシステム。予約サイトのように両方に読めるものは、契約や電話でやり取りする相手なら外部アクター、データをやり取りする仕組みならシステムとする。自社か社外かの印は持たない (RDRA のシステム境界を描くときに要れば足す)。
- 置き場所と情報は `systemInformation` (取得元) と `informationSystem` (保存先) で結ぶ (システム・帳票の両方)。
- コンテキストは RDRA のコンテキストに合わせる。中心は情報で、役割の同じ情報と、それに関係の深い状態・条件・バリエーションをまとめる。この 4 種類は `contextId` で 1 つを指す (null は未分類)。状態は状態グループごとに属する (グループ内の状態はまとめて移し、既にあるグループに足した状態はそのグループのコンテキストになる)。
- 所属は人が決める。条件やバリエーションは複数のコンテキストにまたがりやすく、どこに入れるかは設計上の判断だから。代わりに、つながりから候補を出す (`packages/core/src/model/contexts.ts`)。直接つながる所属要素 (関連する情報、参照する状態・バリエーションなど) は重み 2、操作を介してつながる情報は重み 1 で数え、いちばん重いコンテキストを候補にする。
- コンテキスト自体はほかの要素と関係を持たない。コンテキストどうしの関係 (結合度) は、所属する要素の関係から導く。コンテキストを削除すると、所属していた要素は未分類になる。

### 2.3 課題

- 独立した要素で、`targetIds` に対象の id を複数持てる (0 件も可)。課題を先に書き出し、あとから対象を付けて紐解けるよう、対象なしで作れる。
- 対象の種類で 2 つの区分に分かれる。区分は保存せず、対象から決める (`issueScope`)。
  - **全体的な課題**: 登場人物 (アクター・外部アクター・システム・帳票) が対象。その登場人物全体にかかわる課題。
  - **具体的な課題**: 業務・作業・操作・画面が対象。特定の業務や操作で起きている課題。
  - 対象がまだ無い課題は **未整理** とする。
- 1 つの課題の対象に、登場人物と業務・作業・操作・画面を混ぜない (コマンドで拒否し、検証でエラーにする)。区分を変えるときは、いまの対象を外してから別の区分の対象を付ける。
- `severity` は 1 (低) 〜 5 (高) の整数。
- `analysis` (任意) は深掘りの結果。現象 (`phenomenon`)・所在 (`location`)・理由 (`cause`)・影響 (`impact`) の 4 項目で、すべて任意の文字列。担当者が書いた `description` (原文) は分析で上書きせず、突き止めた内容をここに分けて持つ。AI との深掘り (6.3) で埋まるが、プロパティ欄で手でも書ける。項目ごとに変えられ、空文字で項目が消え、全部消えれば `analysis` 自体が消える。
- ボードには置かない。課題一覧パネル (5.5) で作り、区分ごとに見る。対象カードにはバッジ (件数と最高重要度) を出す。
- 対象要素を削除すると、その id は `targetIds` から外れる。課題自体は残る。

### 2.4 イベント・画面・非機能要件 (0.2.0)

- **イベント**: 操作の実行 (`usecaseEvent`) やシステム (`systemEvent`) が発生させる出来事で、操作のきっかけ (`eventUsecase`) になる。人の動き (「お客様が電話した」など) は含めない。名前は「予約が確定した」のような過去の形で書く。コンテキストに任意で属する。
- **操作の順番**: 作業の中の操作は「次に」(`usecaseNext`) でつなぐ。枝分かれ・合流・輪を許し、自分自身へは結べない。順番は作業ではなく操作どうしの関係で持つので、同じ操作を使う作業が複数あっても、作業の中の並びはその作業が使う操作どうしの「次に」だけで組み立てる。
- **操作の対象は 1 つだけ** (0.3.0): 1 つの操作が持てるのは、対象 (システム・帳票。`usecaseSystem`) か画面 (`usecaseScreen`) のどちらか 1 本まで (0 本も可)。コマンドは 2 本目を「操作の対象は 1 つだけです。今の対象を外してから結んでください」と断り、検証は 2 本以上をエラーにする。プロパティ欄では「対象」の選択欄 (システム・帳票・画面) で選び、選ぶと前の対象と入れ替わる (`setUsecaseTarget`)。0.2.0 のファイルで 2 本以上あるものは、開くときに画面を優先し、同じ種類では先にあるものを残して、外した本数を知らせる。同時編集で 2 本になったときは、サーバーの修復 (`repairModel`) が同じ規則で 1 本にする。
- **自動の処理**: 人が担当しない処理は作業にせず、「イベント → 操作 (対象: システム) → …」で表す。きっかけのイベントから辿れれば、作業に属さなくてよい。
- **画面**: 1 つのシステムに属する (`systemId`)。操作が使い (`usecaseScreen`)、情報を扱う (`screenInformation`)。画面を結んだ操作は、その画面のシステムを対象とみなす。システムを消すと、属する画面も消える。帳票は画面を持たない。
- **非機能要件**: 1 つのシステムに属する (`systemId`)。名前・分類 (IPA 非機能要求グレードの大項目: 可用性・性能・拡張性・運用・保守性・移行性・セキュリティ・システム環境・エコロジー。任意)・説明・検証方法 (任意) を持つ。求める人 (アクター・外部アクター) は `actorNfr` で結ぶ。システムを消すと一緒に消える。

## 3. 関係 (線) の種類

関係は RDRA に沿った型付きのみ。両端の要素の種類から関係の種類が自動で決まり、表にない組み合わせは引けない。自由な線はない。

| relation kind | 始点 → 終点 | 意味 (RDRA での対応) |
| --- | --- | --- |
| `actorBusiness` | アクター → 業務 | 業務の主担当 (`business.main_actor`) |
| `actorActivity` | アクター / 外部アクター → アクティビティ | 作業を行う担い手 (`activity.used_by`)。0.2.0 からシステムは担当にならない |
| `activityUsecase` | アクティビティ → ユースケース | 作業で使うユースケース (`activity.usecase`) |
| `usecaseInformation` | ユースケース → 情報 | 扱う情報 (`usecase.information`) |
| `usecaseCondition` | ユースケース → 条件 | 判断に使う条件 (`usecase.condition`) |
| `informationRelated` | 情報 ↔ 情報 | 関連する情報 (`information.related`)。無向 |
| `informationVariation` | 情報 → バリエーション | 情報の種別 (`information.variation`) |
| `systemInformation` | システム / 帳票 → 情報 | 情報の取得元 |
| `informationSystem` | 情報 → システム / 帳票 | 情報の保存先 |
| `conditionVariation` | 条件 → バリエーション | 条件が参照する種別 (`condition.variation`) |
| `conditionState` | 条件 → 状態 | 条件が参照する状態 (`condition.state`) |
| `stateUsecase` | 状態 → ユースケース | この状態で実行できるユースケース |
| `usecaseState` | ユースケース → 状態 | 実行後に遷移する次の状態 (`next_state`) |
| `usecaseSystem` | ユースケース → システム / 帳票 | 操作の対象 (0.2.0)。`usecaseScreen` と合わせて 1 つの操作に 1 本まで (0.3.0) |
| `usecaseEvent` | ユースケース → イベント | 操作を実行すると発生するイベント (0.2.0) |
| `systemEvent` | システム → イベント | システムが発生させるイベント (0.2.0) |
| `eventUsecase` | イベント → ユースケース | 操作のきっかけ (0.2.0) |
| `usecaseNext` | ユースケース → ユースケース | 作業の中の次の操作 (0.2.0)。自分自身へは不可 |
| `usecaseScreen` | ユースケース → 画面 | 操作で使う画面 (0.2.0)。`usecaseSystem` と合わせて 1 つの操作に 1 本まで (0.3.0) |
| `screenInformation` | 画面 → 情報 | 画面が扱う情報 (0.2.0) |
| `actorNfr` | アクター / 外部アクター → 非機能要件 | その要件を求める人 (0.2.0) |

ルール:

- 関係は `id`、`kind`、`sourceId`、`targetId` を持つ。`kind` は両端の種類から一意に決まり、保存時も冗長に持つ (スキーマ検証とエクスポートを単純にするため)。
- 同じ `(kind, sourceId, targetId)` の関係は 1 本まで。`informationRelated` は無向なので `(a, b)` と `(b, a)` を同一とみなし、重複を拒否する。
- 自己参照 (`sourceId === targetId`) は不可。
- 線はボードごとではなくモデル全体の関係である。両端がボードに置かれていれば、どのボードでも同じ線が表示される。
- 画面では、`informationRelated` は矢印なし、それ以外は終点に矢印。線の上に関係名の短いラベルを出す (例: 「担当」「使う」「次の状態」)。
- 状態遷移は `stateUsecase` と `usecaseState` の 2 本で表す。1 つのユースケースに前の状態と次の状態がそれぞれ複数ある場合、組み合わせが曖昧になる。rdra 出力の TODO で、3 項関係 (前状態・ユースケース・次状態) への拡張か、全組み合わせとして出力するかを決める。

### 3.1 関係の自動判定

`relationKindFor(sourceKind, targetKind)` が上の表を引き、該当なしなら `null` を返す。React Flow の `isValidConnection` でこの判定を使い、引けない組み合わせはドラッグ中に接続不可として扱う。接続時にすでに同じ関係があればトーストで知らせて何もしない。

## 4. データモデル

スキーマは `schema/untie.schema.json` (JSON Schema 2020-12) に定義し、`json-schema-to-typescript` で `packages/core/src/model/schema.d.ts` を生成する。型とスキーマがずれないよう、CI で生成結果の差分を検査する (json-gantt と同じ方式)。

```
UntieModel
├ version: "0.3.0"           … モデルの形式 (スキーマ) のバージョン。semver の文字列
├ meta: { name, description? }
├ elements: Element[]      … 14 種を kind で判別する
├ relations: Relation[]    … 型付きの関係
└ boards: Board[]
   └ nodes: BoardNode[]    … { elementId, x, y, width?, height? }
```

設計方針:

- **形式のバージョンとマイグレーション**: JSON の `version` にモデルの形式のバージョン (semver。現行は `0.3.0` で、`MODEL_VERSION`) を持つ。変換は 0.1.0 → 0.2.0 (システムの作業の担当を操作の対象へ移す。2.2) と 0.2.0 → 0.3.0 (操作の対象を 1 つにする。2.4) の 2 つ。変換で中身を外したときは、開いたときの知らせに出す。スキーマを変えるときは必ずバージョンを上げ、前の版から変換するマイグレーションを `packages/core/src/model/migrate.ts` の `MIGRATIONS` に足す (手順は AGENTS.md)。ファイルを開く・取り込むときは `loadModelJson()` が、古い版の JSON を順に変換して現行の版にしてから検証する。新しい版の JSON (新しいアプリで作られたもの) は、古いアプリで開いて壊さないよう「Untie を更新してください」と断る。0.1.0 より前のファイルは `version` が整数の `1` で、中身は 0.1.0 と同じなので `"0.1.0"` に読み替える。
- **安定 id**: 要素・関係・ボードは作成時に `kind の短い接頭辞 + ランダム文字列` の id を得る (例 `act_k3f9x2ab`)。名前を変えても id は変わらない。参照は全て id で行う。
- **座標の分離**: 要素は業務データ (`elements`) に、座標はボード (`boards[].nodes`) に持つ。1 モデルに複数ボード、同じ要素を複数ボードに置け、座標はボードごと。
- **座標はボード内の絶対座標**で持つ。React Flow は親ノードの子に相対座標を要求するので、ボードを描画するときに親 (業務・BUC の枠) の座標を引いて相対にし、ドラッグ終了時に足し戻す。親の有無でモデルの座標の意味が変わらないようにするため。
- 業務・BUC の枠は `width`・`height` を持つ。それ以外のカードは省略し、表示側の既定サイズを使う。
- 課題はボードに置けない。既定 BUC もボードに置けない (業務の枠の中に直接アクティビティを置く)。
- 参照整合性 (存在しない id を指さない、`bucId` の BUC・`contextId` のコンテキストが存在する、`targetIds` が 業務/アクティビティ/ユースケース を指す、など) は JSON Schema では表現できないので、`validateModel()` でスキーマ検証に続けて検査する。

### 4.1 ボードの種類

ボードは**固定ボード**と**自由ボード**の 2 種類。

- **固定ボード**: レイヤーごとに 1 枚ずつ、計 12 枚。上位の要素を枠にして、その下に下位の要素を自動で並べる。位置は動かせない。上のレイヤーから順に下のレイヤーを詳細化するための場所で、要素の作成・削除、所属と関係の変更はここで行う。モデルには保存せず、毎回モデルから組み立てる (スキーマは変えない)。id は `fixed:<レイヤー>`。
- **自由ボード**: モデルの `boards`。レイヤーに関係なく要素を置き、位置と大きさを自由に決める。変えられるのは配置 (置く・外す・位置・大きさ) と名前・説明だけで、所属・関係・要素の作成と削除はできない。

### 4.2 固定ボード

| レイヤー | 枠 (上位) | 枠に並ぶもの | 枠との結びつき |
| --- | --- | --- | --- |
| 登場人物 | 「アクター」「外部アクター」「システム」「帳票」 | アクター / 外部アクター / システム / 帳票 | なし |
| 業務 | アクター | 主担当の業務 | 関係 `actorBusiness` |
| BUC | 業務 | BUC (既定 BUC は出さない) | 所属 `businessId` |
| アクティビティ | 活動の無い業務 (業務 (活動なし) の枠) と活動 | アクティビティ | 所属 `bucId` |
| ユースケース | アクティビティ (BUC ごとの段落に分ける) | 使うユースケースと、そのきっかけ・発生するイベント (連鎖の順) | 関係 `activityUsecase` |
| 画面 | システム | 属する画面 | 所属 `systemId` |
| コンテキスト | コンテキスト | 属する情報・条件・状態・バリエーション (この順) | 所属 `contextId` |
| 情報 | コンテキスト | 情報。カードに取得元・保存先のシステム・帳票を出す | 所属 `contextId` |
| 条件 | ユースケース | 判断に使う条件 | 関係 `usecaseCondition` |
| 状態 | 状態グループ (`group`) | 状態 | 属性 `group` |
| バリエーション | 情報 | 種別のバリエーション | 関係 `informationVariation` |
| 非機能要件 | システム | 属する非機能要件 | 所属 `systemId` |

- 関係で結ぶ枠では、同じ要素が複数の枠に出る (例: 複数のアクティビティから使われるユースケース)。どの枠にもつながらない要素は「主担当なし」「アクティビティなし」などの枠にまとめる (中身があるときだけ出す)。アクティビティの「未所属」、情報の「未分類」も同じ。状態の「グループなし」は、新しいグループを始める場所として常に出す。
- 作業のボードは、活動の無い業務には業務の枠 (活動なし) を、活動のある業務には活動の枠だけを出す。活動のある業務に業務直下の作業が残っているときだけ、業務の枠を「活動に移してください」の知らせ付きで出し、その枠では「＋作業」を出さない。
- ユースケースのボードは、アクティビティの枠を所属する BUC ごとの段落に分け、見出しと区切り線を付ける。段落の並びはアクティビティのボードと同じ (業務ごとに既定 BUC → BUC)。アクティビティの無い BUC の段落は出さない。BUC に属さないアクティビティは「未所属」、どのアクティビティにも使われていないユースケースは「アクティビティなし」の段落にまとめる。段落の見出しをクリックすると、その BUC (既定 BUC なら業務) を選ぶ。絞り込みで段落の見出しが一致したときは、その段落の枠をすべて出す。
- ユースケース (操作) のボードでは、アクティビティの枠の中に、きっかけのイベント → ユースケース (「次に」の順) → 発生するイベント の順に並べ、1 つ前とつながっている要素の前にだけ矢印を出す。イベントは色と形 (破線・角丸) を分ける。イベントは並べるだけで、枠の × では外さない (プロパティ欄で関係を消す)。作業に属さない自動の処理は「作業なし (イベントから)」の枠に、すべてのイベントは最後の「イベント」の段落の枠に並べ、そこから「＋イベント」で作る。ユースケースのカードには対象のシステム・帳票 (直接結んだ対象か、使う画面のシステム) を出し、画面を使うときはそのシステムの隣に画面名を添える (長い名前はカードの中で折り返す)。
- 画面・非機能要件のボード: システムごとの枠に並べる。枠の「＋」で作るとそのシステムに属する。システムが無ければ、登場人物のボードで先に作るよう案内する。
- コンテキストのボード: コンテキストごとの枠に、属する情報・条件・状態・バリエーション・イベントを並べる。見出しの「＋コンテキスト」でコンテキストを作る (枠の見出しを押すと選んでプロパティ欄で編集する)。枠には 4 種類それぞれの「＋」と、別のコンテキスト (または未分類) の要素を移す「別のコンテキストから移す…」を出す。× で外すと未分類になる。状態は状態グループごとに属するので、移す・外すとグループの状態がまとめて動く。未分類の枠は中身があるときだけ出す。
- ボードの選択肢では、画面を操作の下に、コンテキストをバリエーションの下に、非機能要件を最後に置く。情報・条件・状態・バリエーションをまとめて見る場所なので。トレースやグローバルフィルターのレイヤーの並びは変えない。
- グローバルフィルター: すべての固定ボードに共通の絞り込み。各固定ボードの上に置き、レイヤーごとに要素を 1 つ以上選べる (選んだ要素はチップで出し、× で外せる。「リセット」で全部消す)。選んだ要素からトレースと同じく上下へ辿って届く要素だけを出す。レイヤーの中は「どれかにつながる」(OR)、レイヤーどうしは「すべてにつながる」(AND)。コンテキストは分類なので、選ぶと属する要素から上へも辿る。合う要素のコンテキストと、合う情報の置き場所 (システム・帳票) も出す。見出しの要素が合う枠は中身が無くても残し、それ以外の枠は中身が無ければ出さない。名前の絞り込みとも併用できる。保存せず、履歴にも入れない (ファイルを開くと消える)。
- すべての固定ボードの見出しの下に「書き方のヒント」を出す。ボードで扱う要素と取り違えやすい要素を並べた表 (何を書くか・粒度の目安・書き方・例・大きすぎる例・細かすぎる例) と、迷ったときの問いで、今のボードの種類を強調する。並べる組は、登場人物 = アクター・外部アクター・システム・帳票 (4 種類ともボードに出るので強調しない)、業務 = 業務・活動・作業、活動・作業・操作 = 活動・作業・操作、コンテキスト・情報・バリエーション = コンテキスト・情報・バリエーション、状態・条件 = 状態・条件。大きすぎる例・細かすぎる例には「何に当たるか」を書き、どこへ移せばよいかわかるようにする。最初は閉じておき、開閉の状態は固定ボード全体で覚える (履歴に入れない)。文言は `packages/ui/src/components/granularity.ts` にまとめる。プロパティ欄でも、課題以外の要素の名前欄の下に書き方を 1 行出す。
- 枠の「＋<種類>」で、その枠に結びついた要素を作る (作成と結びつけで 1 件の履歴)。作ったら選択し、プロパティ欄の名前欄にフォーカスする。
- 関係で結ぶ枠では、「既存から足す」で既にある要素を結べ、カード横の × で枠から外せる (関係を消すだけで、要素は残る)。所属で決まる枠 (BUC・アクティビティ・情報・状態) の移動はプロパティ欄で行う。
- 枠の見出し (上位の要素) やカードをクリックすると、その要素を選択してプロパティ欄に出す。
- 上部の「絞り込み」で名前を絞り込む。見出しが一致した枠は中身をすべて出し、それ以外の枠は一致した要素だけを出す。何も一致しない枠は出さない。絞り込みの文字列は固定ボードごとに覚え、履歴には入れない。
- 業務・アクティビティのカードには担当アクター名のラベルを出す (4.4 参照)。

### 4.3 自由ボード

- 業務は枠 (グループノード)。枠の中に BUC の小枠と、既定 BUC のアクティビティを描く。
- アクティビティ・BUC は、所属先の業務の枠 (BUC なら BUC の小枠) が同じボードにあれば、その枠の子として描く。枠がなければ単独のカードとして描き、業務名 (BUC なら「業務名 / BUC 名」) をカードのラベルに出す。
- 所属は変えられないので、枠の外へドラッグしても、別の枠に入れても、要素一覧から枠の上に置いても所属は変わらない。枠を動かすと、所属する子孫も同じ量だけ動く。
- 枠のリサイズ (左端・上端を含む) は枠の位置と大きさだけを変え、子孫の位置 (絶対座標) は動かさない。
- 線 (関係) は表示するだけで、引くことも消すこともできない。接続ハンドルは見せない。
- 線の付け根はボードごとに変えられる。既定は始点の右の辺から出て終点の左の辺に入る。線を選ぶとプロパティ欄に「線の付け根 (このボードだけ)」が出て、始点・終点それぞれ左・右・上・下の辺を選べる (「入れ替え」で両端を入れ替える)。`boards[].edges` に `{ relationId, sourceSide?, targetSide? }` で持ち、既定の辺は省略し、両方とも既定なら項目ごと消す。関係を消すと各ボードの項目も消す。
- 同じ要素を同じボードに 2 回置くことはできない。座標はボードごと。

### 4.4 アクターの担当のラベル

- アクターの担当 (`actorBusiness`・`actorActivity`) は線を引かず、相手の業務の枠のタイトル行・アクティビティのカードに担当名のラベルで出す (固定ボードでは業務・アクティビティのカード)。業務とアクティビティを結ぶ線が多く、図が読みにくくなるため。
- ラベルはアクターがボードに置かれているかに関係なく出る。外部アクターは色を分ける。カードでは 1 行に収め、入りきらない名前は省略する (マウスを乗せると全文)。

### 4.5 分析ボード

固定ボードと同じく中央を広く使い、2〜3 レイヤーをまたいで見渡す表。モデルには保存せず、毎回モデルから組み立てる (`packages/core/src/model/analysis.ts`)。id は `analysis:<種類>`。要素名をクリックすると選択してプロパティ欄に出す。分析ボードで変えられるのは、自由ボードと同じく名前・説明・時間・リンクだけ。

| ボード | 見渡すレイヤー | 何がわかるか |
| --- | --- | --- |
| 課題の分布 | 業務 → 作業・操作 → 課題 | 業務ごとに、業務・その作業・作業が使う操作に付いた課題 (具体的な課題) を重要度順に集める。どの業務にも辿れない具体的な課題は最後にまとめる。全体的な課題は下に別の表で登場人物ごとに、未整理の課題 (対象なし) はその下に別の表で出す |
| 担当別の作業一覧 | 担い手 → 業務・活動 → 作業 → 操作 | 担い手 (アクター・外部アクター) ごとの作業と、作業・操作のリンク (マニュアルなど)。担い手で絞り込める。担当の無い作業は最後にまとめる |
| 情報の所在 | 情報 → システム・帳票 → 操作、システム → 画面 → 情報、システム → イベント → 操作 | 情報 × 置き場所の表に取得・保存を出す。置き場所なし・紙だけ・保存先が複数 (二重管理の可能性) に印を付ける。その下に「画面と情報」の見出しで、システムごとに画面 × 情報の表を並べる (列はそのシステムの画面のどれかが扱う情報だけ)。扱う情報が、そのシステムの置き場所 (取得元・保存先) に無ければ「○!」(転記や二重管理の手がかり)、情報を扱わない画面には「扱う情報なし」の印を付け、画面ごとに使う操作を添える。画面の無いシステムは表を作らず 1 行にまとめる (`screenInformationTables`)。さらにその下に「システムのイベント」の見出しで、システムごとに、システムから発生するイベントを並べる。発生のしかたは「直接」(システム → イベント) と「操作から」(そのシステムを対象にした操作が発生させる。対象が画面なら、画面が属するシステム。帳票はシステムではないので数えない) を分けて出し、イベントごとにきっかけにする操作とその作業 (作業に属さない自動の処理なら「作業なし」) を添える。イベントの無いシステムと、どのシステムにもつながらないイベントは、最後にそれぞれ 1 行にまとめる (`systemEventLists`) |

- **サンプル**: サンプルの一覧 (いまは「店舗の業務」「ネットショップの業務」「宿泊施設の業務」「経理業務」の 4 件。この順に並べる。将来のサンプルギャラリー)。題名と一行の紹介をカードで並べ、押すとそのサンプルを新しいモデルとして開く (元のサンプルは変わらない)。一覧は `@untie/core/sample` の `SAMPLES` (`id`・`title`・`description`・`create`) で、サンプルを足すときはここに 1 件足す。

### 5.1 ツールバー

- 左端の「ホーム」: ホームへ戻る。保存していない変更があれば確認する。
- 「ファイル」メニュー: 新規作成・開く・最近開いたファイル・保存・別名で保存 (6.1)、ログイン中は「クラウドへ保存」(いま開いているモデルをクラウドファイルとして複製する)、プロンプトから作成・AI の設定 (6.2)。ショートカットは Cmd/Ctrl+O、Cmd/Ctrl+S、Shift+Cmd/Ctrl+S (入力欄の中でも効く)。
- 「AI」: 下に AI エージェントのペインを開閉する (6.2)。
- ボード切替 (セレクト)。「固定ボード」(10 枚)・「分析ボード」(3 枚。課題の分布を先頭に置く)・「自由ボード」のグループに分ける。
- 「＋ボード」は自由ボードを追加して切り替える。名前変更・ボード削除は自由ボードだけ (最後の 1 枚は削除できない。確認ダイアログあり)。
- 要素の作成は固定ボードの枠で行うので、ツールバーに「追加」メニューは置かない。
- Undo / Redo ボタン。ショートカットは Cmd/Ctrl+Z と Shift+Cmd/Ctrl+Z (Ctrl+Y も Redo)。
- 「検証」: 右側に検証パネルを出す (プロパティ欄と切り替え)。アクター／外部アクターに辿り着けない要素があれば、その件数をボタンに出す。1 つの業務に複数のアクターが付いている警告は、別の色で件数を並べる (5.6)。
- 「課題一覧」: 右側に課題一覧パネルを出す (プロパティ欄と切り替え)。
- ツールバーの下に、開いているファイル名 (サンプルなら「サンプル (まだ保存していません)」) と、保存していない変更があればその印を出す。

### 5.1.1 クラウドファイルを開いているとき

ツールバーとペインがローカルと変わるところだけを書く。詳細は collab-design 8 章。

- タイトルの横に、接続の状態 (接続中 / 切断。再接続します)、自分の役割、一緒に開いている人の色玉を出す。他の人が選んでいる要素は、その人の色の縁と名前のラベルで固定ボード・自由ボードに出る。プロパティ欄には「○○さんも選択中」を出す (ロックはしない)。
- Undo / Redo は使えない (ボタンは無効、ショートカットも効かない)。共有中の Undo は他の人の変更と絡んで結果が読めないため。誤って消したときは、書き出した JSON と、サーバーに残る 1 時間ごとのスナップショットから戻す。
- 「ファイル」メニューは「ホーム」「JSON に書き出す」「クラウドへ保存 (複製)」だけ。Cmd/Ctrl+S は JSON への書き出しになる。
- 所有者は「共有」ダイアログを開ける (メンバーの役割、メール招待、所有者を譲る、リンクを知っている人の閲覧)。
- `viewer` とリンクで開いた人 (ゲスト) は、上に「閲覧専用です」の帯が出て、編集・AI エージェントが使えない。選ぶことはできる。ゲストは「複製して自分のファイルにする」(ログインが要る) ができる。

### 5.2 要素一覧 (左)

- 自由ボードのときだけ出す。固定ボードは上位の要素から順に辿るので一覧は出さず、中央を広く使う。
- 左上の「‹」で閉じられる。閉じると左端に細い帯だけ残して「要素一覧」と縦書きで出し、帯か「›」で開き直す。右のペインと同じく、開閉は保存せず、履歴にも入れない。
- 種類ごとに折りたたみ。各行は名前と、課題バッジ (あれば)。BUC の行には「業務: 業務名」を添える。
- 行をクリックすると選択し、現在のボードにあればそのカードへスクロールする。
- 自由ボードでは、現在のボードに置かれているかの印を出し、行をキャンバスへドラッグするか、右クリック・行末の「置く」で現在のボードに置ける (すでにあれば何もしない)。固定ボードでは置く操作は出さない。
- 既定 BUC は出さない。

### 5.3 中央

- 固定ボード: 4.2 のとおり、枠を格子状に並べた HTML。上部に見出し・説明・絞り込み。
- 自由ボード: React Flow。ノード種別は `frame` (業務・BUC の枠)、`card` (その他の要素)。カードは種類ごとに色を変え、左上に種類名、中央に名前、右上に課題バッジ (対象になれる種類のみ) を出す。業務の枠はタイトル行に業務名と主担当のラベル、BUC の小枠はタイトル行に BUC 名。枠はリサイズできる。
- 自由ボードの Delete キーは選択中のノードをボードから外す (要素は残る)。線は消せない。固定ボードでは Delete キーは何もしない。
- 線は枠・カードより上に描く。枠の中やカードの上を通る線もクリックで選べる (その分、線が重なる所ではカードより線が先に当たる)。

### 5.4 プロパティ欄 (右)

- 右のペイン (プロパティ欄・課題一覧・検証) は右上の「›」で閉じられる。閉じると中央を広く使い、右端に細い帯だけ残して、いま何のペインかを縦書きで出す。帯か「‹」で開き直す。ツールバーの「検証」「課題一覧」を押したときも開く。開閉は保存せず、履歴にも入れない。

選択中の要素の内容を編集する。固定ボードではすべて編集でき、自由ボードでは名前と説明だけを編集できる (他の欄は無効にし、その旨を出す)。

- 共通: 種類 (表示のみ)、名前、説明。
- 作業・操作: 時間 (時間単位、小数点第一位まで。0 以上。空にすると消す)。作業では、使う操作の時間の合計を「操作の合計」として作業自身の時間とは分けて出す (時間の入った操作が無ければ出さない)。固定ボードのカードと分析ボードの担当別の作業一覧 にも、作業自身の時間と操作の合計を分けて出す。同じ操作を複数の作業が使う場合は、それぞれの作業の合計に入る。名前・説明と同じく自由ボードでも編集できる。
- 作業・操作: リンク (表示名と URL。マニュアルなど)。複数持て、並べ替え・削除でき、名前をクリックすると既定のブラウザで開く (デスクトップは opener プラグイン)。URL は http / https だけ。名前・説明と同じく自由ボードでも編集できる。固定ボードのカードにはリンクの件数を出す。
- アクティビティ: 業務と BUC のセレクト (未所属を含む)。
- BUC: 業務のセレクト。
- 情報・状態・条件・バリエーション: コンテキストのセレクト (未分類を含む。状態は状態グループごと)。つながりから見た候補が今の所属と違えば、候補と「〇〇にする」ボタンを出す。状態: 状態グループ。バリエーション: 値の一覧 (追加・削除・並べ替え)。
- 課題: 重要度 (1〜5)、区分 (全体的・具体的・未整理)、対象の一覧 (種類・名前・そのレイヤーの固定ボードへ移る「移動」・外す)。「対象を追加」はレイヤーごとに分けて出し、対象があるときは同じ区分の候補だけを出す。別の区分に付け替えるときは、いまの対象をすべて外してから追加する。
- 関係一覧: この要素が始点または終点になっている関係を、関係名・向き・相手の種類 (レイヤー名) 付きで一覧し、相手をクリックで選択する。固定ボードでは × で関係を消せ、「関係を追加」のセレクトで結べる要素 (関係名・向き・種類ごと。既にある関係は除く) を選んで関係を足せる。固定ボードの枠で表せない関係 (担当アクター、情報の取得元・保存先、情報どうしの関連、条件とバリエーション・状態、状態とユースケース) はここで編集する。
- トレース (関係と課題の間): 要素から上 (担い手の側) と下 (詳細の側) へ、直接つながっていない要素まで辿り、レイヤーごとに 1 行で表にする (`packages/core/src/model/lineage.ts`)。列はレイヤー・要素・移動。上は登場人物の側から、下は近い順に並べ、自分の行を間に置く。要素名をクリックするとその要素を選ぶ。「移動」はそのレイヤーの固定ボードへ、今の要素を選んだまま移り、その要素のカードか、その要素が見出しの枠 (無ければ所属先や関係で結ばれた要素) までスクロールする。要素が枠や段落の見出しになっているボードでは、その枠・段落を選択中として出す。1 行に 7 件以上あるときは 6 件まで出し、「ほか N 件」で開く。辿る向きは、業務 → 主担当、活動 → 業務、作業 → 活動 (業務に直接なら業務)・担当、操作 → 作業、情報 → 操作・コンテキスト・置き場所、条件 → 操作・コンテキスト、状態 → 操作・条件・コンテキスト、バリエーション → 情報・条件・コンテキスト (下へはこの逆)。情報どうしの関連は同じレイヤーなので辿らない。コンテキストは分類なので、上へは属する要素から辿る。 つながる要素が無くても、その種類の上下に来うるレイヤーは「(未設定)」(灰色) の行で出し、「移動」でそのレイヤーの固定ボードへ移れる (結ぶ相手を作りに行けるように)。来うるレイヤーは種類で決める (例: 帳票の下は情報・バリエーションだけ、外部アクターは業務の主担当にならないので下に業務を出さない)。
- 課題: この要素を対象にしている課題の一覧と「課題を追加」ボタン (登場人物・業務・作業・操作のみ。固定ボードだけ)。見出しに区分 (登場人物なら全体的な課題、業務・作業・操作なら具体的な課題) を添える。
- 自由ボードでは「ボードから外す」(ボードにある場合)、固定ボードでは「削除」。
- 課題では左端に「削除」を出し、課題を削除すると課題一覧へ戻る。右端は作ったばかりかどうかで変える。
  - 追加フォーム (「＋課題」「課題を追加」で作った直後): 「次の課題を登録する」。作ったときと同じ対象で次の課題を作り、名前の入力へ移る。続けて書き出せるようにするため。
  - 編集フォーム (既存の課題を選んだとき、または別の要素を選んでから戻ったとき): 「課題一覧に戻る」。
- 関係 (線) を選択したときは、関係名と両端の要素を出す (削除は無い)。

### 5.5 課題一覧パネル

最初に課題を書き出し、それを紐解くように整理するための場所。

- 見出しの「＋課題」で対象のない課題を作り、選んでプロパティ欄の名前の入力へ移る。どのボードからでも作れる。
- 課題を 未整理・全体的な課題・具体的な課題 の 3 段に分ける。課題の無い段には、何を入れる段かの説明を出す。
- 並べ方は「課題ごと」と「対象ごと」を切り替えられる (保存しない)。
  - 課題ごと: 段ごとに重要度の高い順 (同じなら名前順)。各行は重要度、名前、対象要素の種類と名前。
  - 対象ごと: 全体的・具体的の段を、対象の要素ごとにまとめる。まとまりの見出しに種類・名前・そのレイヤーの固定ボードへ移る「移動」・その要素を対象にした課題を作る「＋課題」を出す。対象は 登場人物 → 業務 → 作業 → 操作 の順、同じ種類は名前順。対象が複数ある課題は、それぞれのまとまりに出る。未整理の段はいつも課題ごとに並べる。
- 行をクリックするとその課題を選択してプロパティ欄に切り替える。対象名をクリックすると対象要素を選択する。
- 課題はどのボードにも出ないので、プロパティ欄では自由ボード・分析ボードでも重要度・対象を編集でき、削除できる。

### 5.6 検証パネル (担い手まで辿れるか)

すべての要素が担い手 (アクター／外部アクター／システム) まで辿れるかを調べる (`packages/core/src/model/trace.ts`)。つながりは必須にしない。上から順に書き出していく途中の状態 (担当の決まっていない作業など) を作れるようにするため。代わりに、辿り着けない要素とどこで途切れているかを知らせる。

- 要素ごとに「担い手に近い側」を決め、担い手から下へ広げて届いたものを「辿り着ける」とする。

| 要素 | 担い手に近い側 |
| --- | --- |
| 業務 | 主担当のアクター |
| 活動 (BUC) | 業務 |
| 作業 | 担当のアクター／外部アクター (必須。所属の活動・業務からは辿らない) |
| 操作 | 使う作業、きっかけのイベント |
| イベント | 発生させる操作・システム |
| 画面・非機能要件 | 属するシステム |
| 情報 | 扱う操作・画面、関連する情報 |
| コンテキスト | 入っている情報 |
| システム | 担い手なので辿り着く先。ただし操作の対象・情報の置き場所・イベントの発生元のどれでもなく、画面も無ければ途切れとする |
| 帳票 | 取得元・保存先として結んだ情報、対象にする操作 |
| 条件 | 判断に使う操作 |
| バリエーション | 種別にしている情報・条件 |
| 状態 | 実行可・次の状態で結んだ操作、状態を参照する条件 |

- 作業は担当を必ず持つ。業務に属していて業務に主担当がいても、作業に担当が無ければ途切れとする。
- 情報はシステム・帳票からは辿らない。置き場所に結んだだけで「どの操作にも扱われていない情報」が見えなくならないようにするため。
- **警告 (エラーではない)** (`traceWarnings`)。辿れるかの件数には数えず、直さなくても編集・保存はできる。パネルでは種類ごとに [警告] の見出しと案内を付けて、要素と関わる要素をリンクにして出し、ボタンには警告の数をエラーとは別の色 (黄) で並べる。
  - **1 つの業務に複数のアクター**: 業務に結ぶのは主担当の 1 人で、ほかの人は作業の担当として作業に結ぶ。案内は「業務をアクターごとに分解できるか検討してください」。外部アクターは業務に結べないので、対象はアクターだけ。
  - 操作の連鎖 (「次に」でつないだ並び) がイベントで終わらなくても警告しない。結果をイベントで表さない操作もあるため。
- 課題 (対象の要素に付くもの) と既定 BUC (業務と一体) は検証の対象にしない。
- 対象のない課題 (未整理) は、エラーではなく [情報] に「対象のない課題」として出す。紐解きの残りが見えるようにするため。
- 辿り着けない要素のうち、アクターに近い側がまったく無いものを「途切れ箇所」とし、種類ごとの理由 (例: 「どの作業にも使われていません」) を出す。関連する情報どうしのように、互いにつながっているだけで外へ出られないものも途切れ箇所にする。
- パネルには途切れ箇所だけを並べ、理由と直し方 (その要素自身で何をすればよいか) を出す。その先で辿り着けない要素 (上へさかのぼるとその途切れ箇所に行き着く要素) は、種類ごとの件数だけを出す。別のレイヤーの要素を開いても直せない (例: 業務の主担当は操作からは結べない) ので、迷わないようリンクにしない。
- 途切れ箇所の要素名をクリックすると、その要素を編集できる固定ボードへ移って選択し、プロパティ欄に出す。
- [情報] として、コンテキストの所属の見直し候補も出す (エラーではないので、ボタンの件数には数えない)。コンテキストに属していない要素 (候補があれば添える) と、属するコンテキストの要素とつながらず別のコンテキストの要素とだけつながる状態・条件・バリエーションを挙げ、候補のコンテキストへ 1 クリックで移せる。情報どうしの関連はコンテキストの結合そのものなので、情報は「未分類」のときだけ挙げる。状態グループは 1 件にまとめる。
- モデルが変わるたびに計算し直す。

## 6. 状態管理と操作

- zustand + immer の単一ストア。`model` (UntieModel) と `history` (undo/redo のスタック)、`ui` (現在のボード、選択、パネルの開閉) を持つ。
- モデルを変える操作はすべて `commands` (純粋関数 `(model, payload) => model`) として `packages/core/src/model/commands.ts` に置き、ストアはそれを呼んで履歴に積む。コマンドは Vitest で直接テストする。
- 履歴はモデルのスナップショット (immer の構造共有で安価) を最大 100 件持つ。UI の状態は履歴に入れない。
- ノードのドラッグ中は座標をストアの一時状態に反映し、ドラッグ終了時に 1 件の履歴として確定する。名前や説明の入力は、入力欄からフォーカスが外れたとき (または 500 ms 入力が止まったとき) に 1 件として確定する (IME の変換中は確定しない)。ドラッグ中の Undo / Redo は無視する。
- 要素削除は、関係・ボード上のノード・課題の対象・(業務なら) BUC をまとめて消す 1 件の履歴。

主なコマンド:

| コマンド | 内容 |
| --- | --- |
| `addElement(kind, name, boardId?, position?)` | 要素を作る。業務なら既定 BUC も作る。boardId があればそのボードに置く |
| `updateElement(id, patch)` | 名前・説明・種類固有の項目を変える |
| `removeElement(id)` | 要素と付随するものを消す |
| `moveActivity(activityId, bucId \| null)` | アクティビティの所属を変える |
| `moveBuc(bucId, businessId)` | BUC の業務を変える |
| `moveToContext(elementId, contextId \| null)` | 情報・状態・条件・バリエーションのコンテキストを変える (状態はグループごと) |
| `addRelation(sourceId, targetId)` | 両端から種類を決めて関係を作る。不可なら失敗を返す |
| `removeRelation(id)` | 関係を消す |
| `addBoard(name)` / `renameBoard(id, name)` / `removeBoard(id)` | ボードの追加・名前変更・削除。最後の 1 枚は削除できない。削除してもボード上の要素は残る |
| `placeOnBoard(boardId, elementId, position)` | 要素をボードに置く |
| `removeFromBoard(boardId, elementId)` | ボードから外す |
| `moveNode(boardId, elementId, position, size?)` | 座標・サイズを変える |
| `setIssueTargets(issueId, targetIds)` | 課題の対象を変える |
| `clearAll()` | 全て消す |

### 6.1 保存・読み込み

- モデルをそのまま JSON (2 スペースで整形) で保存する。拡張子は `.json`。ボードの配置も含む。UI の状態 (選択・開いているボード・絞り込み) は保存しない。
- 読み込むときは、古い版のモデルの形式なら現行へ変換してから (`loadModelJson()`。4 章)、JSON Schema の検証と参照整合性の検査 (`validateModel()`) を通す。変換したときは「古い形式 … から … に変換しました。保存すると新しい形式で書き出します」と知らせる。クラウド版の取り込み (`POST /api/files` の `{ model }`) と、サーバーに古い形式で残っている中身の書き出しも同じく変換する。通らなければ理由を最大 3 件出して、今のモデルを残す。読み込むと履歴を捨て、作業の固定ボードを開く。
- 保存すると保存先を覚え、次からは同じファイルに上書きする。「別名で保存」は保存先を選び直す。保存するときは入力中の名前・説明を先に確定させる。
- 保存していない変更の判定は、最後に保存・読み込みしたときのモデルと今のモデルが同じ参照かで行う (immer の構造共有なので、Undo で保存時点に戻れば変更なしになる)。サンプルは一度も保存していなければ、編集したときだけ変更ありとする。
- 保存していない変更があるとき、「開く」「最近開いたファイル」とウィンドウを閉じる前に確かめる。
- 「最近開いたファイル」は、開いた・保存したファイルを新しい順に最大 5 件覚える (同じファイルは先頭へ移す)。項目にフォーカスするか、マウスを載せるとサブメニューが開き、選ぶとそのファイルを開く (→ でサブメニューへ、← で戻る)。読めなかったファイル (消えた・動かしたなど) は一覧から外す。「一覧を消去」で空にできる。デスクトップアプリではパスを localStorage に、ブラウザでは File System Access API のハンドルを IndexedDB に置く。ブラウザでは開くときに読み書きの許可を求め直すことがある。File System Access API の無いブラウザでは開き直せないので、項目を使えなくする。
- 「新規作成」は空のモデル (空の自由ボード「ボード 1」だけ) を、まだ保存していないモデルとして開く。履歴を捨て、作業の固定ボードを開く。手を付けるまでは保存していない変更なしとして扱う。保存していない変更があれば、先に確認ダイアログで「保存して新規作成」「保存せずに新規作成」「キャンセル」を選ばせる。保存を選んで保存先の選択を取り消したり保存に失敗したりしたら、今のモデルを残す。
- デスクトップアプリでは、ファイル選択と保存先の選択に dialog プラグインを使い、読み書きは Rust のコマンド (`read_model_file` / `write_model_file`) で行う。パスはダイアログで選ばれたもの (と、それを覚えた最近開いたファイル) だけを渡す。ブラウザ (Web 版・開発用) では、File System Access API があれば (Chrome・Edge) `showOpenFilePicker` / `showSaveFilePicker` のハンドルを覚えて同じファイルに上書きする (ストアの `file.path` にはハンドルの代わりに `browser:<番号>` を入れる。ハンドルは最近開いたファイルとして IndexedDB にも残す)。無ければファイル選択とダウンロードで代わりにする。
- **クラウドファイル**はファイルではなくサーバーが正本で、保存の操作は無い (つながっている間は常に反映される)。「JSON に書き出す」で同じ形式 (上のローカルファイルと同じ JSON) の中身を取り出し、「クラウドへ保存」でローカルのモデルをクラウドファイルとして複製する。クラウドファイルにはローカルの履歴 (Undo / Redo)・保存先・最近開いたファイル・「保存していない変更」の判定は無い。つながっていない間に溜めた変更だけが、閉じる前の確認の対象になる。読み込み・書き出しとも `validateModel()` を通す。詳細は collab-design 5 章・8.2。
- Web 版 (ローカル専用) は Cloudflare Pages が `apps/web/dist/` を静的なサイトとして配る (`pnpm web:deploy`。手順は README の「Web 版の配信 (Cloudflare Pages)」)。`apps/web/public/_headers` で CSP を付け、スクリプトは自分のオリジンだけ、通信先は自分のオリジンと各 AI プロバイダーの API だけに絞る。クラウド版は Cloudflare Worker (`apps/server`) が `apps/cloud/dist/` を配り (`pnpm cloud:deploy`)、`apps/server/public/_headers` で同じように絞る (通信先は自分のオリジンの WebSocket を含む)。
- アプリの CSP は eval を許さないので、ajv で実行時にスキーマをコンパイルできない。検証関数は `packages/core/scripts/gen-validator.mjs` で事前に生成し (`packages/core/src/model/schemaValidator.gen.js`)、`pnpm gen:types` で型と一緒に作り直す。CI の `check:types` で生成物がスキーマと一致しているかを検査する。

### 6.2 AI エージェント

**使う AI**: Claude (Anthropic)・Codex (OpenAI)・Gemini (Google) から選ぶ。どれも各社の API をアプリから直接呼ぶ (`packages/ui/src/ai/chat.ts`)。会話の履歴は各社の API の形のまま持ち、モデルを読み書きする道具の定義と実行は共通にする。

| AI | API | 既定のモデル | 備考 |
| --- | --- | --- | --- |
| Claude | Anthropic Messages API (`@anthropic-ai/sdk`、beta) | `claude-opus-5-5` | Opus 5.5・Sonnet 5.5 では、安全のための判定で断られたときに別のモデルで続けるサーバー側のフォールバック (`fallbacks: "default"`) を付ける |
| Codex | OpenAI Responses API (`openai`) | `gpt-5-codex` | |
| Gemini | Gemini API (`@google/genai`) | `gemini-2.5-pro` | |

- モデル名は「AI の設定」で自由に入れられる (候補も出す)。プロバイダーとモデルは端末ごとに覚える (localStorage)。
- **API キー**: プロバイダーごとに「AI の設定」で入れ、OS のキーチェーン (macOS のキーチェーン / Windows の資格情報マネージャー) に保存する (Rust の `keyring` クレート、コマンド `get_secret` / `set_secret` / `delete_secret`。ログインのセッションのトークンも同じキーチェーンに置く)。モデルのファイルには入らない。ブラウザ (Web 版・開発用) ではタブを閉じるまでメモリに持ち、「このブラウザに保存する」を選んだときだけ localStorage (`untie.apiKey.<プロバイダー>`) にも置く。保存済みのキーはチェックを変えるとすぐ置き場所を移し、「消す」で両方から消す。保存するときは前の項目を消してから作り直す (署名の違うアプリが作った項目は上書きしても読めないため)。読み出しに失敗したときは「(未設定)」と区別して「(読み出せません)」と理由を出し、保存し直すよう案内する (AI の会話・プロンプトからの作成でも同じ)。macOS のキーチェーンはアプリの署名で読み出しを許すので、手元で作り直すときは固定の証明書で署名する (`pnpm app:build`、README)。
- アプリの CSP は、各社の API (`api.anthropic.com`・`api.openai.com`・`generativelanguage.googleapis.com`) への接続を足す。デスクトップはサーバーの URL を設定で変えられるので、`connect-src` に `https:`・`wss:` も許している (collab-design 8.4)。API キーはクラウドに置かず、サーバーにも送らない。

**会話 (下のペイン)**: ツールバーの「AI」で開閉する。依頼を書いて Enter で送る (Shift+Enter で改行、変換中は送らない)。

- AI は道具 (`packages/ui/src/ai/tools.ts`) でモデルを読み書きする: `get_model` (要素と関係の一覧。既定 BUC は隠し、業務に直接属する作業は業務を示す)、`add_element`、`update_element`、`remove_element`、`add_relation`、`remove_relation`、`move_activity`、`move_buc`、`set_context`。中身は既存のコマンドを呼ぶだけで、整合性の検査はコマンドに任せる。失敗は理由を AI に返し、AI が直してやり直す。
- 1 回の返答の間の編集は 1 件の履歴にまとめる (`beginAgentEdit` / `agentApply` / `endAgentEdit`)。元に戻す (Undo) で AI の変更をまとめて戻せる。
- 発言には、開いているボードと選択中の要素を添える (「これを直して」が通じるように)。
- 指示 (`packages/ui/src/ai/prompts.ts`) には、要素と画面での呼び名、つながりの決まり、書き方のヒントと同じ粒度の説明を入れる。
- 道具を使った回数と成否を会話に小さく出す。中断できる。プロバイダーやモデルを変えると新しい会話になる。途中でエラーになったら、次の発言では会話を作り直す。

### 6.3 課題の深掘り

課題のプロパティ欄の「AI と深掘りする」で、下のペインを **深掘りモード** にして始める (`packages/ui/src/ai/grill.ts`、`agentStore` の `mode`)。独自のダイアログにしないのは、利用者がボードや課題一覧を見ながら答えられるようにするためと、会話の仕組み (道具ループ・中断・1 回の返答 = 1 件の履歴) をそのまま使うため。

- **進め方**は grill-me (mattpocock/skills の grilling) の方式を、現場担当者が答えられる 4 本の軸に当てはめる。現象 (何が・いつ・どのくらい) → 所在 (どの業務・活動・作業・操作、または登場人物) → 理由 (なぜそこで) → 影響 (誰にどう響く) の順に、前提の揃った問いだけをラウンド (3〜4 問) でまとめて出す。各問いに「➡️ 推奨」の見立てを添え、「はい」で推奨を採る。モデルにある事実 (作業の担当、使う操作など) は利用者に聞かず `get_model` で調べる。開いた問いが無くなったら 4 軸でまとめ、重要度と対象の案を示して確認し、了承後に道具で更新する。
- **渡すもの**: 最初の発言に、課題 (名前・説明・重要度・既にある分析) と、対象ごとの所属 (活動・業務) とつながり (担当・使う操作・扱う情報など) を JSON で入れる。この発言は利用者の発言としては表示しない。残りは `get_model` で読む。
- **道具**は 3 つに絞る: `get_model` (共通)、`update_issue_analysis` (その課題の分析と重要度)、`set_issue_targets` (その課題の対象)。書く道具は深掘り中の課題にだけ効く。要素の追加はできない。所在になる作業などがモデルに無ければ、まとめにその旨を書かせ、通常モードで足してから付ける。
- 1 セッション = 1 課題。開始で会話を作り直し、「深掘りを終える」で通常の会話に戻る (表示は残し、次の発言から新しい会話)。プロバイダーやモデルの切り替えは通常の会話と同じ。会話のログはモデルのファイルには残さない。
- 課題の名前と説明 (原文) は AI に変えさせない。更新されるのは `analysis`・`severity`・`targetIds` だけ。

**プロンプトから作成 (ファイル > プロンプトから作成)**: 初期要望の文章から、新しいモデルを作る (`packages/ui/src/ai/generate.ts`)。RDRA ZeroOne (要望の分析から段階を踏んでモデルを作る進め方) を参考に、指示は自前で書く (参考元のリポジトリにはライセンスの表示が無いので、文面は使わない)。

1. 分析: 初期要望を段階 1〜4 (要望の分析、登場人物、業務と活動、情報・状態・条件・バリエーション) で検討し、箇条書きで出してもらう。画面にそのまま流す。
2. 提出: 段階 5 (作業と操作) まで進め、モデル全体を道具 `submit_model` で出してもらう。下書きは名前で参照する形 (`packages/ui/src/ai/spec.ts`) で、AI には id を作らせない。
3. 組み立てと検査: 下書きを既存のコマンドでモデルに組み立て、スキーマ・参照整合性の検査と、担い手まで辿れるかの検査を通す。見つからない名前や担当の無い作業などがあれば、理由を返して出し直してもらう (2 回まで。それ以降は気づいたことが残っていても受け付ける)。
4. 受け付けたら、新しい (まだ保存していない) モデルとして開き、AI エージェントのペインを開く。作成の会話 (初期要望と、分析・作成結果のまとめ) を引き継ぐので、そのまま「〇〇を足して」と続けられる。

- **ユースケース (10 前後)**: 予約を登録する、予約を検索する、予約を変更する、予約を取り消す、チェックインを記録する、部屋の割り当てを記録する、追加料金を登録する、請求金額を計算する、請求書を発行する、決済を記録する、チェックアウトを記録する、清掃状況を更新する

- **コンテキスト (4)**: 予約、顧客、客室、料金
- **情報 (6)**: 予約 (予約)、宿泊客 (顧客)、部屋・清掃記録 (客室)、料金プラン・請求 (料金)。宿泊管理システム・予約サイト・決済サービスから取得し、宿泊管理システム・会計システム・宿泊者名簿・清掃チェック表に保存する

### 7.1 ネットショップの業務 (サンプル)

`packages/core/src/sample/netshop.ts`。架空の雑貨のネットショップ (自社サイトとモールで売り、倉庫から出荷する小さな店)。ホームのサンプルの一覧から開く。構成は宿泊施設と同じで、実在の店・実データは使わない。**モデルの形式 0.2.0 の書き方の見本**で、イベント・「次に」・画面・非機能要件を使い、検証のエラーも警告も出ない。

- **業務 (7)**: 入荷・在庫管理、受注処理、出荷、返品・交換、問い合わせ対応、売掛金・入金管理、月次の数字の確認。受注処理だけ、活動 (BUC) を「注文の確認」「入金の確認」の 2 つに分ける。モールからの入金 (手数料などを引いた額で、あとから届く) を、会計システムの画面で注文と突き合わせて消し込む。月次の数字の確認は、経理担当 (主担当) と店長が会計システムの月次レポートで損益計算書 (PL) と貸借対照表 (BS) を見て報告する (売上は PL に、売掛金は BS につながる)
- **自動の処理**: 「注文が確定した」→ 在庫を引き当てる (対象: 販売管理システム) →「在庫が引き当てられた」、「出荷が記録された」→ 売掛金を登録する (対象: 会計システム) →「売掛金が計上された」。人の作業もイベントをきっかけに始まる (例: 「入金が確認された」→ ピッキングリストを出す、会計システムの「月次の締めが済んだ」→ 損益計算書を見る)
- **イベント (20)・画面 (10)・非機能要件 (4)**: 作業の操作の並びは、すべてイベントで終わる。画面は販売管理システム (受注入力・受注一覧・在庫一覧・出荷指示・返品登録・問い合わせ履歴)、モールの管理画面、決済サービス、会計システム (売掛金の消込画面・月次レポート) に置く。非機能要件は、セールの日の注文の量・データの控え・カード番号を保存しない・会計の画面を開ける人

- **アクター (5)**: 受注担当、倉庫担当、カスタマーサポート、店長、経理担当。**外部アクター (3)**: 購入者、仕入先、配送業者
- **システム (5)・帳票 (2)**: 自社サイトのカート、モールの管理画面、販売管理システム、決済サービス、会計システム / 入荷検品表、返品受付票
- **作業 (22)・操作 (23)**、情報 11 (注文・返品・購入者・問い合わせ履歴・商品・在庫・出荷・売掛金・入金・損益計算書・貸借対照表)、状態 11 (注文の状態 5・返品の状態 3・売掛金の状態 3)、バリエーション 3 (販売チャネル・支払方法・配送方法)、条件 3
- **課題 (5)**: 自社サイトとモールの在庫を別々に更新している (重要度 5。現象・所在・理由・影響の分析つき)、モールの注文を手で移している (4)、返品が棚に戻るまで何日もかかる (4)、セールの翌日は出荷が遅れる (3)、配送状況の問い合わせが多い (2)
- **ボード (3)**: 全体、入荷から返品・問い合わせまで、情報と状態

困りごとの傾向は、EC 運営の解説記事 (在庫のずれ・売り越し、返品と在庫の分断、注文データの手入力、繁忙期の人手) を参考にした。文章は写さず、数や会社名はすべて架空。

### 7.2 店舗の業務 (サンプル)

`packages/core/src/sample/retail.ts`。架空の日用品店 (駅前の 1 店舗で、本部が発注の基準を出す)。ホームのサンプルの一覧から開く。構成は宿泊施設・ネットショップと同じで、実在の店・実データは使わない。

- **業務 (7)**: 発注・入荷、陳列・在庫管理、レジ・接客、レジ締め・売上報告、棚卸、売掛金・入金管理、月次の数字の確認。レジ・接客だけ、活動 (BUC) を「会計」「返品・交換」「お取り寄せ」の 3 つに分ける。売掛金・入金管理は本部の会計システムが対象で (入金の管理・消し込み)、クレジットカードや電子マネーの売上があとから振り込まれるのを突き合わせる。売掛金の計上は自動の処理 (「カード・電子マネーで支払われた」→ 売掛金を登録する)。月次の数字の確認は、店長と本部の経理担当が本部の会計システムで損益計算書 (PL) と貸借対照表 (BS) を見る (売上は PL に、売掛金は BS につながる)
- **アクター (6)**: 店長、レジ担当、売場担当、バックヤード担当、本部の仕入担当、本部の経理担当 (本部は店の外だが同じ会社なので、外部アクターにしない)。**外部アクター (2)**: 来店客、仕入先
- **システム (4)・帳票 (3)**: POSレジ、決済端末、本部の発注システム、会計システム / 納品書・検品票、レジ締め表、棚卸表
- **作業 (23)・操作 (20)・イベント (1)**、情報 11 (商品・在庫・棚卸の結果・発注・入荷・売上・現金・支払・売掛金・入金・損益計算書・貸借対照表)、状態 11 (発注の状態 3・1 日の締めの状態 5・売掛金の状態 3)、バリエーション 3 (支払方法・商品区分・発注の種類)、条件 3
- **課題 (5)**: レジ締めの金額が合わず原因探しに毎晩時間がかかる (重要度 5。現象・所在・理由・影響の分析つき)、帳簿の在庫と実際の在庫がずれる (4)、発注数を経験で決めている (4)、本部への連絡が電話とメールに分かれている (3)、夕方に値引きと値札の貼り替えが重なる (2)
- **ボード (3)**: 全体、発注からレジ締め・棚卸まで、情報と状態

困りごとの傾向は、店舗運営の解説記事 (レジ締めの金額のずれ、帳簿と実在庫のずれ、本部と店舗の連携、バックヤードの人手不足) を参考にした。文章は写さず、数や会社名はすべて架空。

### 7.3 経理業務 (サンプル)

`packages/core/src/sample/accounting.ts`。架空の中小企業 (従業員 50 人ほど) の経理部門。ホームのサンプルの一覧から開く。構成はほかのサンプルと同じで、実在の会社・実データは使わない。1 つの業務の主担当は 1 人にしてあり (業務に複数のアクターを結ぶと検証が警告を出す)、ほかの人は作業の担当にしている。

- **業務 (6)**: 請求・売掛金管理、支払・買掛金管理、経費精算、仕訳・記帳、月次決算、年次決算・税務。請求・売掛金管理だけ、活動 (BUC) を「請求」「入金の管理」「消し込み」の 3 つに分ける。会計システムが売掛金と入金の管理・消し込みの操作の対象になり、月次決算では損益計算書 (PL) と貸借対照表 (BS) を見る
- **アクター (6)**: 請求担当、支払担当、経費担当、記帳担当、経理責任者、経営者。**外部アクター (5)**: 得意先、仕入先、従業員、銀行、税理士
- **システム (3)・帳票 (3)**: 会計システム、販売管理システム、インターネットバンキング / 受領した請求書 (紙)、経費精算書 (紙)、小口現金出納帳
- **作業 (22)・操作 (17)**、情報 12 (請求書・売掛金・入金・仕入先の請求書・買掛金・支払・経費の申請・仕訳・小口現金・試算表・損益計算書・貸借対照表)、状態 9 (売掛金・支払・月次決算の各 3)、バリエーション 3 (入金の方法・経費の区分・税区分)、条件 3
- **課題 (5)**: 月末月初に入金の消し込みが集中し月次決算が遅れる (重要度 5。現象・所在・理由・影響の分析つき)、紙の請求書を手で入力している (4)、経費精算が紙で確認と差し戻しに時間がかかる (4)、月次の損益があとから直される (3)、仕訳の手順が担当者ごとに違う (2)
- **ボード (3)**: 全体、請求・支払から決算まで、情報と状態

困りごとの傾向は、経理業務の解説記事 (紙の請求書の手入力、月末月初の入金消込の集中、少人数での兼任と属人化) を参考にした。文章は写さず、数や会社名はすべて架空。

## 9. テスト

Vitest で以下を検証する。E2E は省く。

- モデル: id 生成、要素の追加・削除と付随処理 (既定 BUC、関係・ノード・課題対象の掃除)、所属の変更。
- 関係ルール: 表にある組み合わせは引け、ない組み合わせは引けない。重複と自己参照の拒否。無向関係の同一視。
- 検証: スキーマに合わない JSON とエラー内容。参照整合性の各ケース。
- Undo / Redo: 連続操作と履歴上限。
- サンプル: スキーマ検証と参照整合性検査を通る。
- 固定ボード: 各レイヤーの枠の組み立て、絞り込み、枠への追加・既存の紐づけ・外す。
- UI: 要素一覧・固定ボード・プロパティ欄・ツールバーの主要な振る舞い (自由ボードで所属・関係を変えられないことを含む) を Testing Library で確認する。キャンバスは React Flow のノード・エッジへの変換 (座標の相対化を含む) を純粋関数として切り出し、その関数をテストする。
- クラウド版 (詳細は collab-design 11 章): 権限の規則 `can` と API の契約 (`packages/api`)、Y.Doc の往復・合流・修復 (`packages/collab`。`rebuildModel(applyModelDiff(a, b)) ≡ b` をランダムなコマンド列で確かめる)、サーバー (`apps/server`。`@cloudflare/vitest-plugin` で workerd の中に本物の D1 と Durable Object を立て、ログイン・セッション・権限・招待・リンク・ルームの接続と kick・cron を確かめる)、クラウドのストアと接続 (2 つの Y.Doc をつなぐ)、ホーム・共有ダイアログ・招待・リンクの画面、デスクトップのログインと Web の Platform。
- 生成物: `pnpm check:types` が、スキーマから生成した型と検証関数が最新かを確かめる。
- `pnpm test` がルートから全プロジェクトを走らせ、`pnpm typecheck` (`tsc -b`) が全パッケージの型を検査する。

## 10. ビルドと配布

- `pnpm dev` で Web 版 (Vite、5174) を、`pnpm dev:cloud` でクラウド版の画面 (Vite、5173) とサーバー (`wrangler dev`、8787) を同時に動かす。`pnpm tauri dev` でデスクトップアプリ、`pnpm app:build` (手元の証明書で署名) か `pnpm tauri build` で Mac 用 .app / .dmg。
- **Web 版**: Cloudflare Pages (プロジェクト `untie`)。`pnpm web:deploy` か、Pages の Git 連携 (Build command `pnpm --filter @untie/web build`、出力 `apps/web/dist`)。手順は README の「Web 版の配信 (Cloudflare Pages)」。
- **クラウド版とサーバー**: 1 つの Cloudflare Worker (`apps/server`、名前は `untie-cloud`) がクラウド版の画面 (`apps/cloud`) の静的ファイル・API・ログイン・Durable Object を持つ。`pnpm cloud:deploy` が画面を build して `wrangler deploy` する。初回の手順 (D1 の作成、OAuth クライアント、秘密の値、`APP_ORIGIN`) は README の「クラウド版の配信 (Cloudflare Workers)」、設計は collab-design 2.3・9 章。
- GitHub Actions:
  - `ci.yml`: PR と main push で `pnpm check:types`、`pnpm typecheck`、`pnpm test`、`pnpm build` (Web 版・クラウド版・デスクトップのフロントの build と `wrangler deploy --dry-run`)。別のジョブで Linux の `cargo check` (Rust 側がコンパイルできるか)。
  - `release.yml`: `v*` タグ push で `tauri-apps/tauri-action` を使い、`macos-latest` (aarch64-apple-darwin) で .dmg、`windows-latest` で .msi と .exe (NSIS) を作り、GitHub Releases に添付する。
- Windows 版は CI でしか作れないため、動作確認は CI の成果物で行う。
- 署名なしなので、README に開き方 (Mac は右クリック → 開く、Windows は SmartScreen の「詳細情報」→「実行」) を書く。
