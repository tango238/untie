# Untie PoC 設計書

Untie は、現場担当者が自分の業務を言語化するための業務可視化ツールである。人・作業・情報・ルール・判断をカードにし、図の上で関係を整理する。将来は RDRA モデルに展開して要件定義につなげる。

この PoC では「カードと図で業務要素と関係を編集する体験」を確かめる。モデルは JSON ファイルに保存・読み込みできる。AI エージェント (会話でモデルを直す・初期要望からモデルを作る) を持つ (6.2)。RDRA 出力は対象外だが、データモデルはそれに耐える形にしておく。

## 1. 前提と範囲

| 項目 | 内容 |
| --- | --- |
| 配布形態 | Tauri 2 デスクトップアプリ。Mac (Apple Silicon) と Windows (x64)。署名なし |
| 技術 | TypeScript / React 18 / Vite / Vitest / pnpm、zustand + immer、ajv、@xyflow/react (React Flow)、Tauri 2 |
| アプリ名 | Untie、識別子 `net.tech-square.untie`、バージョン 0.1.0 |
| 永続化 | JSON ファイルに保存・読み込みする (6.1)。起動時はサンプルを開く |
| 言語 | UI・ドキュメント・コメントはすべて日本語 |
| 対象外 | 文章からの要素抽出、矛盾検出、rdra.yml 出力、コード署名、Intel Mac |

Rust ツールチェーンは rustup の stable (`~/.rustup/toolchains/stable-aarch64-apple-darwin/bin`) を使う。`~/.cargo/bin` は無いので、ローカルで `pnpm tauri build` するときはこのパスを `PATH` に加える。

## 2. 要素 (カード) の種類

14 種。RDRA の「画面」とイベントストーミング要素 (イベント・ポリシー・集約) は持たない。メモカードは入れず、各要素の説明欄で代用する。

| kind | 表示名 | 役割 | 種類固有の項目 |
| --- | --- | --- | --- |
| `actor` | アクター | 業務を行う社内の人・役割 | なし |
| `externalActor` | 外部アクター | 顧客・取引先など、社外の人や組織 | なし |
| `system` | システム | 情報システム (自社・社外を問わない)。作業の担当にも、情報の取得元・保存先にもなる | なし |
| `ledger` | 帳票 | 紙の台帳・伝票。情報の取得元・保存先にだけなる | なし |
| `business` | 業務 | 業務のまとまり。ボード上では枠 (グループノード) | なし |
| `buc` | 活動 (BUC) | 業務の中の作業のまとまり (Business Use Case)。任意 | `businessId`、`isDefault` |
| `activity` | 作業 (アクティビティ) | 業務の中の個々の作業 | `bucId` (null 可)、`links` (リンク、任意)、`hours` (時間、任意) |
| `usecase` | 操作 (ユースケース) | システムに期待する振る舞い | `links` (リンク、任意)、`hours` (時間、任意) |
| `context` | コンテキスト | 役割の同じ情報と、関係の深い状態・条件・バリエーションをまとめる親カテゴリ。関係は持たない | なし |
| `information` | 情報 | 業務で扱う情報 | `contextId` (null 可) |
| `state` | 状態 | 情報やモノの状態 | `group` (状態グループ、任意)、`contextId` (null 可) |
| `variation` | バリエーション | 種別・区分と、その値の一覧 | `values: string[]`、`contextId` (null 可) |
| `condition` | 条件 | 判断の条件・ルール | `contextId` (null 可) |
| `issue` | 課題 | 現場で困っていること。自由ボードには置かない | `severity` (1〜5)、`targetIds` |

画面の表示名は RDRA の用語と変えている: `buc` は「活動」、`activity` は「作業」、`usecase` は「操作」と出す (現場担当者に通じる言葉にするため)。この設計書とコード・スキーマは RDRA の用語 (BUC・アクティビティ・ユースケース) のまま書く。

全要素に共通: `id` (安定した文字列)、`kind`、`name`、`description` (任意の説明文)。

### 2.1 業務 ⊃ BUC ⊃ アクティビティ

- 業務・BUC・アクティビティ・ユースケースの 4 段をモデルに持つ。BUC は任意。
- 業務を作ると、その業務の **既定 BUC** (`isDefault: true`、名前は業務名と同じ) が自動で 1 つ作られる。既定 BUC はボードにも要素一覧にも出さない。
- アクティビティは `bucId` で BUC を 1 つ指す。業務の枠に直接置いたアクティビティは、その業務の既定 BUC に入る。
- 業務ごとに、作業は「すべて業務に直接 (既定 BUC)」か「すべてどれかの活動 (既定でない BUC)」のどちらかにする (混ぜない)。業務に初めて活動を作ると (活動の固定ボードの「＋活動」)、業務に直接あった作業はその活動へ移る (作成と移動で 1 件の履歴)。プロパティ欄の活動のセレクトは、活動のある業務では「(業務に直接)」を出さない。スキーマとコマンドは混ざったデータも受け付ける (古いファイルや AI の作成のため) が、作業のボードで知らせる。
- BUC を作りたい人は、業務の枠の中に BUC の小枠を作り、アクティビティをそこへドラッグして移す。
- `bucId` が null のアクティビティ (未所属) も許す。現場担当者が業務を決める前に作業を書き出せるようにするため。rdra 出力では未所属を出せないので、出力時に警告する (将来の TODO)。
- 既定 BUC は削除できない。既定でない BUC を削除すると、所属アクティビティは業務の既定 BUC に戻る。業務を削除すると、その BUC は全て消え、所属アクティビティは未所属になる。

### 2.2 担い手と置き場所 (システム・帳票) とコンテキスト

役割で 2 つに分け、種類をこれに合わせる。

| | 作業をする (担い手) | 情報を取り出す・残す (置き場所) |
| --- | --- | --- |
| アクター | ○ | – |
| 外部アクター | ○ | – |
| システム | ○ | ○ |
| 帳票 | – | ○ |

- システムは情報システム。自社のものも社外のもの (予約サイト・決済サービスなど) も含む。実際のシステムはデータを持ちつつ自動で作業もするので、両方の役割を兼ねる。作業とは `actorActivity` (担当) で結ぶ。
- 帳票は紙の台帳・伝票。作業はしないので、置き場所の役割だけを持つ (画面では破線で描く)。紙をシステムと同じ種類にすると「システムは担当になれる」が紙のときだけ成り立たなくなるため、別の種類にした。関係のルールは種類だけで決まる。
- 外部アクターとシステムの線引きは「人か仕組みか」の 1 本にする。社外の人・組織は外部アクター、仕組みは自社・社外を問わずシステム。予約サイトのように両方に読めるものは、契約や電話でやり取りする相手なら外部アクター、データをやり取りする仕組みならシステムとする。自社か社外かの印は持たない (RDRA のシステム境界を描くときに要れば足す)。
- 置き場所と情報は `systemInformation` (取得元) と `informationSystem` (保存先) で結ぶ (システム・帳票の両方)。
- コンテキストは RDRA のコンテキストに合わせる。中心は情報で、役割の同じ情報と、それに関係の深い状態・条件・バリエーションをまとめる。この 4 種類は `contextId` で 1 つを指す (null は未分類)。状態は状態グループごとに属する (グループ内の状態はまとめて移し、既にあるグループに足した状態はそのグループのコンテキストになる)。
- 所属は人が決める。条件やバリエーションは複数のコンテキストにまたがりやすく、どこに入れるかは設計上の判断だから。代わりに、つながりから候補を出す (`src/model/contexts.ts`)。直接つながる所属要素 (関連する情報、参照する状態・バリエーションなど) は重み 2、操作を介してつながる情報は重み 1 で数え、いちばん重いコンテキストを候補にする。
- コンテキスト自体はほかの要素と関係を持たない。コンテキストどうしの関係 (結合度) は、所属する要素の関係から導く。コンテキストを削除すると、所属していた要素は未分類になる。

### 2.3 課題

- 独立した要素で、`targetIds` に対象の id を複数持てる (0 件も可)。課題を先に書き出し、あとから対象を付けて紐解けるよう、対象なしで作れる。
- 対象の種類で 2 つの区分に分かれる。区分は保存せず、対象から決める (`issueScope`)。
  - **全体的な課題**: 登場人物 (アクター・外部アクター・システム・帳票) が対象。その登場人物全体にかかわる課題。
  - **具体的な課題**: 業務・作業・操作が対象。特定の業務や操作で起きている課題。
  - 対象がまだ無い課題は **未整理** とする。
- 1 つの課題の対象に、登場人物と業務・作業・操作を混ぜない (コマンドで拒否し、検証でエラーにする)。区分を変えるときは、いまの対象を外してから別の区分の対象を付ける。
- `severity` は 1 (低) 〜 5 (高) の整数。
- ボードには置かない。課題一覧パネル (5.5) で作り、区分ごとに見る。対象カードにはバッジ (件数と最高重要度) を出す。
- 対象要素を削除すると、その id は `targetIds` から外れる。課題自体は残る。

## 3. 関係 (線) の種類

関係は RDRA に沿った型付きのみ。両端の要素の種類から関係の種類が自動で決まり、表にない組み合わせは引けない。自由な線はない。

| relation kind | 始点 → 終点 | 意味 (RDRA での対応) |
| --- | --- | --- |
| `actorBusiness` | アクター → 業務 | 業務の主担当 (`business.main_actor`) |
| `actorActivity` | アクター / 外部アクター / システム → アクティビティ | 作業を行う担い手 (`activity.used_by`) |
| `activityUsecase` | アクティビティ → ユースケース | 作業で使うユースケース (`activity.usecase`) |
| `usecaseInformation` | ユースケース → 情報 | 扱う情報 (`usecase.information`) |
| `usecaseCondition` | ユースケース → 条件 | 判断に使う条件 (`usecase.condition`) |
| `informationRelated` | 情報 ↔ 情報 | 関連する情報 (`information.related`)。無向 |
| `informationVariation` | 情報 → バリエーション | 情報の種別 (`information.variation`) |
| `systemInformation` | システム / 帳票 → 情報 | 情報の取得元 |
| `informationSystem` | 情報 → システム / 帳票 | 情報の保存先 |
| `conditionVariation` | 条件 → バリエーション | 条件が参照する種別 (`condition.variation`) |
| `conditionState` | 条件 → 状態 | 条件が参照する状態 (`condition.state`) |
| `stateUsecase` | 状態 → ユースケース | この状態で実行できるユースケース |
| `usecaseState` | ユースケース → 状態 | 実行後に遷移する次の状態 (`next_state`) |

ルール:

- 関係は `id`、`kind`、`sourceId`、`targetId` を持つ。`kind` は両端の種類から一意に決まり、保存時も冗長に持つ (スキーマ検証とエクスポートを単純にするため)。
- 同じ `(kind, sourceId, targetId)` の関係は 1 本まで。`informationRelated` は無向なので `(a, b)` と `(b, a)` を同一とみなし、重複を拒否する。
- 自己参照 (`sourceId === targetId`) は不可。
- 線はボードごとではなくモデル全体の関係である。両端がボードに置かれていれば、どのボードでも同じ線が表示される。
- 画面では、`informationRelated` は矢印なし、それ以外は終点に矢印。線の上に関係名の短いラベルを出す (例: 「担当」「使う」「次の状態」)。
- 状態遷移は `stateUsecase` と `usecaseState` の 2 本で表す。1 つのユースケースに前の状態と次の状態がそれぞれ複数ある場合、組み合わせが曖昧になる。rdra 出力の TODO で、3 項関係 (前状態・ユースケース・次状態) への拡張か、全組み合わせとして出力するかを決める。

### 3.1 関係の自動判定

`relationKindFor(sourceKind, targetKind)` が上の表を引き、該当なしなら `null` を返す。React Flow の `isValidConnection` でこの判定を使い、引けない組み合わせはドラッグ中に接続不可として扱う。接続時にすでに同じ関係があればトーストで知らせて何もしない。

## 4. データモデル

スキーマは `schema/untie.schema.json` (JSON Schema 2020-12) に定義し、`json-schema-to-typescript` で `src/model/schema.d.ts` を生成する。型とスキーマがずれないよう、CI で生成結果の差分を検査する (json-gantt と同じ方式)。

```
UntieModel
├ version: 1
├ meta: { name, description? }
├ elements: Element[]      … 14 種を kind で判別する
├ relations: Relation[]    … 型付きの関係
└ boards: Board[]
   └ nodes: BoardNode[]    … { elementId, x, y, width?, height? }
```

設計方針:

- **安定 id**: 要素・関係・ボードは作成時に `kind の短い接頭辞 + ランダム文字列` の id を得る (例 `act_k3f9x2`)。名前を変えても id は変わらない。参照は全て id で行う。
- **座標の分離**: 要素は業務データ (`elements`) に、座標はボード (`boards[].nodes`) に持つ。1 モデルに複数ボード、同じ要素を複数ボードに置け、座標はボードごと。
- **座標はボード内の絶対座標**で持つ。React Flow は親ノードの子に相対座標を要求するので、ボードを描画するときに親 (業務・BUC の枠) の座標を引いて相対にし、ドラッグ終了時に足し戻す。親の有無でモデルの座標の意味が変わらないようにするため。
- 業務・BUC の枠は `width`・`height` を持つ。それ以外のカードは省略し、表示側の既定サイズを使う。
- 課題はボードに置けない。既定 BUC もボードに置けない (業務の枠の中に直接アクティビティを置く)。
- 参照整合性 (存在しない id を指さない、`bucId` の BUC・`contextId` のコンテキストが存在する、`targetIds` が 業務/アクティビティ/ユースケース を指す、など) は JSON Schema では表現できないので、`validateModel()` でスキーマ検証に続けて検査する。

### 4.1 ボードの種類

ボードは**固定ボード**と**自由ボード**の 2 種類。

- **固定ボード**: レイヤーごとに 1 枚ずつ、計 10 枚。上位の要素を枠にして、その下に下位の要素を自動で並べる。位置は動かせない。上のレイヤーから順に下のレイヤーを詳細化するための場所で、要素の作成・削除、所属と関係の変更はここで行う。モデルには保存せず、毎回モデルから組み立てる (スキーマは変えない)。id は `fixed:<レイヤー>`。
- **自由ボード**: モデルの `boards`。レイヤーに関係なく要素を置き、位置と大きさを自由に決める。変えられるのは配置 (置く・外す・位置・大きさ) と名前・説明だけで、所属・関係・要素の作成と削除はできない。

### 4.2 固定ボード

| レイヤー | 枠 (上位) | 枠に並ぶもの | 枠との結びつき |
| --- | --- | --- | --- |
| 登場人物 | 「アクター」「外部アクター」「システム」「帳票」 | アクター / 外部アクター / システム / 帳票 | なし |
| 業務 | アクター | 主担当の業務 | 関係 `actorBusiness` |
| BUC | 業務 | BUC (既定 BUC は出さない) | 所属 `businessId` |
| アクティビティ | 活動の無い業務 (業務 (活動なし) の枠) と活動 | アクティビティ | 所属 `bucId` |
| ユースケース | アクティビティ (BUC ごとの段落に分ける) | 使うユースケース | 関係 `activityUsecase` |
| コンテキスト | コンテキスト | 属する情報・条件・状態・バリエーション (この順) | 所属 `contextId` |
| 情報 | コンテキスト | 情報。カードに取得元・保存先のシステム・帳票を出す | 所属 `contextId` |
| 条件 | ユースケース | 判断に使う条件 | 関係 `usecaseCondition` |
| 状態 | 状態グループ (`group`) | 状態 | 属性 `group` |
| バリエーション | 情報 | 種別のバリエーション | 関係 `informationVariation` |

- 関係で結ぶ枠では、同じ要素が複数の枠に出る (例: 複数のアクティビティから使われるユースケース)。どの枠にもつながらない要素は「主担当なし」「アクティビティなし」などの枠にまとめる (中身があるときだけ出す)。アクティビティの「未所属」、情報の「未分類」も同じ。状態の「グループなし」は、新しいグループを始める場所として常に出す。
- 作業のボードは、活動の無い業務には業務の枠 (活動なし) を、活動のある業務には活動の枠だけを出す。活動のある業務に業務直下の作業が残っているときだけ、業務の枠を「活動に移してください」の知らせ付きで出し、その枠では「＋作業」を出さない。
- ユースケースのボードは、アクティビティの枠を所属する BUC ごとの段落に分け、見出しと区切り線を付ける。段落の並びはアクティビティのボードと同じ (業務ごとに既定 BUC → BUC)。アクティビティの無い BUC の段落は出さない。BUC に属さないアクティビティは「未所属」、どのアクティビティにも使われていないユースケースは「アクティビティなし」の段落にまとめる。段落の見出しをクリックすると、その BUC (既定 BUC なら業務) を選ぶ。絞り込みで段落の見出しが一致したときは、その段落の枠をすべて出す。
- コンテキストのボード: コンテキストごとの枠に、属する情報・条件・状態・バリエーションを並べる。見出しの「＋コンテキスト」でコンテキストを作る (枠の見出しを押すと選んでプロパティ欄で編集する)。枠には 4 種類それぞれの「＋」と、別のコンテキスト (または未分類) の要素を移す「別のコンテキストから移す…」を出す。× で外すと未分類になる。状態は状態グループごとに属するので、移す・外すとグループの状態がまとめて動く。未分類の枠は中身があるときだけ出す。
- ボードの選択肢では、コンテキストを固定ボードの最後 (バリエーションの下) に置く。情報・条件・状態・バリエーションをまとめて見る場所なので。トレースやグローバルフィルターのレイヤーの並びは変えない。
- グローバルフィルター: すべての固定ボードに共通の絞り込み。各固定ボードの上に置き、レイヤーごとに要素を 1 つ以上選べる (選んだ要素はチップで出し、× で外せる。「リセット」で全部消す)。選んだ要素からトレースと同じく上下へ辿って届く要素だけを出す。レイヤーの中は「どれかにつながる」(OR)、レイヤーどうしは「すべてにつながる」(AND)。コンテキストは分類なので、選ぶと属する要素から上へも辿る。合う要素のコンテキストと、合う情報の置き場所 (システム・帳票) も出す。見出しの要素が合う枠は中身が無くても残し、それ以外の枠は中身が無ければ出さない。名前の絞り込みとも併用できる。保存せず、履歴にも入れない (ファイルを開くと消える)。
- すべての固定ボードの見出しの下に「書き方のヒント」を出す。ボードで扱う要素と取り違えやすい要素を並べた表 (何を書くか・粒度の目安・書き方・例・大きすぎる例・細かすぎる例) と、迷ったときの問いで、今のボードの種類を強調する。並べる組は、登場人物 = アクター・外部アクター・システム・帳票 (4 種類ともボードに出るので強調しない)、業務 = 業務・活動・作業、活動・作業・操作 = 活動・作業・操作、コンテキスト・情報・バリエーション = コンテキスト・情報・バリエーション、状態・条件 = 状態・条件。大きすぎる例・細かすぎる例には「何に当たるか」を書き、どこへ移せばよいかわかるようにする。最初は閉じておき、開閉の状態は固定ボード全体で覚える (履歴に入れない)。文言は `src/components/granularity.ts` にまとめる。プロパティ欄でも、課題以外の要素の名前欄の下に書き方を 1 行出す。
- 枠の「＋<種類>」で、その枠に結びついた要素を作る (作成と結びつけで 1 件の履歴)。作ったら選択し、プロパティ欄の名前欄にフォーカスする。
- 関係で結ぶ枠では、「既存から足す」で既にある要素を結べ、カード横の × で枠から外せる (関係を消すだけで、要素は残る)。所属で決まる枠 (BUC・アクティビティ・情報・状態) の移動はプロパティ欄で行う。
- 枠の見出し (上位の要素) やカードをクリックすると、その要素を選択してプロパティ欄に出す。
- 上部の「絞り込み」で名前を絞り込む。見出しが一致した枠は中身をすべて出し、それ以外の枠は一致した要素だけを出す。何も一致しない枠は出さない。絞り込みの文字列は固定ボードごとに覚え、履歴には入れない。
- 業務・アクティビティのカードには担当アクター名のラベルを出す (4.4 参照)。

### 4.3 自由ボード

- 業務は枠 (グループノード)。枠の中に BUC の小枠と、既定 BUC のアクティビティを描く。
- アクティビティ・BUC は、所属先の業務の枠 (BUC なら BUC の小枠) が同じボードにあれば、その枠の子として描く。枠がなければ単独のカードとして描き、業務名 (BUC なら「業務名 / BUC 名」) をカードのラベルに出す。
- 所属は変えられないので、枠の外へドラッグしても、別の枠に入れても、要素一覧から枠の上に置いても所属は変わらない。枠を動かすと、所属する子孫も同じ量だけ動く。
- 枠のリサイズ (左端・上端を含む) は枠の位置と大きさだけを変え、子孫の位置 (絶対座標) は動かさない。
- 線 (関係) は表示するだけで、引くことも消すこともできない。接続ハンドルは見せない。
- 線の付け根はボードごとに変えられる。既定は始点の右の辺から出て終点の左の辺に入る。線を選ぶとプロパティ欄に「線の付け根 (このボードだけ)」が出て、始点・終点それぞれ左・右・上・下の辺を選べる (「入れ替え」で両端を入れ替える)。`boards[].edges` に `{ relationId, sourceSide?, targetSide? }` で持ち、既定の辺は省略し、両方とも既定なら項目ごと消す。関係を消すと各ボードの項目も消す。
- 同じ要素を同じボードに 2 回置くことはできない。座標はボードごと。

### 4.4 アクターの担当のラベル

- アクターの担当 (`actorBusiness`・`actorActivity`。作業の担当にはシステムも含む) は線を引かず、相手の業務の枠のタイトル行・アクティビティのカードに担当名のラベルで出す (固定ボードでは業務・アクティビティのカード)。業務とアクティビティを結ぶ線が多く、図が読みにくくなるため。
- ラベルはアクターがボードに置かれているかに関係なく出る。外部アクターは色を分ける。カードでは 1 行に収め、入りきらない名前は省略する (マウスを乗せると全文)。

### 4.5 分析ボード

固定ボードと同じく中央を広く使い、2〜3 レイヤーをまたいで見渡す表。モデルには保存せず、毎回モデルから組み立てる (`src/model/analysis.ts`)。id は `analysis:<種類>`。要素名をクリックすると選択してプロパティ欄に出す。分析ボードで変えられるのは、自由ボードと同じく名前・説明・時間・リンクだけ。

| ボード | 見渡すレイヤー | 何がわかるか |
| --- | --- | --- |
| 課題の分布 | 業務 → 作業・操作 → 課題 | 業務ごとに、業務・その作業・作業が使う操作に付いた課題 (具体的な課題) を重要度順に集める。どの業務にも辿れない具体的な課題は最後にまとめる。全体的な課題は下に別の表で登場人物ごとに、未整理の課題 (対象なし) はその下に別の表で出す |
| 担当別の作業一覧 | 担い手 → 業務・活動 → 作業 → 操作 | 担い手 (アクター・外部アクター・システム) ごとの作業と、作業・操作のリンク (マニュアルなど)。担い手で絞り込める。担当の無い作業は最後にまとめる |
| 情報の所在 | 情報 → システム・帳票 → 操作 | 情報 × 置き場所の表に取得・保存を出す。置き場所なし・紙だけ・保存先が複数 (二重管理の可能性) に印を付ける |

│ ファイル: hotel.json  ● 保存していない変更があります                             │
├──────────┬────────────────────────────────────┬───────────────┤
│ 要素一覧  │ 固定ボード (自動で並ぶ)  [絞り込み___] │ プロパティ     │
│ ▸ アクター │ ┌ チェックイン 業務(BUC なし) ┐ ┌ 客室対応 ┐ │               │
│ ▸ 業務    │ │ [本人確認をする] フロント担当│ │ [...]   │ │ 名前          │

起動時・新規作成・ファイルを開いたときは、分析ボード「課題の分布」を開き、右ペインは課題一覧を開いておく (課題から紐解くため)。固定ボード・分析ボードでは左の要素一覧を出さない (図は自由ボードのときの 3 カラム)。

### 5.1 ツールバー

- 「ファイル」メニュー: 新規作成・開く・保存・別名で保存 (6.1)、プロンプトから作成・AI の設定 (6.2)。ショートカットは Cmd/Ctrl+O、Cmd/Ctrl+S、Shift+Cmd/Ctrl+S (入力欄の中でも効く)。
- 「AI」: 下に AI エージェントのペインを開閉する (6.2)。
- ボード切替 (セレクト)。「固定ボード」(10 枚)・「分析ボード」(3 枚。課題の分布を先頭に置く)・「自由ボード」のグループに分ける。
- 「＋ボード」は自由ボードを追加して切り替える。名前変更・ボード削除は自由ボードだけ (最後の 1 枚は削除できない。確認ダイアログあり)。
- 要素の作成は固定ボードの枠で行うので、ツールバーに「追加」メニューは置かない。
- Undo / Redo ボタン。ショートカットは Cmd/Ctrl+Z と Shift+Cmd/Ctrl+Z (Ctrl+Y も Redo)。
- 「検証」: 右側に検証パネルを出す (プロパティ欄と切り替え)。アクター／外部アクターに辿り着けない要素があれば、その件数をボタンに出す。
- 「課題一覧」: 右側に課題一覧パネルを出す (プロパティ欄と切り替え)。
- ツールバーの下に、開いているファイル名 (サンプルなら「サンプル (まだ保存していません)」) と、保存していない変更があればその印を出す。

### 5.2 要素一覧 (左)

- 自由ボードのときだけ出す。固定ボードは上位の要素から順に辿るので一覧は出さず、中央を広く使う。
- 左上の「‹」で閉じられる。閉じると左端に細い帯だけ残して「要素一覧」と縦書きで出し、帯か「›」で開き直す。右のペインと同じく、開閉は保存せず、履歴にも入れない。
- 種類ごとに折りたたみ。各行は名前と、課題バッジ (あれば)。BUC の行には「業務: 業務名」を添える。
- 行をクリックすると選択し、現在のボードにあればそのカードへスクロールする。
- 自由ボードでは、現在のボードに置かれているかの印を出し、行をキャンバスへドラッグするか、右クリック・行末の「置く」で現在のボードに置ける (すでにあれば何もしない)。固定ボードでは置く操作は出さない。
- 既定 BUC は出さない。

### 5.3 中央

- 固定ボード: 4.2 のとおり、枠を格子状に並べた HTML。上部に見出し・説明・絞り込み。
- 自由ボード: React Flow。ノード種別は `frame` (業務・BUC の枠)、`card` (その他の要素)。カードは種類ごとに色を変え、左上に種類名、中央に名前、右上に課題バッジ (対象になれる種類のみ) を出す。業務の枠はタイトル行に業務名と主担当のラベル、BUC の小枠はタイトル行に BUC 名。枠はリサイズできる。
- 自由ボードの Delete キーは選択中のノードをボードから外す (要素は残る)。線は消せない。固定ボードでは Delete キーは何もしない。
- 線は枠・カードより上に描く。枠の中やカードの上を通る線もクリックで選べる (その分、線が重なる所ではカードより線が先に当たる)。

### 5.4 プロパティ欄 (右)

- 右のペイン (プロパティ欄・課題一覧・検証) は右上の「›」で閉じられる。閉じると中央を広く使い、右端に細い帯だけ残して、いま何のペインかを縦書きで出す。帯か「‹」で開き直す。ツールバーの「検証」「課題一覧」を押したときも開く。開閉は保存せず、履歴にも入れない。

選択中の要素の内容を編集する。固定ボードではすべて編集でき、自由ボードでは名前と説明だけを編集できる (他の欄は無効にし、その旨を出す)。

- 共通: 種類 (表示のみ)、名前、説明。
- 作業・操作: 時間 (時間単位、小数点第一位まで。0 以上。空にすると消す)。作業では、使う操作の時間の合計を「操作の合計」として作業自身の時間とは分けて出す (時間の入った操作が無ければ出さない)。固定ボードのカードと分析ボードの担当別の作業一覧 にも、作業自身の時間と操作の合計を分けて出す。同じ操作を複数の作業が使う場合は、それぞれの作業の合計に入る。名前・説明と同じく自由ボードでも編集できる。
- 作業・操作: リンク (表示名と URL。マニュアルなど)。複数持て、並べ替え・削除でき、名前をクリックすると既定のブラウザで開く (デスクトップは opener プラグイン)。URL は http / https だけ。名前・説明と同じく自由ボードでも編集できる。固定ボードのカードにはリンクの件数を出す。
- アクティビティ: 業務と BUC のセレクト (未所属を含む)。
- BUC: 業務のセレクト。
- 情報・状態・条件・バリエーション: コンテキストのセレクト (未分類を含む。状態は状態グループごと)。つながりから見た候補が今の所属と違えば、候補と「〇〇にする」ボタンを出す。状態: 状態グループ。バリエーション: 値の一覧 (追加・削除・並べ替え)。
- 課題: 重要度 (1〜5)、区分 (全体的・具体的・未整理)、対象の一覧 (種類・名前・そのレイヤーの固定ボードへ移る「移動」・外す)。「対象を追加」はレイヤーごとに分けて出し、対象があるときは同じ区分の候補だけを出す。別の区分に付け替えるときは、いまの対象をすべて外してから追加する。
- 関係一覧: この要素が始点または終点になっている関係を、関係名・向き・相手の種類 (レイヤー名) 付きで一覧し、相手をクリックで選択する。固定ボードでは × で関係を消せ、「関係を追加」のセレクトで結べる要素 (関係名・向き・種類ごと。既にある関係は除く) を選んで関係を足せる。固定ボードの枠で表せない関係 (担当アクター、情報の取得元・保存先、情報どうしの関連、条件とバリエーション・状態、状態とユースケース) はここで編集する。
- トレース (関係と課題の間): 要素から上 (担い手の側) と下 (詳細の側) へ、直接つながっていない要素まで辿り、レイヤーごとに 1 行で表にする (`src/model/lineage.ts`)。列はレイヤー・要素・移動。上は登場人物の側から、下は近い順に並べ、自分の行を間に置く。要素名をクリックするとその要素を選ぶ。「移動」はそのレイヤーの固定ボードへ、今の要素を選んだまま移り、その要素のカードか、その要素が見出しの枠 (無ければ所属先や関係で結ばれた要素) までスクロールする。要素が枠や段落の見出しになっているボードでは、その枠・段落を選択中として出す。1 行に 7 件以上あるときは 6 件まで出し、「ほか N 件」で開く。辿る向きは、業務 → 主担当、活動 → 業務、作業 → 活動 (業務に直接なら業務)・担当、操作 → 作業、情報 → 操作・コンテキスト・置き場所、条件 → 操作・コンテキスト、状態 → 操作・条件・コンテキスト、バリエーション → 情報・条件・コンテキスト (下へはこの逆)。情報どうしの関連は同じレイヤーなので辿らない。コンテキストは分類なので、上へは属する要素から辿る。 つながる要素が無くても、その種類の上下に来うるレイヤーは「(未設定)」(灰色) の行で出し、「移動」でそのレイヤーの固定ボードへ移れる (結ぶ相手を作りに行けるように)。来うるレイヤーは種類で決める (例: 帳票の下は情報・バリエーションだけ、外部アクターは業務の主担当にならないので下に業務を出さない)。
- 課題: この要素を対象にしている課題の一覧と「課題を追加」ボタン (登場人物・業務・作業・操作のみ。固定ボードだけ)。見出しに区分 (登場人物なら全体的な課題、業務・作業・操作なら具体的な課題) を添える。
- 自由ボードでは「ボードから外す」(ボードにある場合)、固定ボードでは「削除」。
- 課題では左端に「削除」を出し、課題を削除すると課題一覧へ戻る。右端は作ったばかりかどうかで変える。
  - 追加フォーム (「＋課題」「課題を追加」で作った直後): 「次の課題を登録する」。作ったときと同じ対象で次の課題を作り、名前の入力へ移る。続けて書き出せるようにするため。
  - 編集フォーム (既存の課題を選んだとき、または別の要素を選んでから戻ったとき): 「課題一覧に戻る」。
- 関係 (線) を選択したときは、関係名と両端の要素を出す (削除は無い)。

### 5.5 課題一覧パネル

最初に課題を書き出し、それを紐解くように整理するための場所。

- 見出しの「＋課題」で対象のない課題を作り、選んでプロパティ欄の名前の入力へ移る。どのボードからでも作れる。
- 課題を 未整理・全体的な課題・具体的な課題 の 3 段に分ける。課題の無い段には、何を入れる段かの説明を出す。
- 並べ方は「課題ごと」と「対象ごと」を切り替えられる (保存しない)。
  - 課題ごと: 段ごとに重要度の高い順 (同じなら名前順)。各行は重要度、名前、対象要素の種類と名前。
  - 対象ごと: 全体的・具体的の段を、対象の要素ごとにまとめる。まとまりの見出しに種類・名前・そのレイヤーの固定ボードへ移る「移動」・その要素を対象にした課題を作る「＋課題」を出す。対象は 登場人物 → 業務 → 作業 → 操作 の順、同じ種類は名前順。対象が複数ある課題は、それぞれのまとまりに出る。未整理の段はいつも課題ごとに並べる。
- 行をクリックするとその課題を選択してプロパティ欄に切り替える。対象名をクリックすると対象要素を選択する。
- 課題はどのボードにも出ないので、プロパティ欄では自由ボード・分析ボードでも重要度・対象を編集でき、削除できる。

### 5.6 検証パネル (担い手まで辿れるか)

すべての要素が担い手 (アクター／外部アクター／システム) まで辿れるかを調べる (`src/model/trace.ts`)。つながりは必須にしない。上から順に書き出していく途中の状態 (担当の決まっていない作業など) を作れるようにするため。代わりに、辿り着けない要素とどこで途切れているかを知らせる。

- 要素ごとに「担い手に近い側」を決め、担い手から下へ広げて届いたものを「辿り着ける」とする。

| 要素 | 担い手に近い側 |
| --- | --- |
| 業務 | 主担当のアクター |
| 活動 (BUC) | 業務 |
| 作業 | 担当のアクター／外部アクター／システム (必須。所属の活動・業務からは辿らない) |
| 操作 | 使う作業 |
| 情報 | 扱う操作、関連する情報 |
| コンテキスト | 入っている情報 |
| システム | 担い手なので辿り着く先。ただし作業の担当にも情報の置き場所にもなっていなければ途切れとする |
| 帳票 | 取得元・保存先として結んだ情報 |
| 条件 | 判断に使う操作 |
| バリエーション | 種別にしている情報・条件 |
| 状態 | 実行可・次の状態で結んだ操作、状態を参照する条件 |

- 作業は担当を必ず持つ。業務に属していて業務に主担当がいても、作業に担当が無ければ途切れとする。
- 情報はシステム・帳票からは辿らない。置き場所に結んだだけで「どの操作にも扱われていない情報」が見えなくならないようにするため。
- 課題 (対象の要素に付くもの) と既定 BUC (業務と一体) は検証の対象にしない。
- 対象のない課題 (未整理) は、エラーではなく [情報] に「対象のない課題」として出す。紐解きの残りが見えるようにするため。
- 辿り着けない要素のうち、アクターに近い側がまったく無いものを「途切れ箇所」とし、種類ごとの理由 (例: 「どの作業にも使われていません」) を出す。関連する情報どうしのように、互いにつながっているだけで外へ出られないものも途切れ箇所にする。
- パネルには途切れ箇所だけを並べ、理由と直し方 (その要素自身で何をすればよいか) を出す。その先で辿り着けない要素 (上へさかのぼるとその途切れ箇所に行き着く要素) は、種類ごとの件数だけを出す。別のレイヤーの要素を開いても直せない (例: 業務の主担当は操作からは結べない) ので、迷わないようリンクにしない。
- 途切れ箇所の要素名をクリックすると、その要素を編集できる固定ボードへ移って選択し、プロパティ欄に出す。
- [情報] として、コンテキストの所属の見直し候補も出す (エラーではないので、ボタンの件数には数えない)。コンテキストに属していない要素 (候補があれば添える) と、属するコンテキストの要素とつながらず別のコンテキストの要素とだけつながる状態・条件・バリエーションを挙げ、候補のコンテキストへ 1 クリックで移せる。情報どうしの関連はコンテキストの結合そのものなので、情報は「未分類」のときだけ挙げる。状態グループは 1 件にまとめる。
- モデルが変わるたびに計算し直す。

## 6. 状態管理と操作

- zustand + immer の単一ストア。`model` (UntieModel) と `history` (undo/redo のスタック)、`ui` (現在のボード、選択、パネルの開閉) を持つ。
- モデルを変える操作はすべて `commands` (純粋関数 `(model, payload) => model`) として `src/model/commands.ts` に置き、ストアはそれを呼んで履歴に積む。コマンドは Vitest で直接テストする。
- 履歴はモデルのスナップショット (immer の構造共有で安価) を最大 100 件持つ。UI の状態は履歴に入れない。
- ノードのドラッグ中は座標をストアの一時状態に反映し、ドラッグ終了時に 1 件の履歴として確定する。名前や説明の入力は、入力欄からフォーカスが外れたとき (または 500 ms 入力が止まったとき) に 1 件として確定する (IME の変換中は確定しない)。ドラッグ中の Undo / Redo は無視する。
- 要素削除は、関係・ボード上のノード・課題の対象・(業務なら) BUC をまとめて消す 1 件の履歴。

主なコマンド:

| コマンド | 内容 |
| --- | --- |
| `addElement(kind, name, boardId?, position?)` | 要素を作る。業務なら既定 BUC も作る。boardId があればそのボードに置く |
| `updateElement(id, patch)` | 名前・説明・種類固有の項目を変える |
| `removeElement(id)` | 要素と付随するものを消す |
| `moveActivity(activityId, bucId \| null)` | アクティビティの所属を変える |
| `moveBuc(bucId, businessId)` | BUC の業務を変える |
| `moveToContext(elementId, contextId \| null)` | 情報・状態・条件・バリエーションのコンテキストを変える (状態はグループごと) |
| `addRelation(sourceId, targetId)` | 両端から種類を決めて関係を作る。不可なら失敗を返す |
| `removeRelation(id)` | 関係を消す |
| `addBoard(name)` / `renameBoard(id, name)` / `removeBoard(id)` | ボードの追加・名前変更・削除。最後の 1 枚は削除できない。削除してもボード上の要素は残る |
| `placeOnBoard(boardId, elementId, position)` | 要素をボードに置く |
| `removeFromBoard(boardId, elementId)` | ボードから外す |
| `moveNode(boardId, elementId, position, size?)` | 座標・サイズを変える |
| `setIssueTargets(issueId, targetIds)` | 課題の対象を変える |
| `clearAll()` | 全て消す |

### 6.1 保存・読み込み

- モデルをそのまま JSON (2 スペースで整形) で保存する。拡張子は `.json`。ボードの配置も含む。UI の状態 (選択・開いているボード・絞り込み) は保存しない。
- 読み込むときは JSON Schema の検証と参照整合性の検査 (`validateModel()`) を通す。通らなければ理由を最大 3 件出して、今のモデルを残す。読み込むと履歴を捨て、作業の固定ボードを開く。
- 保存すると保存先を覚え、次からは同じファイルに上書きする。「別名で保存」は保存先を選び直す。保存するときは入力中の名前・説明を先に確定させる。
- 保存していない変更の判定は、最後に保存・読み込みしたときのモデルと今のモデルが同じ参照かで行う (immer の構造共有なので、Undo で保存時点に戻れば変更なしになる)。サンプルは一度も保存していなければ、編集したときだけ変更ありとする。
- 保存していない変更があるとき、「開く」とウィンドウを閉じる前に確かめる。
- 「新規作成」は空のモデル (空の自由ボード「ボード 1」だけ) を、まだ保存していないモデルとして開く。履歴を捨て、作業の固定ボードを開く。手を付けるまでは保存していない変更なしとして扱う。保存していない変更があれば、先に確認ダイアログで「保存して新規作成」「保存せずに新規作成」「キャンセル」を選ばせる。保存を選んで保存先の選択を取り消したり保存に失敗したりしたら、今のモデルを残す。
- デスクトップアプリでは、ファイル選択と保存先の選択に dialog プラグインを使い、読み書きは Rust のコマンド (`read_model_file` / `write_model_file`) で行う。パスはダイアログで選ばれたものだけを渡す。ブラウザ (開発用) ではファイル選択とダウンロードで代わりにする。
- アプリの CSP は eval を許さないので、ajv で実行時にスキーマをコンパイルできない。検証関数は `scripts/gen-validator.mjs` で事前に生成し (`src/model/schemaValidator.gen.js`)、`pnpm gen:types` で型と一緒に作り直す。CI の `check:types` で生成物がスキーマと一致しているかを検査する。

### 6.2 AI エージェント

**使う AI**: Claude (Anthropic)・Codex (OpenAI)・Gemini (Google) から選ぶ。どれも各社の API をアプリから直接呼ぶ (`src/ai/chat.ts`)。会話の履歴は各社の API の形のまま持ち、モデルを読み書きする道具の定義と実行は共通にする。

| AI | API | 既定のモデル | 備考 |
| --- | --- | --- | --- |
| Claude | Anthropic Messages API (`@anthropic-ai/sdk`、beta) | `claude-opus-5-5` | Opus 5.5・Sonnet 5.5 では、安全のための判定で断られたときに別のモデルで続けるサーバー側のフォールバック (`fallbacks: "default"`) を付ける |
| Codex | OpenAI Responses API (`openai`) | `gpt-5-codex` | |
| Gemini | Gemini API (`@google/genai`) | `gemini-2.5-pro` | |

- モデル名は「AI の設定」で自由に入れられる (候補も出す)。プロバイダーとモデルは端末ごとに覚える (localStorage)。
- **API キー**: プロバイダーごとに「AI の設定」で入れ、OS のキーチェーン (macOS のキーチェーン / Windows の資格情報マネージャー) に保存する (Rust の `keyring` クレート、コマンド `get_api_key` / `set_api_key` / `delete_api_key`)。モデルのファイルには入らない。ブラウザ (開発用) ではタブを閉じるまでメモリに持つ。保存するときは前の項目を消してから作り直す (署名の違うアプリが作った項目は上書きしても読めないため)。読み出しに失敗したときは「(未設定)」と区別して「(読み出せません)」と理由を出し、保存し直すよう案内する (AI の会話・プロンプトからの作成でも同じ)。macOS のキーチェーンはアプリの署名で読み出しを許すので、手元で作り直すときは固定の証明書で署名する (`pnpm app:build`、README)。
- アプリの CSP は、各社の API (`api.anthropic.com`・`api.openai.com`・`generativelanguage.googleapis.com`) への接続だけを足す。

**会話 (下のペイン)**: ツールバーの「AI」で開閉する。依頼を書いて Enter で送る (Shift+Enter で改行、変換中は送らない)。

- AI は道具 (`src/ai/tools.ts`) でモデルを読み書きする: `get_model` (要素と関係の一覧。既定 BUC は隠し、業務に直接属する作業は業務を示す)、`add_element`、`update_element`、`remove_element`、`add_relation`、`remove_relation`、`move_activity`、`move_buc`、`set_context`。中身は既存のコマンドを呼ぶだけで、整合性の検査はコマンドに任せる。失敗は理由を AI に返し、AI が直してやり直す。
- 1 回の返答の間の編集は 1 件の履歴にまとめる (`beginAgentEdit` / `agentApply` / `endAgentEdit`)。元に戻す (Undo) で AI の変更をまとめて戻せる。
- 発言には、開いているボードと選択中の要素を添える (「これを直して」が通じるように)。
- 指示 (`src/ai/prompts.ts`) には、要素と画面での呼び名、つながりの決まり、書き方のヒントと同じ粒度の説明を入れる。
- 道具を使った回数と成否を会話に小さく出す。中断できる。プロバイダーやモデルを変えると新しい会話になる。途中でエラーになったら、次の発言では会話を作り直す。

**プロンプトから作成 (ファイル > プロンプトから作成)**: 初期要望の文章から、新しいモデルを作る (`src/ai/generate.ts`)。RDRA ZeroOne (要望の分析から段階を踏んでモデルを作る進め方) を参考に、指示は自前で書く (参考元のリポジトリにはライセンスの表示が無いので、文面は使わない)。

1. 分析: 初期要望を段階 1〜4 (要望の分析、登場人物、業務と活動、情報・状態・条件・バリエーション) で検討し、箇条書きで出してもらう。画面にそのまま流す。
2. 提出: 段階 5 (作業と操作) まで進め、モデル全体を道具 `submit_model` で出してもらう。下書きは名前で参照する形 (`src/ai/spec.ts`) で、AI には id を作らせない。
3. 組み立てと検査: 下書きを既存のコマンドでモデルに組み立て、スキーマ・参照整合性の検査と、担い手まで辿れるかの検査を通す。見つからない名前や担当の無い作業などがあれば、理由を返して出し直してもらう (2 回まで。それ以降は気づいたことが残っていても受け付ける)。
4. 受け付けたら、新しい (まだ保存していない) モデルとして開き、AI エージェントのペインを開く。作成の会話 (初期要望と、分析・作成結果のまとめ) を引き継ぐので、そのまま「〇〇を足して」と続けられる。

## 7. サンプル (架空の宿泊施設)

起動時に `src/sample/hotel.ts` のモデルを読み込む。実在の施設名・実データは使わない。

- **業務 (5)**: 予約受付、チェックイン、滞在中の対応、チェックアウト、清掃・準備
- **アクター (4)**: 予約担当、フロント担当、清掃担当、支配人
- **外部アクター (2)**: 宿泊客、旅行会社
- **BUC**: 「滞在中の対応」の中に「客室対応」「飲食提供」「追加料金の対応」の 3 つ (この業務の作業はすべていずれかの活動に入る)。他の業務は既定 BUC のみ (BUC の使い方を示すため 1 業務だけ BUC を切る)
- **アクティビティ (15 前後)**: 予約を受け付ける、予約内容を確認する、予約を変更・取消する、到着を確認する、本人確認をする、部屋を割り当てる、鍵を渡す、客室の要望に応える、ルームサービスを提供する、追加料金を記録する、宿泊料金を計算する (宿泊管理システムが担当)、請求を作成する、精算する、鍵を回収する、清掃を指示する、清掃する、部屋を点検する
- **ユースケース (10 前後)**: 予約を登録する、予約を検索する、予約を変更する、予約を取り消す、チェックインを記録する、部屋の割り当てを記録する、追加料金を登録する、請求金額を計算する、請求書を発行する、決済を記録する、チェックアウトを記録する、清掃状況を更新する
- **システム (4)**: 宿泊管理システム、会計システム、予約サイト、決済サービス。宿泊管理システムは作業「宿泊料金を計算する」、予約サイトは「予約を受け付ける」、決済サービスは「精算する」を担当する
- **帳票 (2)**: 宿泊者名簿、清掃チェック表
- **コンテキスト (4)**: 予約、顧客、客室、料金
- **情報 (6)**: 予約 (予約)、宿泊客 (顧客)、部屋・清掃記録 (客室)、料金プラン・請求 (料金)。宿泊管理システム・予約サイト・決済サービスから取得し、宿泊管理システム・会計システム・宿泊者名簿・清掃チェック表に保存する
- **状態 (2 グループ)**: 予約の状態 (仮予約 / 確定 / チェックイン済 / チェックアウト済 / 取消)、部屋の状態 (清掃待ち / 清掃中 / 準備完了 / 使用中)
- **バリエーション (3)**: 部屋タイプ (シングル / ツイン / スイート)、予約経路 (電話 / 予約サイト / 直接来館)、支払方法 (現金 / クレジットカード / 事前決済)
- **条件 (3)**: 取消料が発生する、早めのチェックインができる、満室である
- **課題 (5)**: 予約サイトからの予約を手で転記している (重要度 5)、繁忙期にチェックインの列ができる (4)、追加料金の記録漏れがある (4)、清掃完了の連絡が電話頼みになっている (3)、取消料の説明が担当者によって違う (2)
- **自由ボード (3)**: 「全体」(業務の枠とアクティビティ。アクターはラベルで出す)、「予約からチェックアウトまで」(アクティビティ → ユースケース → 情報・条件)、「情報と状態」(情報・状態・バリエーション・条件と状態遷移)

サンプルはテストでスキーマ検証と参照整合性検査を通す。

## 9. テスト

Vitest で以下を検証する。E2E は省く。

- モデル: id 生成、要素の追加・削除と付随処理 (既定 BUC、関係・ノード・課題対象の掃除)、所属の変更。
- 関係ルール: 表にある組み合わせは引け、ない組み合わせは引けない。重複と自己参照の拒否。無向関係の同一視。
- 検証: スキーマに合わない JSON とエラー内容。参照整合性の各ケース。
- Undo / Redo: 連続操作と履歴上限。
- サンプル: スキーマ検証と参照整合性検査を通る。
- 固定ボード: 各レイヤーの枠の組み立て、絞り込み、枠への追加・既存の紐づけ・外す。
- UI: 要素一覧・固定ボード・プロパティ欄・ツールバーの主要な振る舞い (自由ボードで所属・関係を変えられないことを含む) を Testing Library で確認する。キャンバスは React Flow のノード・エッジへの変換 (座標の相対化を含む) を純粋関数として切り出し、その関数をテストする。
